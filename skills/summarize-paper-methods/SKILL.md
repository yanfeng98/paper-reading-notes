# 跨论文方法汇总（生成与复核）

默认产物是一份 `docs/<slug>.md`，把同一主题的多篇**已读论文**按同一套问题重写，并在篇间做横向对比与术语消歧。**权威是原文**——按文档声明的版本重新获取的原文，不是记忆，也不是各篇笔记（笔记是索引与二次材料；两者冲突时回原文，并在文档里标明版本）。

本 skill 所在目录为 `<仓库根>/skills/summarize-paper-methods/`，检查脚本为 `<该目录>/scripts/doc_lint.py`（机械项）与 `<该目录>/scripts/github_render_check.py`（GitHub 原生渲染计数），PDF 脚本为 `<该目录>/scripts/render_pdf.mjs`。经 `~/.claude/skills/` 的符号链接加载时，先解析真实路径再定位仓库根目录，不依赖调用时的工作目录。仓库内的现有示例是 `docs/rsi-methods.md`（篇数以文档为准）：只看结构与做法，不照搬其中的 RSI 术语。

## 这份 skill 管什么、不管什么

- **管**：跨篇汇总文档的生成（新建、增量）与复核；统一框架、横向表、术语消歧、版本口径、全文一致性、渲染检查。
- **不管**：单篇精读与笔记生成（→ `read-paper-blog`）；单篇笔记的逐项核对细节与像素测量方法（→ `check-paper-note`，直接引用，不重写）；大范围文献综述（按 read-paper-blog 的边界，不自动扩展）。
- **缺笔记的论文**：先与用户确认是否按 `read-paper-blog` 精读并落笔记；不精读时，文档里标注「无单篇笔记」并只引用原文，不把二手印象写成机制描述。

## 两种模式与判定

| 用户意图 | 模式 |
| --- | --- |
| 给主题/论文列表，要汇总、对比、串讲；或往已有汇总里加一篇 | **生成**（新建 / 增量） |
| 给已有汇总文档，要检查、复核、和原文对一下 | **复核**（默认动手修复；用户明确只要报告时除外） |

## 开工决策

在动笔前把下面几项定下来（能从 README/笔记推断的直接推断，**影响产物形态的必须问用户**）：

1. **篇目与纳入标准**：至少 2 篇；用户只给主题时，从根 `README.md` 与 `notes/` 提候选（编号 / 标题 / 是否已有笔记 / 建议版本），列给用户确认后再开工。
2. **版本基准**：**README 当行已锁定具体版本（如 v2/v3 或归档 PDF）时以该版本为准**；用户指定版本时用指定版；两者都未锁定版本时取生成日最新版并写明。非 arXiv 来源用归档 PDF 的版本。同一工作有多个渠道（项目页/arXiv/OpenReview/期刊）时，不混用不同版本的实验数字。
3. **产物路径**：`docs/<slug>.md`（slug 用简短英文短横线）。不新建其他目录，不改 `notes/` 里的单篇笔记（除非用户同时要求）。
4. **公式与渲染约定**（用户已明确要求；如需例外须用户明确说明）：正文段落/列表/表格**不写行内公式**；独立公式块**一律用 ```math 代码围栏**（GitHub 原生支持，列表内也可用）；新文档**不要写 `$$…$$`**（单行 `$$` 与列表项内的 `$$` 在 GitHub 上不可靠，只有旧文档兼容时才保留）。全篇不超过 3 处、每块紧跟一句白话读法；伪代码用围栏代码块；迭代闭环用 Mermaid。货币符号 `$` 请放进代码段或改写（检查脚本会把正文中的 `$` 视为行内公式）。
5. **README**：默认不动。用户明确要求挂链接时，只在**编号说明 blockquote 之后、`## 论文` 之前**新增或更新**一行**主题汇总链接（同步编号集合与篇数），不重排、不改表格、不动其他行。
6. **提交**：不自动提交；用户明确要求时再提交。

## 生成流程

### 第 1 步：确定篇目与纳入标准

确认「哪几篇、为什么是这几篇」：同一主题/同一系列；写清纳入与排除的理由（例如「同主题且已有笔记」「用户点名的五篇」）。用户只给主题时，候选清单要标出**缺笔记**的论文，并先问是否补笔记。

### 第 2 步：锁定每篇的版本与身份

- 每篇一个独立临时目录（如 `/tmp/<topic>-docs/<编号>/`），不与下载物混放。
- **arXiv**：从 abs 页读**版本列表与各版日期**；下载目标版本；校验三件事——`%%EOF` 存在、**两次下载 sha256 一致**、页数（`gs -q -dNODISPLAY -dNOSAFER -c "(<pdf>) (r) file runpdfbegin pdfpagecount = quit"`）合理。`curl -m` 超时会把文件截断成「看起来像 PDF」的半截文件，**首次下载失败要重取并比哈希**。若与笔记记录的 sha256 不同（同一 vN 可能被重新发布/重编译），先逐页比文本与图，记录旧/新副本；不把旧副本的缺陷写成当前版的问题。若正文/数字有实质差异，按版本问题记录并请用户确认是否重读，不静默换基准。
- **非 arXiv**：用仓库归档 PDF；核对编号、页数与笔记记录的 sha256。
- 记录成表（文档开头的版本表就是它的定稿）：编号、标题、版本、日期、页数、来源链接、笔记路径、README 当行指向。
- **与笔记的版本关系**：笔记可能基于旧版（实际发生过：某文项目页版 36 页，arXiv v2 43 页且重写了目标函数）。文档按 README 指向的版本写，差异写进该篇的〈版本关系〉，不静默沿用笔记的旧口径。

### 第 3 步：逐篇建档

每篇派一个子 agent（并行）回原文产出 dossier，交给它固定十问（见下节）。要求：每个数字带**页码/表号/图号/节号**；明确区分「原文说的」「复算的」「图内读数的」「你的推断」；复核该篇笔记的〈原文自身的表述张力〉；末尾给出「未核/无法确认清单」。dossier 是工作产物，**不提交进仓库**。

### 第 4 步：设计统一框架与横向表

先定框架再写正文：章节顺序（默认按编号降序，或按用户指定）、每篇统一的子节模板、速览表列、概念对照的术语表、横向对比的维度。**非迭代类论文**（基准、评测、分析）做**槽位映射**——同一节回答「它测量什么/协议是什么」，不强行套「一轮迭代」的演化闭环；在格子里注明它的定位（如「不提出演化方法」）。

### 第 5 步：按模板成文

按〈文档模板〉写六部分；遵守〈写作纪律〉；写完做〈术语审计〉。总体判断一节必须标注「本文归纳，非任一篇的结论」，且不引入新事实。

### 第 6 步：核对与交付

按〈检查清单 A–H〉自查，跑 `doc_lint.py` 和（有公式/Mermaid 时）`github_render_check.py`，再按〈复核模式〉执行相应轮次；用户要求发布时按〈渲染与发布〉运行 `site/build.py`、生成/更新 PDF 并核对 Pages 链接；用户要求挂 README 时加一行；在对话里交付（见〈交付〉）。

## 逐篇 dossier：固定问题与证据要求

1. **一句话内核**：它交付的到底是什么（系统/方法/基准/分析），被改的对象是什么。
2. **要解决什么**：具体失败现象 + 论文给的证据（不是抽象动机）。
3. **系统由哪些部件组成**：表格 `部件 | 具体是什么 | 作用 | 输入 → 输出`，用论文原名，落到载体（文件/代码/状态/门控）。
4. **一轮迭代怎么走**：编号步骤；谁调用谁、产物落在哪；可选阶段与短路条件；门/接受步骤的**完整顺序**。
5. **轮与轮之间更新了什么**：`更新什么 | 载体 | 谁写 | 何时写 | 可否回滚`；明确哪些不动（权重？评测器？）。
6. **什么时候停、什么算更好**：停止条件、接受准则（是否非补偿）、无候选时的行为、预算。
7. **监督信号**：verifier / reward / judge / 无监督；谁打分、口径、是否留出。
8. **关键数字**：主结果、相对基线、成本；每个数字注版本与出处；口径（均值构成、峰值/最终值、预算/实耗、百分点/相对提升）必须写清。
9. **术语**：本篇的易混词与同名不同义；哪些名字只是类比。
10. **陷阱与版本**：作者自述局限 + 你发现的问题；各版本差异与代码/数据发布状态（独立核验并注明日期）。

## 文档模板

1. **关于这份文档**：目的、覆盖篇目与版本表、核对方式与日期、公式约定、读法建议。
2. **一页速览**：一张表（≤7 列），一眼看出每篇「被改对象 / 一次迭代 / 谁动手 / 产物与载体 / 反馈信号 / 接受规则与停止」。
3. **逐篇章节**（每篇同一子节顺序）：`一句话` / `它要解决什么` / `系统由哪些部件组成` / `一次迭代怎么走`（含 Mermaid）/ `轮与轮之间更新了什么` / `什么时候停、什么算「更好」` / `监督信号从哪来` / `关键数字` / `陷阱与边界` / `版本关系`（多版本时）。
4. **概念对照**：`名词 × 论文` 的表，逐格写「它实际是什么」；没有该概念时写清是「未用作机制名」还是「确实没出现」。
5. **横向对比（坐标系）**：用一组维度（如「改什么 / 谁改 / 何时改 / 验收 / 反馈」）把各篇放进同一张表；借其他笔记的框架时注明出处，并说明省略了哪些维度。
6. **版本与核对说明**：采用版本、核对手段、图内读数口径、仍不可核验的事项、文档与各篇笔记的关系。

## 写作纪律：数字、归属、公式

- **每个数字带出处**（页/表/图/节）和版本；没有出处的数字不写。速览表与坐标系表列数有限，可只给结论，详细出处见各篇〈关键数字〉（表下或表前注明这一点）。
- **表格/附录值优先于摘要值**；两者冲突时就地注明（实际发生过：摘要写「30% fewer tokens」，表格是 3.80M → 2.42M ≈ 36%；摘要写 OOD +4.3，表格 JobBench 是 +4.7）。
- **复算值**标「复算」并写口径（分母、是否按任务数、四舍五入）；**图内读数**标「图内读数」并写来源（笔记的像素测量/本轮复测），不能写成论文数字。
- **极值、全称、否定断言**逐条回表格与全文找反例或检索（「唯一/最大/从未/未使用」是重灾区）。
- **原文自身的张力**（正文 vs 附录、摘要 vs 表、图例 vs 图注、面板标题 vs 图注）如实记录，不替作者裁决。
- 区分**作者结论 / 原文数值 / 复算 / 图内读数 / 本文推断 / 补充背景**；总体判断一律标「本文归纳」。
- 正文零行内公式；少量独立公式块必须配白话读法；伪代码是示意就注明，不冒充作者实现。

## 术语审计

概念对照表的每一格都可能出错，尤其是「未使用 / 无此词」：

1. 先建候选术语表（各篇笔记标题、速览单元格、出现在 ≥2 篇的词、易混对）。
2. 把每篇原文**抽成全文文本**（`gs -sDEVICE=txtwrite -dTextFormat=3` 或 `pymupdf`），按术语做**大小写不敏感**的全文检索，取上下文；折行/连字先归一化（把空白折叠后再搜）。
3. 分类：**机制名** / **普通词义出现** / **确实没出现** / **不适用**。「普通词义出现」不等于「用作机制名」（实际发生过：`policy` 在某篇里是「基础策略」之意、在另一篇里只是 `tool policy` 的搭配；`probe` 只在定性描述里出现）。**组件名、工具名、阶段名等专名也应归入「机制名」（或单列「专名」）**，不要因为词形普通就归为「普通词义」（实际发生过：`verification policies`、`tools/probe.py`、`candidate generation` 被写成普通词义/普通搭配）。
4. **负断言必须记录检索词与来源**；有命中先读上下文再下结论。文本抽不出（字体无 Unicode 映射）时，回渲染页或换工具，不以「抽不到」当「没有」。
5. 同名不同义单列说明（实际发生过：`policy` 在一篇里指冻结的 LLM、在另一篇里指被进化的探索策略代码；`L0/L1/L2` 在一篇里是状态层级、在另一篇里只是正则化类比；`β` 在两篇里分别是预算偏好旋钮与成本系数）。
6. 表列顺序 = 章节顺序；新增一篇时必须**逐格**回原文核对新列，不按相邻篇类推。

## 增量维护：新增或替换一篇论文的联动清单

往里加一篇论文时，下面每一处都要改，漏一处就会自相矛盾：

1. 标题与开篇的「共 N 篇」；
2. 版本表新增一行（版本、日期、页数、来源、笔记、README 指向）；
3. 一页速览新增一行；
4. 概念对照新增一列（列序=章节序）；
5. 坐标系/横向对比新增一列；
6. 总体判断补上该篇的定位，必要时调整旧结论（如「唯一……的一篇」要重新核）；
7. 版本与核对说明里的篇数、核对轮次、图内读数来源；
8. 「与各篇笔记的关系」里的条目；
9. README 顶部链接行里的编号集合与「N 篇」（仅在用户要求维护该行时）；
10. 发布联动：按〈渲染与发布〉运行 `python3 site/build.py --out _site`、重新生成 PDF、跑 `github_render_check.py`；若更新 README 行，在线链接指向站点根/`/docs/<slug>/`，PDF 文件名对得上；Pages 部署后核对实际 URL。

替换/更新版本时同样走一遍，并在该篇〈版本关系〉写清旧版与新版的差异。

## 复核模式：分层与五轮工作流

**分层**：

- **新建或大改**（新增论文、重写章节、批量修复）：走完整五轮；
- **单点修正**（一个数字、一处措辞）：只查受影响的 A/B 项 + 关联的一致性项 + lint；若动到公式/Mermaid 或 PDF，按〈渲染与发布〉补跑渲染检查/重生成 PDF。

**五轮**（本次实战验证有效；每轮可派独立子 agent，要求「只报告、不改文件」，其结论逐条自验；**高严重度发现也要先回渲染页验证——混淆矩阵/分类图的列序读反是常见误报**）：

1. **全量回原文**：逐篇核对数字、机制、表格与图内标签；
2. **修正项复查 + 内部一致性 + 渲染**：上一轮每项修复是否改对；跨表列序、同一数字多处一致、lint；有公式/Mermaid 时跑 `github_render_check.py`；有 PDF 时重新生成并目检高图完整；
3. **术语审计 + 文档 vs 笔记/README**：负断言逐条检索；文档与各篇笔记的版本/结论是否一致；README 链接与篇数；
4. **元数据直查**：版本列表/日期、页数、sha、README 指向；
5. **读者视角连贯性 + 数字抽查**：只读文档能否回答每篇的四个问题（改了什么/组件/一轮流程/轮间更新）+ 验收/监督/数字/版本；随机抽查数字。

**「未发现问题」是合法结论**，但必须附覆盖度声明（查了哪些、怎么查、哪些没查）。

## 检查清单 A–H

**A. 范围与版本基准**：标题、速览、版本表、章节的 N 一致；每篇有编号/来源/版本/日期/页数/笔记链接；README 指向与文档采用版本一致；arXiv 版本列表与日期独立核过；页数已核对并写入版本表，sha256 已记录在工作记录或核对说明（不要求写进版本表）；笔记版本更旧时已在〈版本关系〉说明。

**B. 事实与数字**：每个数字有出处；表格值优先；复算有标注与口径；图内读数有来源；口径陷阱（均值构成、峰值 vs 最终值 vs 域均值、预算 vs 实耗、摊销范围、百分点 vs 相对提升、分母是否固定）；极值与全称断言有反例检查。**混淆矩阵/分类热图逐行逐列读标签**，不按位置推断（列序读反是高发误报）。

**C. 机制**：「改了什么」落到载体；部件表完整（名称/是什么/作用/输入输出）；一轮流程的步骤、可选阶段、门顺序、各阶段读取对象；非补偿逻辑；停止与接受；监督信号与成本边界；不把「同一轮内」写成「交替」、不把「并行」写成「先后」。

**D. 归属与证据层次**：「论文说/§x/图注」逐处回原文确认；摘要/引言/结论不混写；原文自身张力如实记录；负断言有检索记录；多面板图逐面板读「图内标题 + 图注」；跨文引用（「某篇就是另一篇引的那篇」）要到**被引论文**里核对。

**E. 术语与概念对照**：分类正确；「未使用」有检索记录；同名不同义已消歧；列序与章节序一致；新列逐格回原文。

**F. 横向一致性与结构**：每篇都出现在每张表与每个章节；子节名一致（非迭代论文可按其协议命名，如「一次运行怎么走」，但顺序与语义对应；标题可带括号说明）；N、日期、版本表与各篇版本行一致；总体判断覆盖全部篇目且不引入新事实；相对链接可达。

**G. 读者理解**：只读文档能回答每篇的四问 + 验收/监督/关键数字/版本；Mermaid 与文字流程一致；伪代码与文字一致；公式块后跟白话读法，且**全篇公式块不超过 3 处**（人工核对，脚本只计数）；没有「见下节」指不到的地方。

**H. 机械检查与交付**：`doc_lint.py` 零错误；有公式/Mermaid 时 `github_render_check.py` 通过（源块数与 GitHub 渲染数一致、无 `language-*` 残留）；`python3 site/build.py --out _site` 成功（README 双向映射、图片/链接/计数校验通过）；**再用无头 Chromium 实载改动页，确认无 `render-error`、Mermaid 块数等于 `data-expected-mermaid`**（`github_render_check` 只验围栏，不验语法）；若生成 PDF，`render_pdf.mjs` 校验通过且目检高图完整；脚本只做机械项，Mermaid 语义、锚点与链接语义仍需人工或渲染核对；**表格单元格内用 `**…**` 强调中文时，确认闭合标记后接标点/空格、渲染后无字面 `**`；新增列/宽表后目检 PDF，列数多到过窄时缩短单元格或拆表，保持列序与篇目不丢**；README 边界未越；核对说明与实际做过的核对相符；临时文件已清理；未提交。

## 修复规则

- 先改**确凿错误**，再处理易误读的表述；不确定的宁可不改或在文中标注不确定。
- 每处修改都回原文验证**新文字本身**（补丁也会引入新错误）。
- 最小改动；保留用户手写内容与批注。
- **不静默更换版本基准**（换版本=重读，需用户明确要求）；不把「加限定词」当成修复。
- 更新 N 篇计数与所有联动表；README 只在用户要求时动那一行，其他行不动。
- 修复后重跑 lint 与受影响的核对项；不自动提交。

## 常见陷阱（均为实际发生过）

1. **版本漂移**：文档采用的新版重写目标函数，而笔记描述的是旧版——不标版本就会「两边都对、合起来错」。
2. **摘要 vs 表格**：摘要的百分比与表格复算不一致；冲突时用表格值并注明。
3. **口径**：「五基准均值」实际是四基准（不含某基准）；「峰值」在某域是域均值；预算不是实耗；摊销只适用于某个基准。
4. **「未使用」过度断言**：`policy`/`probe`/`held-out`/`generation` 都出现过「文档说没有、原文其实有」的情况。
5. **归因**：把图内读数写成论文数字；单点尖峰当成普遍改进；图例线位置与标签不符。
6. **机制误读**：把「同一轮内执行」写成「交替」；门的检查顺序漏项；把 A 阶段读取的对象写成 B 阶段读取。
7. **跨表列序不一致**：概念对照/坐标系与正文章节顺序不同，读者对列错位；新增一篇时列序必须同步。
8. **README 越界**：顺手改了表格、分组或其他行；默认只允许用户明确要求的一行链接。
9. **二手材料当原文**：只读笔记不读原文就写机制；笔记的推断被当成论文结论。
10. **公式渲染**：行内 `$…$`、单行 `$$…$$` 或列表项内的 `$$` 在 GitHub 上不可靠；新文档统一用 ```math（列表内也有效），并用 `github_render_check.py` 验证。
11. **PDF 高图 / Pages**：Mermaid 图超过一页高时会被跨页裁断；阅读页打印样式已限高 250mm，仍要目检高图完整。Pages 未启用时 workflow 应跳过部署而不是每次 push 红叉；分支部署已退役，完整站点必须用 Actions。
12. **同版本 PDF 被重发布**：同一 arXiv vN 的 PDF 可能被替换/重编译；hash 与笔记记录不同先逐页比文本与图，别把旧副本的图缺陷当成当前版问题。
13. **CJK 表格加粗**：`**…**` 的闭合标记后面紧接汉字时可能显示字面 `**`；闭合标记后接标点/空格，渲染后目检。
14. **Mermaid 标签触发整页失败**：阅读页为 CJK 溢出设了 `htmlLabels:false`；Mermaid 11.12 在标签较宽、需要自动换行时，节点/边标签以 `1.`/`1)` 这类有序列表标记开头**且**含 `<br>` 会抛 `splitLineToFitWidth does not support newlines in the line`，整页变成「正文渲染失败」，而 `build.py`、`github_render_check` 都可能通过（`doc_lint.py` 会提示但不阻断）。标签改用 `①②③`/`第 1 步` 或去掉 `<br>`；交付前仍用浏览器实载确认。

## 环境与工具

- 本机（2026-10 实测）：poppler 系命令行工具（`pdftotext`/`pdfinfo`/`pdftoppm`）缺失；系统 `python3` 也缺 `pymupdf`/`PIL`/`numpy` 与 `pip`。已装 Miniconda（`~/miniconda3`，base），`pymupdf`/`Pillow`/`numpy` 可用。**本文中的 `python3 -I` 在本机指 `~/miniconda3/bin/python3 -I`**——agent 的非交互 shell 不会自动激活 conda；交互终端经 `conda init bash` 后已指向 conda。ghostscript（`gs`）可作后备：
  - 抽文本：`gs -q -dNOPAUSE -dBATCH -sDEVICE=txtwrite -dTextFormat=3 -sOutputFile=<out.txt> <in.pdf>`；
  - 页数：`gs -q -dNODISPLAY -dNOSAFER -c "(<pdf>) (r) file runpdfbegin pdfpagecount = quit"`；
  - 渲染页面：`gs -q -dNOPAUSE -dBATCH -sDEVICE=png16m -r<N> -dFirstPage=<a> -dLastPage=<b> -sOutputFile=<prefix>-%03d.png <pdf>`；
  - 校验：`sha256sum`、`tail -c 40 <pdf> | strings`（找 `%%EOF`）；
  - 下载：`curl -sSL -m <sec> -A '<UA>' -o <out> <url>`；大文件放后台，别用默认超时。
- pymupdf 的字体判定（`page.get_text('dict')`）、矢量/图块定位（`get_drawings()`/`get_image_info()`）、局部裁剪（`page.get_pixmap(clip=…)`）与 PIL/numpy 像素测量均可用；换到未装这些包的机器时，把相应核对标注「未做」，不得声称已核。
- `Read` 工具读 PDF 每次最多 20 页，长文分页读；文本抽取只做检索，公式/表格/上下标以渲染页为准。
- **无头浏览器可用于页面渲染验证**：本机 `~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome` 已存在（Playwright 缓存），可直接 `--headless=new --dump-dom`；`npx` 安装 mermaid-cli 会超时，不要因此跳过渲染核对。装了 Playwright 时也可用 `render_pdf.mjs` 的 `PLAYWRIGHT_MODULE`。
- 渲染发布（静态站点 / PDF / Pages）见下一节〈渲染与发布〉。
- 临时目录 `/tmp/<topic>-docs/<编号>/`；用后清理，不把临时文件提交进仓库。

## 渲染与发布（静态站点 / PDF / Pages）

### 站点源码与构建

- 源码在 `site/`：`build.py`（Python 标准库）、`templates/home.html`（资料库）、`templates/doc.html`（阅读页）、`assets/site.css`、`assets/site.js`、`vendor/`（marked/MathJax/Mermaid 与许可证）。构建输出 `_site/`，已 gitignore，不提交。
- 构建：
  - `python3 site/build.py --out _site`
  - 本地预览：`python3 -m http.server 8000 --directory _site`
- `build.py` 自动发现 `notes/papers/*/note.md`、`notes/blogs/*/note.md`、`docs/*.md`；从 README 5 列表取编号/标题/年份/单位/原文链接；每个 note.md 必须有 README 行，否则构建失败（双向校验）。它同时校验 31 张笔记图片、全部本地链接、公式/Mermaid 围栏计数。
- 路由按源文件深度生成：`/notes/papers/<slug>/`、`/notes/blogs/<slug>/`、`/docs/<slug>/`；首页 `_site/index.html` 是资料库（卡片、筛选、搜索、排序），阅读页是独立文章页。笔记图片按原 `assets/` 目录复制，不扁平化。
- 新汇总：放到 `docs/<slug>.md` 即自动进入资料库；多篇汇总都会作为首页 featured 卡片，各自有独立 `/docs/<slug>/` 阅读页。同名 `docs/<slug>.pdf` 会复制到 `/docs/<slug>/<slug>.pdf` 并在阅读页显示 PDF 按钮。新笔记：写入 `notes/.../note.md` 并回写 README 后自动进入；不需要手改站点。
- 汇总相对链接 `../notes/...` 在阅读页由 resolver 改成站内笔记路由；`papers/*.pdf` 等未复制文件跳到 GitHub；笔记的 `assets/...` 用站内复制路径。Python 构建期与 JS 运行期规则一致，构建失败即代表链接不可达。
- 旧 `docs/index.html`、`docs/assets/reader.css`、`docs/.nojekyll` 已删除；旧 `?doc=rsi-methods.md` 由首页 JS 重定向到 `/docs/rsi-methods/`，根级 `_site/rsi-methods.pdf` 保留旧 PDF 链接兼容别名。
- 打印 CSS 把 Mermaid 限高 250mm；高图等比缩放避免跨页裁断，宽幅 LR 图在 A4 上会偏小，必要时改成 TD/拆图。
- **构建成功 ≠ 页面能渲染**：`build.py` 只校验围栏计数；Mermaid 语法错误会让阅读页整页显示「正文渲染失败」。每次构建后实际打开至少一个改动页：
  ```bash
  CHROME=$(ls -d ~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome | sort -V | tail -1)
  "$CHROME" --headless=new --no-sandbox --disable-gpu --virtual-time-budget=20000 \
    --dump-dom "http://127.0.0.1:8000/<route>/" > /tmp/dom.html
  ! grep -q 'class="[^"]*render-error' /tmp/dom.html   # 无匹配才算通过
  ```
  再核对 `.mermaid` 块数等于 `data-expected-mermaid`、TOC 条目数非零（含表格的文档再核对表格数）；`render_pdf.mjs` 内部也会检查 `.render-error`、图数与打印溢出，失败时不写出 PDF。没有 Playwright 缓存时用 `PLAYWRIGHT_MODULE` 或系统 Chromium，仍要做这一步。

### GitHub 原生渲染检查（笔记和汇总都适用）

- 公式/Mermaid 一律用围栏（```math / ```mermaid）；不用行内 `$…$`、单行 `$$…$$` 或列表项内的 `$$`。
- 机械检查：
  - `python3 -I <skill 目录>/scripts/doc_lint.py <file.md>`
  - `python3 -I <skill 目录>/scripts/github_render_check.py <file.md>`
- `github_render_check.py` 会 POST 到 GitHub Markdown API，要求源公式/图块数与 `<math-renderer>`/`highlight-source-mermaid` 数一致，且没有 `language-math`/`language-mermaid` 残留；需要联网，未认证限 60 次/小时，可设 `GITHUB_TOKEN`。它只验证 GitHub 是否识别围栏，**不验证 Mermaid 图语法**——图语法由站点/PDF 渲染或 mermaid 解析器另行检查。
- 旧文档若仍有 `$$` 块，先按用户要求改写为 ```math；批量改写旧笔记需要用户明确要求。

### PDF

- 先生成站点，再打印：
  ```bash
  python3 site/build.py --out _site
  PLAYWRIGHT_MODULE=<playwright 模块路径> node <skill 目录>/scripts/render_pdf.mjs \
    --site _site --page docs/rsi-methods/index.html --out docs/rsi-methods.pdf
  python3 site/build.py --out _site   # 把新 PDF 复制进 _site
  ```
- 脚本服务 `_site`，强制浅色 + print media，等待 `window.__renderDone`；检查 `.render-error`、公式/Mermaid 计数、`leftover`、打印溢出，失败**非零退出且不写 PDF**。多篇汇总时把 `docs/rsi-methods/...` 和 `docs/rsi-methods.pdf` 换成目标 slug 即可。
- 每次改动汇总 Markdown 或站点样式后重新生成；用 pymupdf/`gs` 抽查页数、公式页和含图页，重点看高图完整、宽图可读。构建发现 PDF 比 Markdown/样式旧会警告，不失败。
- PDF 文件名必须与汇总 Markdown 同名；阅读页 PDF 按钮和根级别名都依赖这个约定。CI 不安装 Playwright，不生成 PDF。

### GitHub Pages

- **只支持 GitHub Actions**；分支部署 `main /docs` 已退役。`.github/workflows/pages.yml` 在 `notes/**`、`docs/**`、`site/**`、`README.md` 或 workflow 变化时触发，执行 `python3 site/build.py --out _site`，再上传 `_site`。**本地构建/PDF 不会上线；必须 commit/push**，Actions 才会构建部署。
- 构建在 Pages `build_type` 守卫之前执行，保证 README/链接/图片校验每次 push 都跑；未启用或仍是 `legacy` 分支部署时只跳过部署步骤并给 notice。
- **首次必须在 Settings → Pages 选择 GitHub Actions**：`GITHUB_TOKEN` 没有权限自动开启 Pages；启用后手动 Run workflow 或下次 push 生效。
- 部署后核对实际 URL：账号自定义域名可能让 `github.io` 301 到自定义域名；README 只加用户要求的一行链接，链接用实际可达地址。旧 `?doc=` 与根 PDF 别名只用于兼容，不再作为文档主入口。
- **部署核对**：没有 `gh` 时用 GitHub API 查最新 run（`/repos/<owner>/<repo>/actions/runs?per_page=5` 的 `status`/`conclusion`）；部署后用 `curl -sIL` 检查首页、`/docs/<slug>/`、笔记页与 PDF 的 HTTP 状态/内容类型。**README 里的 `./docs/<slug>.pdf` 是仓库相对链接**，站点 PDF 实际在 `/docs/<slug>/<slug>.pdf` 与根级 `/<slug>.pdf`；不要用 `/docs/<slug>.pdf` 验证站点（会 404），也不要把这个 404 当成构建失败。

## 与其他 skill 的分工

- **单篇笔记没有**：按 `read-paper-blog` 精读生成（需用户同意）；文档里标「无单篇笔记」。
- **单篇笔记复核**：按 `check-paper-note`（像素测量、字体判定、版本复核等细节都在那里），本 skill 引用其结论，不重复实现。
- **本 skill 只做**：跨篇框架、逐篇方法重建、术语消歧、横向对比、汇总级一致性与复核。
