# 论文与英文博客阅读

默认交付完整中文技术笔记，保留关键英文术语，重点解释问题、设计动机、工作机制和工程意义。假定读者有机器学习基础；对本文特有的概念和理解方法必需的背景做解释，不从通用基础知识开始长篇铺垫。用户指定阅读重点、输出位置或只需对话解答时，以当前要求为准；只需对话解答时不创建笔记或持久归档文件。

用户要求离线或仅基于提供内容时，该限制适用于论文、博客和补充资料：不联网获取原文、确认最新版本或核验当前软件行为；按已有材料解读，并明确哪些信息未核实。

## 获取和确认原文

- 接受 arXiv 链接或编号、论文 PDF 链接、本地 PDF、英文博客链接及用户提供的正文。用户只给出标题时，先查根 `README.md` 的题目列与 `papers/` 归档——命中唯一就直接复用该行的编号与归档（不重复归档、不新建编号），命中多行或含糊时先确认文章身份。
- 对在线来源实际获取原文，不能用搜索摘要代替全文。优先使用环境已有的网页、PDF 和文件读取能力，不假定某个专用工具存在，也不默认安装依赖。**本机环境（2026-10/11 实测）**：poppler 系命令行工具（`pdftotext`/`pdfinfo`/`pdftoppm`）缺失；系统 `python3`（`/usr/bin/python3`）也缺 `pymupdf`/`PIL`/`numpy` 与 `pip`。已安装 Miniconda（`~/miniconda3`，base 环境），其中 `pymupdf`/`Pillow`/`numpy` 可用。**本机 `python3` 现已解析到 `~/miniconda3/bin/python3`（2026-11 在 agent shell 复核，`python3 -I` 同样可用）；若某次环境解析到 `/usr/bin/python3`（缺 `pymupdf`），改用 `~/miniconda3/bin/python3 -I` 显式调用。** 文本抽取/页数/渲染也可用 ghostscript 后备：`gs -q -dNOPAUSE -dBATCH -sDEVICE=txtwrite -dTextFormat=3 -sOutputFile=<out.txt> <in.pdf>`（输出会折行，检索前先把换行折叠为空格）；`gs -q -dNODISPLAY -dNOSAFER -c "(<pdf>) (r) file runpdfbegin pdfpagecount = quit"`（`file` 报的页数不可靠这一点不变）；`gs -q -dNOPAUSE -dBATCH -sDEVICE=png16m -r<N> -dFirstPage=<a> -dLastPage=<b> -sOutputFile=<prefix>-%03d.png <pdf>`。**pymupdf 专有操作**（`page.get_text('dict')` 的字体判定、`get_drawings()`/`get_image_info()` 的图形定位、`page.get_pixmap(clip=…)` 的局部裁剪）与基于 `PIL`/`numpy` 的像素测量用 conda 解释器执行；若换到未装这些包的机器，按 gs 替代并把无法执行的核对标注「未做」，不得声称已核。**ImageMagick（`magick`）可用**：`magick -density 300 x.svg -background white -flatten x.png` 可把论文 HTML 的 SVG 图资产渲染成高分辨率位图（但 MSVG 渲染器可能静默丢掉虚线/描边，部分内联 SVG 还会报 `pt` 错误；见下文「arXiv HTML 的图」，取用前必须与 PDF 渲染页对照）。
- **博客正文抓不到时先去源码仓库**：JS 构建的单页应用（Vite/Next 等）在 HTML 里只留一个 `#root` 壳与打包产物，正文是内嵌在 JS bundle 里的 markdown 字符串。到站点源码仓库取源文件（如 `site/src/data/blog/*.md`），**把 commit 与文件 sha256 记为版本锚点**；`raw.githubusercontent.com` 不可达时用 GitHub API 的 blob 接口兜底（`/repos/<owner>/<repo>/git/blobs/<sha>` 返回 base64；二进制文件可直接用 `/repos/<owner>/<repo>/contents/<path>` 加 `Accept: application/vnd.github.raw` 取原始字节）。双语站点两个语言版本都取回交叉核对——常见只更新一侧。
- **服务端渲染的博客页面（没有源码仓）**：先探测 markdown 直链（`…/article.md`、`…/raw` 等），404 就按页面本身锁版本：取正文区块（如 `<article>`），用固定口径——**标签替换为空格、解 HTML 实体、连续空白折叠为单空格**——记录**字符数与 sha256**，并写清口径与抓取日期；复核时按同一口径重算，一致才可放心回引原文片段。不要只记"抓取日期"（页面可能静默更新）。另注意页面导语（standfirst / meta description）与正文常是两套措辞、强度也可能不同（实际发生过导语 "can improve"、正文 "frequently outperformed"）：引用以正文为准。
- **微信公众号文章（`mp.weixin.qq.com`）**：正文在 `#js_content` 内，标题取 `h1.rich_media_title` / `var msg_title`，发布时间取 `var createTime`。**完整性要用浏览器渲染后的 `innerText` 复核**（标签剥离只能证明文本没丢，证明不了段落与空格）：实际发生过正文段落被写成 `<h1>/<h2>`（靠 15px 字号区分）、章节标题是 18px 加粗 `<span>`：按标签转换会把 22 个正文段落当成标题（`h1/h2` 共 45 个，其中真实标题 23 个）；另外 2 个真实标题写成加粗 `<p>`（§5 18px、§7.2 16px），只按 h1/h2 统计会漏。按字号与字重判定（正文 15px、二级标题 16px、一级标题 18px 且加粗）即可区分。图片在 `data-src` 上，`/640` 是缩放版，把路径换成 `/0` 取原图（实测 PNG 从 1080 宽变 1170 宽），下载时带上 `Referer: https://mp.weixin.qq.com/`（本次实测不带也能取到，但带上更稳）。两个渲染陷阱：① 部分 `<em>` 被内层 `font-style: normal` 抵消（实际 25 个 `<em>` 里 9 个是直立体，多为图注），按标签一律转斜体会与原文不符；② 中文标点或 `&nbsp;` 紧邻 `**` 时，CommonMark 的 flanking 规则会输出字面 `**`，需把边界标点移到加粗范围外（文字不动），并确认括注仍成对。文末常附公众号二维码、招聘海报等非正文物料，用户要求时可整段不收录，并在来源信息里写明。
- 对 arXiv 链接或编号，指定版本时使用该版本；未指定时先从官方元信息确认最新版本，再获取该版本。若只能获取较旧版本，明确说明，不称其为最新版。正文、PDF、图表和补充材料应来自同一版本，不能混用不同版本的实验数字。
- **同一 arXiv 版本可能被重新发布/重编译成不同 PDF**：记录本次抓取 PDF 的 sha256 与抓取日期（arXiv 不归档，但核对凭据要留）；再次核对时先比 sha。若同一 vN 的 hash 不同，逐页比文本与图，记录旧/新副本的差异，**不把旧副本的图缺陷写成论文或当前版的问题**（实际发生过：同一 v2 的旧副本 p4 Figure 1 不完整、当前副本完整，其余 40 页文本一致）；若正文/数字也有实质差异，按版本变化处理，先请用户确认是否重读，不静默用新副本替换旧解读。
- **慢链路上的大 PDF**（本机实测 26 MB 的 arXiv PDF 约 10–15 KB/s、需半小时以上）：先启动后台下载，有同版本 HTML 时用它读正文，最后再回 PDF 核对表格与图，不要空等。有的论文仓库或项目页会附同一稿的 PDF（可能被 iLovePDF 等工具压缩，`producer` 不同）；等待期可用它做页号与表格核对，但必须先确认**页数相同、逐页比对抽取文本**——文本一致（实测两版差异只有 p.1 的 arXiv 版本水印）时结论才对官方版成立，**文本不同就不用它下结论**。基准不换、副本不归档，来源信息里写清两者关系。
- **同一工作常有多个发布渠道**（项目页/预印本、arXiv、OpenReview、期刊）。**材料自述的状态不是核验结果**：仓库 README、项目页、CITATION 里写的发布渠道、许可、版本、star 都要独立核验并注明核验方式与日期（实际发生过：仓库 README 写 "arXiv posting 🔜 / in progress"，而 arXiv 上该文早已有 v1、其后又更新到 v2）。发现其他渠道的版本后，**用多组关键句检索**比对关键数字与关键表述，不能只看标题与摘要就断定是同一版本；各版页数也要分别记录（同一工作可能是 36 页与 43 页两个不同版本）。**比对的关键句里必须包括「发布/开源/许可声明」类句子**——这类句子是版本间最易变动、对读者又最有用的（实际发生过：站点 tech report 与 arXiv v3 全文 43 页、关键数字出现次数逐一相同，**唯一实质差异就是这一句**：站点版写「will be open-sourced in a future release」，v3 改写为项目主页链接）。**论文自己没写代码仓库时，去看正文给的项目主页**：主页常链着仓库，用 GitHub API 核对存在性、许可、创建/最后 push 时间与顶层目录结构，只核到结构层面并声明「未验证其与实验的可复现性对应」——**「论文未声明」不等于「没有公开」**，两件事要分开写。
- 记录标题、作者或机构（含作者数、共同一作 ∗ 与通讯作者 †，按贡献/脚注判定——第一作者未必是通讯作者，p.1 的联系邮箱也不一定等于通讯作者列表；实际发生过把共同一作也列为通讯作者）、来源链接、发布日期和阅读日期；arXiv 论文额外记录编号和版本，已保存的 PDF 记录本地路径。公司/团队署名的技术报告按署名团队记录，个人贡献者名单若在附录，注明所在节即可，不必强行标注共同一作/通讯。不适用的字段省略，适用但无法确认的字段注明未知，不猜测。用户提供的本地文件或正文无法确定线上身份时，以提供内容为准。
- 本地 PDF 可能是删减笔记或注释版。先判断其性质，不把仓库现有的学习笔记当成论文完整原文。允许联网且能确认来源时，可补充获取对应版本的原文，并说明两者关系，不能用最新版悄悄替换用户提供的版本。
- 论文可使用同版本 HTML 或 LaTeX 辅助理解；arXiv 论文获取全文仅用于阅读与核对，不归档 PDF；非 arXiv 来源的论文默认归档时尽力获取对应的原文 PDF。不能因 PDF 不可得而放弃对已有正文的解读。核对文本抽取容易损坏的公式、上下标和表格：表格数字与公式以 PDF 版式文本或渲染页为准（HTML 线性化表格易丢列错位），不凭文本抽取直接下结论。**跨列/跨行错配**也是常见错位：文本层按列输出或表格有 `-`/空单元格时，同一列里较靠后的数值容易被配到更早的行标签上（实际发生过：Table 9 的 66.9 属 MMLU-Redux，初稿配给 RULER@128k；回 400 dpi 渲染页才纠正）。把多列表格转写进笔记（重排、摘列或改列名）后必须回渲染页**逐格复核**，不能按位置对照——宽表转写是列错位高发点（实际发生过摘要表两列数值整体写反）；列多的表优先照抄原文列序，再另行注释。写「低于/高于某基线」时按列名确认基线，别按位置或加粗猜（实际发生过：Table 5 的 Commit 列 MLA 33.2 被当成 GDN-H 30.5）。**摘录或合并行要在表前注明**（省略了哪几行、合并了哪几行），否则读者会把节选当成全表（实际发生过：Table 1 原文 22 行、笔记压成 18 行却未声明，复核时才补上）。
- **arXiv HTML 的图通常是独立文件，需要引用时优先整图取用**：LaTeXML 版通常把每张图作为独立资产放在 HTML 的路径上，形如 `<id>vN/<name>.png`（位图，`<img src=…>`）或 `<id>vN/<name>.svg`（矢量，`<object type="image/svg+xml" data=…>`；实测某文的 Figure 7/8 曲线图就是这种，也有 `<id>vN/figures/<name>.jpg` 这类子目录，以 HTML 里的 `src`/`data` 为准），路径相对 HTML 页、完整 URL 为 `/html/<id>vN/<path>`。可直接下载，写笔记时整图复制进 `assets/`——位图不裁剪，SVG 用 `magick -density 300 … -background white -flatten` 渲染（`-density` 只是参数，报 DPI 时按输出像素与图幅换算）；矢量图的优势是可按任意 DPI 重渲染、不受裁剪窗口限制（清晰度仍取决于 DPI，PDF 里的矢量图在同 DPI 下一样清晰），也不会因裁剪窗口漏掉图内元素（但渲染器本身可能丢元素，见下）；位图则要先比分辨率。**`magick` 的 MSVG 渲染器不可全信**：实测它可能把某些 LaTeXML SVG 里的虚线/描边路径静默丢掉（同一张 Figure 7 资产渲染后只剩星形点与文字标签，拟合曲线和坐标轴线条都没了），遇到描边属性带 `pt` 单位的内联 SVG 还会直接报 `non-conforming drawing primitive`。图里有曲线/坐标轴/虚线时，渲染后必须与 PDF 渲染页对照；不确定就改用无头 Chromium。**有些图不是独立资产而是 HTML 内联 `<svg>`**（TikZ 图常见）：标签常在 `<foreignObject>` 里，抽成独立 `.svg` 后文字会丢、`magick` 也可能失败——把这段 `<svg>…</svg>` 原样嵌进一个 HTML 页面（必要时补 `xmlns`），用 Chromium `--force-device-scale-factor=3~4 --screenshot` 截取，再与 PDF 对照。**如果 HTML 给的是缩略图**（实测某 24 案例的大图只有 784 px 宽，PDF 渲染页更大），改从 PDF 渲染页裁剪或换更高分辨率来源；取用后仍要回 PDF 渲染页核对「图号—图注—内容」三者对应，并在凭据里记资产 URL（否则复核者无法复现，实际发生过审计只能标「待确认」）。**图内文字颜色也要核**：有的标签在 PDF 与 HTML 中都是白色（白底不可见），这不是抽图丢了；以 PDF 渲染页为准，并在图注里说明。HTML 抽正文时保留 `<math alttext="…">` 的 alttext（否则公式会丢失或变成乱码），并跳过 LaTeXML 的目录、页脚与 `\setCJKmainfont` 之类源码样板行。
- 图中的定量读数（曲线起止/平台值、柱高、倍数）不靠缩略图目读：先放大核对坐标轴量程与刻度标签文字本身，再读数；支撑结论的关键读数（如「从 X 升到 Y」）用像素测量复核（方法见 check-paper-note 的「读图的像素测量」），并在笔记中标注「图中读数」、**取数口径（质心/顶点/边缘）**与近似程度，与论文数字区分。**散点与拟合线要分开**：同一策略可能同时画数据点和拟合线，两者可能相差 0.3–0.7（实测）；写「X 步到 Y」前确认 Y 来自散点还是拟合线（实际发生过：Summary 散点 60.2 约在 364 步，拟合线末端约 60.9，初稿把两者混成一句）。**图的构成本身也是事实断言**：写「只有拟合曲线」前先放大看有没有数据点/误差棒（实际发生过：Figure 7 被写成「只有拟合曲线、没有数据点」，实际两条虚线旁都有星形点）。低分辨率下误认刻度是此类错误的主要来源（实际发生过把 7–14 的纵轴读成 3–15、把坐标轴下限当成曲线起点）；折线剧烈升降处（V 形回落、陡升段）取点，±窗口内的像素簇会**混入线画段**把读数拉偏——按标记自身定心（连通域质心/上下边中点）并在标注里写明口径（实际发生过：V 底右侧一点因簇心含上行线段被低估，复核时按标记质心口径修正——该轮记录为 H4「约 41」→「约 43」）。**端点处的措辞与图内读数可能不一致**：原文写「nearly 2× up to 64K」时，64K 端点读数可能只有约 1.6×；写「接近/最高 N×」时并列原文措辞与图内读数，不要替原文改口径。
- **混淆矩阵/分类热图**：先高倍渲染核对行、列标签与轴语义，再逐格读值；不按单元格位置推断（实际发生过：独立复核把 Pass/Fail 两列读反，把 41.7% 当成 58.3%）。
- **并列柱状图的数值标签按 x 坐标配对，不按文本流顺序**：多面板柱图的标签常被文本层按「面板 → 系列 → 从左到右」重排，同组两根柱的标签还会上下错行；按阅读顺序取数会把相邻格的值配到别的格上。用 `page.get_text('words')` 取标签 bbox、按 x 与柱中心配对，再用柱高在 y 轴上交叉验证（实际发生过：把 32K 的 0.48 配给了 16K 的 0.28——16K 实际是 0.40→0.28、32K 才是 0.48→0.35——算出 1.714× 并据此推出「1.71× 那格就是默认 workload」）。**折线图上的加速比/倍数标注也要按箭头的 x 坐标配对**（这类标注通常是箭头的说明，常偏在箭头右侧）：先找箭头/线段，用它的 x 与刻度对齐；没有箭头时，才用 `get_text('words')` 取标注 bbox 的最近刻度。文本流顺序与横坐标顺序不一定一致（实际发生过：Fig 7b 的 1.8× 属 512K、2.2× 属 1M，初稿按文本顺序对调，连带把 1M 的加速比写成「四个版本」（6.3× / 2.3× / >2× / 1.8×））。再按纵轴刻度读出箭头两端的值并复算倍数（线性纵轴；不要用箭头长度直接当倍数）。
- **总览图与主表交叉核对**：Figure 1 这类多面板总览图可能把不同设置（有/无上下文管理、不同 agent 框架）的数字塞进同一张图。逐面板拿 1–2 个模型对照主表：若某值在主表**该指标**的任何一档都对不上，或同一面板里各模型的设置不一致，就按「此图不能直接做跨模型比较」记录。实际发生过：某图 BrowseComp 面板把无上下文管理的 51.4 与 w/ CM 的 75.9/59.2 并列，Claude 的 67.8 在 BrowseComp 各档里都对不上（表里 w/ CM 是 57.8）；Terminal-Bench 面板把 DeepSeek 在 Claude Code 框架下的 46.4 与 Terminus-2 的其余值并列。引用时以主表为准（若两处无法判断谁对，就并列两值并注明冲突），并在笔记的图注说明与「原文自身的表述张力」里说明。**图注与正文的模型集合也可能对不上**：实际发生过图注写 DeepSeek-V3.2、正文同一段写 GLM-4.7，而图中只有前者——引用前把图注、图例、正文三处都看一遍。**同一指标的 split / 月份 / 子集也可能混用**：实际发生过 Figure 1 的 HMMT 组里 V3.2-Thinking 标 90.2（Table 2/3 的 Nov 值），其余模型是 Feb 值，而图注写统一报 February——逐柱对主表，不要只看柱高。
- 获取失败时尝试可用的官方页面或另一种原文格式；仍失败则说明缺失范围。只有摘要时只能输出标明“仅基于摘要”的有限解读；需要全文才能回答的问题暂不下结论。不能把 HTML 错误页保存为 PDF，也不能声称已归档未获取的原文。

## 阅读与分析

先梳理文章整体结构，再阅读正文及理解核心方法、训练目标或实验结论所需的附录。长文按章节或页码分段读取，检查工具输出是否截断；保留关键证据的位置，不能把一次读取成功等同于已获取全文。结合关键图表建立论证链条，不能只读摘要和结论就交付完整技术解读。实际未读到的部分要披露。

### 论文笔记

按内容组织以下信息，允许合并章节，避免没有内容的固定模板：

1. **核心结论**：文章解决什么问题、核心方法是什么、结果说明什么，以及适合什么场景。
2. **问题与动机**：已有方法的具体瓶颈，本文依赖的前提及必要背景。
3. **方法与贡献**：说明输入、输出、核心组件、数据流和训练或推理过程；将作者声称的贡献与原文实际提供的证据分开。显式覆盖两类易漏内容：① 相对前代/同类工作的**结构性变化**（架构替换、模块增删、简化——常写在引言与架构图里）；② 论文自报的**关键效率数字**（FLOPs / 每 token 字节 / token 预算 / 吞吐——常出现在引言与独立效率图）。**机制描述保留频次/作用域限定**（per layer / per step / per rank）：漏一个限定词会把开销写小近两个数量级（K3 的 93 层；实际发生过：QB 直方图是 per layer per step 一次 all-reduce，笔记写成每 step 一次）。
4. **关键公式与直觉**：解释必要的变量、维度、假设、目标函数和关键推导。**正文不写行内公式**（段落、列表、表格中不出现 `$…$`）——需要公式时**一律用 `math` 代码围栏**（三反引号 math，GitHub 原生支持，列表内也可用；新笔记不写 `$$…$$`，单行/列表内 `$$` 不可靠；全篇少量，只在公式本身是机制核心处），每块紧跟一句白话读法；变量名与符号用行内代码或文字表示。沿用原文符号，**上下标与向量/矩阵记号逐条从渲染页抄写**（文本抽取会丢失或混淆上下标，必要时裁剪放大核对），交付前对每条公式做一次「渲染页 ↔ 笔记」对照。区分原文推导与为教学补充的推导。不要为覆盖所有公式而机械转抄。**目标函数里的条件项与正则项（mask、KL、stop-gradient、序列级统计量）不要省略或只写主体**；笔记公式与被引式号必须完整对应；若省略了条件项，至少标出省略项（实际发生过：GRPO 式 (8) 的 `M_{i,t}` 初稿漏写，正文却又说它乘在式 8 上）。**不等式的方向与严格性（`>` 与 `≥`）也要照渲染页抄**（实际发生过：α 的下界是严格大于 e^−5，笔记写成「不小于」）。
5. **实验与证据**：分析关键图表、数据集、基线、指标、消融和实验条件。记录有解释价值的数值，说明比较是否控制模型规模、数据、算力或推理预算。区分相对提升、百分点变化及不同指标方向，不将特定条件下的收益泛化为普遍结论。**逐实验记录（若适用）样本量、模式（thinking / non-thinking）、scaffold、user simulator 与评测环境**；不要把一个小样本诊断实验的样本量套到另一个下游基准消融上（实际发生过：Table 5 的 50 条任务被写成 Figure 5 的样本量）。**某个基准的硬件/设置不能外推到全套评测**（实际发生过：原文只说明 PostTrainBench 与 SWE-Marathon 用 H20，笔记写成「评测在 H20 上」）。**评测清单列出的基准不一定都有结果**：报告覆盖范围要逐项回表（实际发生过：§4.1 列了 Aider-Polyglot，Table 2/3 没有它的数字）。**同一篇论文不同实验的「×」可能是几何平均、算术平均、项均值或维度均值的均值**，跨设置横比前回原文确认聚合口径（实际发生过：EAT 的 MI350X 用算术平均、B200 用 geomean，统一写成算术平均会错）。**表里的 Average/域均值也未必是表内数字的直接平均**——可能把某一列换成另一个指标再平均（实际发生过：某表 Productivity 均值用 GDPVal 的平局调整胜率，而表里只显示 Elo），复算前先读表注与附录。写下「全部/均/全面/无一例外」类全称断言前，回表格逐项找反例（实际发生过「性能全面超过前代」与表格中三处更低的值冲突）；有反例就改用具体范围表述。**原文自述与自己表格/附录对不上的地方也要记录**（摘要口径与表值不符、正文宣称的覆盖范围有反例、称某组数字「在 Table n」而该表没有这几行）——笔记正文改用可复算的表值并注明出处，把差异单列成「原文自身的表述张力」一节，别把它当成本文结论。
6. **工程视角**：解释实现步骤、关键接口或张量流、计算和存储成本、依赖条件及可能的失败模式。必要时给最小例子或伪代码；只有原文或推导支持时才量化成本，不将示意代码说成作者实现。**从仓库推断实现形态**（语言、框架、桌面/CLI）时，以 `package.json`/`pyproject.toml`/`Cargo.toml`/`go.mod` 等构建配置的依赖与 scripts 为准，不凭目录名猜（实际发生过：只看目录与 electron 配置，漏掉 `package.json` 里的 `cli` 入口，把「Electron 客户端 + CLI」写成了「不是纯 CLI」）。
7. **局限与待确认问题**：区分作者明确讨论的局限和读者根据证据提出的判断，指出哪些问题尚无实验证据。只出现在表格、正文未讨论的指标属于表格读数，不能写进「作者承认的局限」。

额外的要点：

- **基准/评测类论文**（贡献是基准本身，评测对象是系统或过程而非模型能力）：除常规项外写清四件事——① 评测协议与角色分离（谁开发、谁执行、谁判分，哪些产物被冻结、反馈如何回到开发者）；② 判分口径与可比性（指标是率/分/胜率，参照是否在同一执行器下配对、是否本地复跑）；③ 留出与防泄漏设计（反馈集/留出集怎么切、什么信号永不回传）；④ 基准本体的发布状态（代码、数据、split 是否已发布；「将随基准发布」如实写）。
- **系统 / harness 类技术报告**（贡献是运行时、平台或 agent 框架；模型与训练流程通常是现成的，实验用来验证系统）：① 逐条列出核心主张并标证据等级——哪些有基准数字、哪些只有定性案例或单一轨迹（单轨迹要标「无对照、无重复」）；② 卖点若是「长期运行 / 持续监控 / 可恢复」，专门找跨天、中断恢复、误唤醒的指标，没有就写「未测量」，不把机制描述当效果证据；③ 成本、时延、token 的报告缺位要明说（可附检索词）；④ 定性交付物比较写清谁在看、样本数、是否盲评，作者自列的边界与反例照收；⑤ 分清「谁在进化」：同一篇里 harness 固定、被改的是另一个模型（如自动后训练）时，不要把结论写成 harness 自进化。
- **与本仓库已读条目有引用/同族关系的论文**：可单列一节「与本仓库其他条目的关系」（标注为本笔记补充），写清咬合点（引用、同族、概念互证），并留意**同名不同文**（实际发生过：某文引用的 Evo-Bench 与仓库另一条目 Evo-Harness 是两篇不同工作）。**同一工作可能占两个编号**（技术报告与期刊/会议版，如 R1 的 00045 与 00095）；写清本文实际引的是哪一个，别把同族或同工作的另一版当成同一份参考文献。该节只作定位与对照，不扩展为大范围文献综述。写完笔记后，用 `grep -rn '<编号或标题>' notes/` 检查其他笔记里是否还写「未生成 / 待生成」；不改他篇，只在交付报告中列出（实际发生过：Kimi Linear 笔记生成后，K3 笔记仍写「本仓库未生成笔记」）。

默认不运行文章附带的代码、不训练模型、不开展复现。下载、文本提取、PDF 渲染和文件校验等阅读辅助操作可正常使用。用户明确要求复现时，再按其范围处理。

### 博客笔记

围绕核心观点、论证过程、技术机制、关键代码或案例、实践建议及适用边界展开。技术教程要讲清操作的前提和关键步骤；观点文章要区分经验判断、可验证事实与推测。不强行加入论文式实验、贡献或消融章节。

**导读、综述、awesome list 这类转引型材料**（自己不给数据，只转述 N 篇论文）：笔记里按条目标注每条数字的核对层级（元信息／摘要／全文／复算／未核），并单列材料自身的省略之处（未引的更强结果、被省略的限定词，如子集口径）；材料没说的内容标成「补充背景」并注明取自哪篇论文。逐篇核到什么程度以及核对的目标（转引忠实 ≠ 结论成立），见 check-paper-note 的「转引型材料的核对」。

转引同站自家材料（例如厂商的另一篇 best-practice、或本文引用的自家内部对比）时，**核对措辞强度**：同一组对比可能在不同文章里分别写成 "consistently has outperformed" 与 "frequently outperformed"（实际发生过），引用时保留各自原文并注明差异，不要替作者加强或减弱；被引文章若只给结论不给任务数、模型和成本口径，也一并写明。

**用户明确要求「原文照录 / 逐字转载」时**（此时「不归档整篇正文」的默认让位于该要求）：正文与配图按原序照录，页首只加一段明确标注「编者添加」的来源信息；**用浏览器 `innerText` 与转载页正文做含空格的逐字符比对**（只比去空白后的结果会漏掉空格错误），并记录字符数与 sha256 作为版本锚点（口径写清楚：本仓库用过「块级元素记一个空格、行内元素不记空格、解实体、空白折叠」，与「标签一律替换为空格」得到的字符数不同）。字号、颜色、居中、加粗边界、`<em>` 直立体等排版差异逐项写进「排版处理」，不静默处理。转载页与阅读笔记各占一个 README 条目（转载页同样占编号，编号列与标题列都链原文地址——站点的「原文 ↗」取自标题列），两边互相链接；用户只要求本地留档、不要进站时，说明缺 README 行会让 `site/build.py` 失败，由用户决定是否收录；决定不收录就不要把文件留在 `notes/` 下（移走或删除），否则构建仍会失败。

代码示例应解释关键行为、依赖及上下文。文章中的历史版本和当下行为需要区分；用户需要当前可用方案且允许联网时，查询对应官方文档并标注补充来源。无法核验时，只说明文章所述版本的行为，不宣称当前仍然适用。**博客若附配套仓库/工具**（文章末尾的 kit、demo 仓等），核对其存在性、许可、最后提交时间与文中声称的功能是否对得上，作为交叉证据单独注明（实际发生过：某文附 `single-agent-loop-kit`，核到 release 分支的 README 与文中描述一致）。

## 证据与表达

- 以中文解释为主，首次出现的重要术语附英文。**不写行内公式**（GitHub 对行内数学渲染不可靠）：段落、列表、表格里不出现 `$…$`；确有必要时用 `math` 代码围栏（三反引号 math；新笔记不写 `$$…$$`，单行/列表内 `$$` 不可靠；全篇少量）并紧跟白话读法，其余用文字、行内代码（如 `δ`）或围栏代码块表达。优先用具体例子解释抽象机制；流程确有帮助时可画 `mermaid` 图（三反引号 + mermaid；标签换行用 `<br/>`）。**站点阅读页为 CJK 溢出设了 `htmlLabels:false`；Mermaid 11.12 在标签较宽、需要自动换行时，对「以 `1.`/`1)` 这类有序列表标记开头 + 含 `<br>`」会抛 `splitLineToFitWidth` 错误并让整页显示「正文渲染失败」**（实际发生过；短标签可能侥幸通过）：步骤标签改用 `①②③`/`第 1 步`，或去掉 `<br>`；`doc_lint` 会对这种组合给提示（不阻断），写完仍要实际渲染验证（见交付前检查）。
- 关键结论和数据就近注明章节、公式编号、图表编号或原文小节链接。PDF 页码有歧义时注明是文件页码还是正文页码。**自己按表格复算或推算出来的数字**（百分点差、相对提升、平均值）标注为「本笔记复算」并与论文原数字区分；**复算要写明口径**——均值 / 单项原始变化 / 相对变化 / 百分点，不能混写（实际发生过把「六数据集均值改善 656 ms」与「单个数据集的原始变化 −4934 ms」并成一句）。**还要区分速率与累计量、单次规模与总量**（实际发生过：原文「秒级创建数万个沙箱、累计 5100 万」被写成「跑几十万次」）。**同一效率指标还要带 batch/设置**：6.3×（更大 batch）与 2.2×（batch=1）不是同一口径；同一设置下的 0.1× 差异（如 2.2× vs 2.3×）可能只是取整。论文自报的「平均提升约 N%」还要问清基准集合与聚合方式（哪些基准、哪一档设置、算术平均、几何平均还是中位数），按两种自然口径复算并写明；复算不出唯一值就标「口径未给」（实际发生过：GLM-5 的「约 20%」按四个均值口径算得 16.5%–26.8%；若把中位数也算入口径，范围扩到 15.1%–26.8%）。无法找到定位信息时不要编造；无法核实的实现细节（如代码仓库某个目录的作用）要么查清再写、要么略去，**不在正文留「？」式猜测**。
- 写「摘要 / §x / 图注 / 正文 说…」这类**归属句**之前，回渲染页确认该句所在的**页与小节**：跨页论文的摘要、引言与结论常用近似措辞（实际发生过把 §1 引言里的一整段逐域结果声明写成「摘要写」，而摘要全篇没有数字），凭通读印象归属会写错。断言某说法在摘要/引言/结论**重复**、或说某处「没有带限定词」时，把**每一处**都打开核对完整句子（含后半句限定）——同一概括常在多处出现，各处的措辞与限定并不相同（实际发生过把 §6 开头段写成「§6.2 结论重复」：§6.2 并无该句，§6 开头那句还自带 code/search 限定）。**表题/图注也是归属对象**（实际发生过：Table 3/4 的 caption 都写 consistently；Table 3 的 EvalPlus、Table 4 的 LiveBench/MATH500/EvalPlus 就是反例）；别只核摘要与正文。
- 一句话里并列两个产物或两个实验时，数字与素材要分别归属（实际发生过：把 teaser 视频的「56 段素材」写成了架构讲解动画的素材）。
- **篇幅类数字（「约 N 页」「pp.a–b」、附录跨度、各区块页码范围）先定位起止页再写**：按标题逐页检索定出跨度，不凭通读印象（实际发生过两处附录页数凭印象写错——把约 5 页写成 15 页、把约 10 页写成 14 页，复核时才改回；也发生过参考文献止页多算一页——笔记写「参考文献 p24–27」，实际止于 p26，p27 是贡献与致谢——**区块边界要按标题所在页定，别把紧跟其后的另一节并进去**；反过来也别漏掉**末页续文**：下一节标题上方可能仍是上一节的内容（含表格/图），记跨度前要看到最后一页的实际内容——**确认该页标题上方确有上一节的内容才把它计入上一节；没有就仍按上一节最后一页截断**（实际发生过：§6 记到 p29，但 §6.3.5 的最后一段续到 p30，§7 也在 p30 开头，故 §6 应记到 p30）。
- **复现原文的排版强调（加粗/斜体）时，「强调的是不是原文强调的那几处」也要核**：渲染页目测区分常规与粗体容易混（同一张表里数值列与差值列尤其如此），用 PDF 的字体信息判定最稳——`page.get_text('dict')` 的 span `font`（加粗体通常是 `Xxx-Bold`）可以精确列出哪些格是粗体（实际发生过：笔记 Table 4 的加粗与原文差 6 格——**2 格误加**（把 Δ 列当成原文加粗）＋**4 格漏加**（Evolved 列后四个值）；复核时才用字体判定纠正）。**若加粗其实是本笔记自己的强调，就不要写成「加粗为原文所加」**——归属句写错就是事实错误。**先确认表注规则本身成立**：表注说「两类各自最优」或 `*` 标某条件时，逐行/逐格验证。前者可能遇到原文例外（实际发生过：Table 2 的 Codeforces 开源最优 V3.2 2386、BrowseCompZh 闭源最优 GPT-5 63.0 未按类内最优加粗）；后者要核准 `*` 到底标了哪些单元格（实际发生过：BrowseComp 的 `*` 还标了 Gemini 60.2，笔记曾写成只标 V3.2 的 67.6）。
- 明确标记“作者结论”“补充背景”“解读/推断”等证据层次，尤其不要把工程建议或自拟伪代码归于作者。
- 仅在理解原文所需时补充查阅外部资料，优先论文、官方文档或作者材料，单独注明来源；不自动扩展为大范围文献综述。
- 博客以自己的表述总结，少量必要引用附来源，不默认复制或翻译归档整篇第三方文章（用户明确要求逐字转载时，按「博客笔记」一节的例外处理）。

## 保存笔记和原文

本 skill 所在目录为 `<仓库根目录>/skills/read-paper-blog/`，默认以该仓库根目录定位 `notes` 与 `papers`，不依赖调用时的工作目录；若通过符号链接加载，先解析其真实路径再定位仓库根目录。只有实际阅读时才创建产物目录。

| 来源 | 默认产物 |
| --- | --- |
| arXiv 链接或编号 | 笔记 `notes/papers/<arxiv-id>-<version>-<短标题>/note.md`（不归档 PDF，note 中记录官方 arXiv 链接） |
| 其他来源的论文 | 笔记 `notes/papers/<短标题>/note.md`，原文归档 `papers/<编号>-<短标题>.pdf` |
| 英文博客 | `notes/blogs/<站点>-<短标题>/note.md` |
| 无论文的代码仓库（GitHub 系统） | 笔记 `notes/papers/<短标题>/note.md`（站点只扫描 `notes/papers` 与 `notes/blogs`，暂借 papers 目录）；来源信息注明「代码仓库，非论文」，记 repo URL、commit、许可、最后提交日期；不归档代码 |
| 原文照录（用户明确要求） | `notes/blogs/<站点>-<短标题>-original/note.md`，配图放同目录 `assets/` |

arXiv 论文仍会获取完整原文用于阅读和核对，只是不把 PDF 归档进仓库。

归档编号为 5 位零填充，接续现有编号递增（编号数与条目数不必相等，不保证连续）。同一个条目沿用原编号，不复用、不跳号、不改号；**分配前现查**`papers/` 文件名、根 README 编号列与上游归档仓库三者的最大值，不凭记忆也不写死（只看一侧会在归档文件缺失时发出重复编号；上游不收录非论文条目，序列会与本仓库错位）。

- **论文与非论文条目共用一条编号序列**：导读、博客、系统这类条目按用户要求收录时同样占号。它们没有可归档的 PDF，该行编号单元格直接指向原文在线地址，不写 `papers/` 路径；分组按其署名方，归并规则见「回写根 README」一节（只有 1 个条目的单位不新建分组，并入「### 其他」）。
- 从上游导入论文时若编号已被本仓库的非论文条目占用，顺延取下一个空号，不覆盖已占用条目。
- 目录使用简短、稳定的英文 slug。将编号或标题中不适合路径的字符替换为连字符；例如旧式 arXiv 编号中的 `/`。版本使用 `v1`、`v2` 等，无法确认时注明 `version-unknown`，不编造版本号。
- 写入前检查现有目录和笔记中的来源信息。比较 arXiv 身份时使用编号和版本，不以 abs、pdf 或 html 链接形式判断是否同一篇。同一论文已有笔记目录时优先复用，不因来源或短标题变化而重复归档（例如清单里记的是 GitHub 版、本次给的是 arXiv 链接）；只有已有笔记记录的是另一个 arXiv 版本（已有 v1、本次读 v3）时才按版本另建。非 arXiv 来源论文若发现同时存在 arXiv 版本：仍按本次阅读来源与既有归档处理（不改目录名、不换归档策略），但在来源信息中记录 **arXiv 编号 + 核验状态（核验方式与日期；不可达就写「未核验」）+ 版本关系**——不要只写「疑似编号」。**若基准版不是最新公开版**：不换基准、不改归档，但要给出「版本关系」小节（各版页数与日期、关键数字是否一致、正文与图/表编号是否变动、新版有哪些内容本笔记未覆盖），并给笔记里对具体版本的论断（尤其「原文自身的表述张力」）标注适用版本。**表格/图号相同不等于实验数字相同**：逐页 diff 后单独检查正文里的基线数字；实际发生过 arXiv v1 删掉 p17 的 140 与 53.4，而主表与图号完全一致，笔记却写成「实验数字无差异」。
- 不同来源发生名称冲突时追加 arXiv 编号或来源 URL 的短哈希。无 URL 的本地材料使用文件内容的 SHA-256 前 12 位；提供的正文使用文本内容的同类哈希。版本未知或非 arXiv 来源论文的文件发生变化时，先比较内容，无法确认是同一版本则使用带内容哈希的新目录，不覆盖旧文件或混合解读。博客同一 URL 内容更新时复用目录，并为新解读标注阅读日期。
- `note.md` 开头列出来源信息、阅读范围和原文链接；arXiv 论文记录官方 arXiv 链接；非 arXiv 来源的论文使用 `[原文 PDF](../../../papers/<编号>-<短标题>.pdf)` 关联已归档的文件，并记录页数与 sha256（便于下次复核对齐版本）。阅读范围分两级写：「已渲染并逐项核对（含像素测量等）」与「仅按正文/图注引用」，且声明里提到的核对手段必须在笔记中有对应产出（声明了像素测量就要有图中读数）；**同时记下可复现的核对凭据**——渲染 DPI、裁剪框像素坐标、定标锚点（如「网格线 y=1072 ↔ 2.0」）、否定性断言的检索词，下次复核可直接复用，也让「声明了却没做」一眼可查；**本轮值得进 skill 的观察也一并写进凭据区**（哪类读法会出错、哪种裁剪会漏元素、工具与环境上的坑）——skill 的素材就来自这些记录。**声明只能写已经做完的事**：表格与公式的渲染页核对要在写完笔记之前完成，不能先把「已逐格核对」写进声明再去补做（实际发生过声明里列了 5 张表和 3 个公式、当时只读了 HTML 版）。获取 PDF 失败时注明未归档，不生成失效的本地链接。
- 博客没有版本号，来源信息要记**能锁住版本的东西**：标题（各语言版本的题名都记）、站点与署名方、源文件路径 + commit + sha256（页面无源码仓时改记：正文区块的规范化口径 + 字符数 + sha256）、发布日期、原文在线地址、许可状态（站点/仓库未标注时如实写「许可未标注」，不默认套用）、配图来源与许可；条目已占编号时另记仓库编号。转引型材料还要写明对被引论文核到哪一层。
- 在线 PDF 先下载到临时文件，检查文件标识并用可用的 PDF 读取工具确认可读，核对标题及可确认的版本；非 arXiv 来源的论文核对后归档为 `papers/<编号>-<短标题>.pdf`，arXiv 论文仅用于本次阅读与核对、用后清理临时文件、不保存。**Hugging Face 的 `blob/main/…` 是网页，原文文件通常用 `resolve/main/…` 取**（gated 仓库需先登录/授权，否则会拿到权限页）。下载或验证失败时清理本次临时文件，保留已有有效文件。只有文件扩展名或 HTTP 成功状态不足以证明它是正确的 PDF。多 MB 的 PDF 可能超过单次命令超时：改用后台下载或分段重试，校验必须等文件完整：**下载字节数等于响应 `Content-Length`**（若有；可用 `curl -w '%{size_download}'`）、文件尾有 `%%EOF`、页数命令能解析且页数合理（本机用 gs，见环境说明）；半截文件的 xref/trailer 报错是下载未完成的预期现象。**下载中的文件不要读元数据**：后台下载时文件大小会持续增长，用 pymupdf 打开半截副本仍可能报出页数、却给出**完整文件里没有的元数据**（实际发生过：文件只下到 6.9 MB（总 8.1 MB）时打开，读到 `creationDate 2026-09-11`，完整文件没有该字段，笔记据此写错了一条「原文张力」）；只有下载字节数与 `Content-Length` 一致、页数合理、且 sha256 与笔记记录（若有）一致之后，才记录元数据与体积。没有 sha 记录时**不必**强制第二次下载，只在怀疑副本不同或元数据异常时再下一份比对；HTTP `ETag` 不是文件 sha256，不要混用。arXiv abs 页提交记录里的 size 是提交的 **e-print 源码包**大小，与 arXiv 编译出的 PDF 未必是同一个文件（作者直接上传 PDF 时两者才会接近；实际发生过：abs 页标 6,866 KB 而 PDF 实得 8,101,889 B，也有标 199 KB 而 PDF 609,291 B 的情形）——既不能当作 PDF 完整性校验，也不要把这个差值写成「abs 页滞后」的原文张力。内置网页抓取被网络策略拦截时改用 curl 等命令行工具；域名完全不可达时如实记录「链接无法验证」，不冒充已验证。**可达性会变**：2026-10 曾实测 huggingface.co 被拦截，2026-11 曾有可达记录，2026-11-05、11-06 又连续实测不可达；不要按上一次的结论假定本次可下载。
- 非 arXiv 来源论文的本地原文原样复制为 `papers/<编号>-<短标题>.pdf`；注释版、删减版或性质无法确认的用户 PDF 原样保存为该篇笔记目录下的 `provided.pdf`，在笔记中以“用户提供的 PDF”链接，不称为原文。能获取对应原文时另外归档到 `papers/`（arXiv 论文不保存）。已有相同文件不重复保存或覆盖；同一论文版本下存在内容不同的用户 PDF 时，使用 `provided-<内容短哈希>.pdf` 分别保留。无法确认版本时如实记录。
- 明确记录本次解读实际基于哪些材料。补充归档完整 PDF 不代表已阅读它；先前仅基于摘要或删减版的笔记不能因补存原文就自动标为完整解读。
- 重复阅读时先读已有笔记，保留人工内容、批注和待办；将新解读补充到合适位置，不能区分内容归属时追加带日期的补充，不整篇覆盖。
- 需要引用本地图表图片时，按需放入该篇目录下的 `assets/`，使用相对链接，注明图号和来源；仅使用有助于解释的图表。**独立图片文件（博客/项目站的 PNG、SVG）整图复制、不裁剪**——一步规避越界、黑边与像素差三类风险；**论文的图在 PDF 里没有独立文件时，只能从渲染页裁**（arXiv HTML 带原图资产时优先取原图，见上文「arXiv HTML 的图是独立文件」）：**先用图形元素定 bbox**——`page.get_drawings()` 与 `page.get_image_info()` 的并集给出该页图形范围，再用 `page.get_text('blocks')` 找以 `Figure n`／`Table n` 开头的**题注块**定下边界（并集若把同页其他矢量元素——如别处的表格线——也圈进来，按 y 分段取与图相邻的那一段），比纯像素剖面更快也更稳；**随后仍要在整页渲染上做行/列剖面，标出该图的完整内容范围**——逐类点名：图内标题、图例、坐标轴标签（**共享轴标签常位于整图最底部、与主体隔开**）、**图内说明/注记行（位于坐标轴之下、论文题注之上的居中文字）**、Zoom-in 子框、色标（图的第一个内容行可能紧接页眉之下，与主体相隔十几个空白行）。**剖面用的 y 窗口不是内容边界**：窗口下沿要一直放到页脚/题注之后，或先定位题注首行再截断——把窗口边界当成图上边界，会把窗口外的图内元素整块漏掉（实际发生过两例：共享轴标签 "Harness version" 与图内说明行 "Downstream score as % …" 都因剖面窗口提前截断而漏裁，且两张成品边缘干净、像素差为 0）。**不要只凭视觉框选**：按「图框」裁会把图内标题整块丢掉（实际发生过首版裁掉图内顶部的 "Update Policy" 标注，而边缘干净、像素差比对也通过——缺的不是边缘而是整块元素）。边界取在内容范围之外、图注之间的空白行，别把图注切一半（下边界位置可用像素行扫描找题注首行的 y 坐标来确定），并保留图例、坐标轴与刻度完整，分辨率足够（约 ≥200 dpi）。注明来源与许可——arXiv 版默认多是 `nonexclusive-distrib` 而**不是** CC，按 abs 页「view license」指向的实际协议写（abs 页源码里 `grep -oP 'licenses/[^"]*'` 可直接看到协议路径，实测有 `by-nc-sa/4.0` 这类）；非 arXiv 来源未见许可标注时如实写「许可未标注」，不默认套用。裁剪框先校验在图像尺寸内（越界会被工具静默补黑边——实际发生过成品图约 35% 是黑边、内容截断而未发现），**每次改动裁剪框后都要重新回看成品图**，并分两步核验：① 边缘像素干净（无黑边/越界/截断/切字）；② **按元素清单逐项点名**确认都在框内——①只证明边界没切到东西，不证明没有元素整块留在框外（只做①会把「整块元素被排除在外」漏掉）。再与原文同区域重裁做像素差比对（差异应≈0）；像素差只证明「与原文同位置一致」，不证明「这块位置选得对」，两者要分别确认。若截图后裁剪/导出，凭据还要记**最终资产尺寸**（实际发生过：截图 2480×2596、裁白边后 2442×2436，笔记只记前者）。
- 在来源信息里下**整类声明**（「插图均为示意图」「未做像素测量」「未从图中读数」）之前，先把手头全部图过一遍：论文与导读里常混着带色标、内嵌柱状/折线图的定量图（实际发生过声明「均为示意图」而其中 2 张含定量元素，复核时被抓出）。声明只覆盖真看过的范围，没看的写「未逐张检查」。
- 博客默认保存笔记及原文链接，不归档整篇正文。用户提供的正文缺少网址时说明来源为用户提供，不虚构 URL；无法确认站点时，目录中的站点使用 `provided`。缺少标题时，根据内容生成简短描述性标题并注明为自拟标题。
- 不修改 `papers/` 里已有的归档文件和其他索引；`README.md` 只按「回写根 README」一节修改——默认只回写笔记地址，其余改动（追加行、新建分组、合并／改名分组、搬迁既有行）都需用户明确要求。不自动提交 Git，用户明确要求时再提交。

## 回写根 README

生成笔记后，把根 `README.md` 中对应行的「笔记地址」单元格改为笔记链接；本 skill 修改 `README.md` 仅限：回写笔记地址，以及用户明确要求时的收录与分组改动（追加行、新建分组、合并／改名分组、搬迁既有行，见本节末条）、**更换某条目编号单元格的来源指向**（如非 arXiv 来源的论文随后在 arXiv 发布、原链接失效；换链接不动其他单元格，不换编号、不删已归档的 PDF）。

- 定位唯一匹配行，按顺序尝试：先按 arXiv 编号（版本号和 `abs`、`pdf`、`html` 链接形式都视为同一篇），再按来源 URL 精确匹配，最后按与清单行完全相同的标题匹配（用于同一论文在清单中以别的来源收录，例如用 arXiv 链接读一篇清单里记成 GitHub 版的论文）。
- 同一来源存在多行（如 GitHub 版与期刊版）时，以本次实际阅读的链接那行为准；候选不唯一就按匹配不到处理，不挑一个写入。
- 单元格写成 `[笔记](./notes/<papers|blogs>/<...>/note.md)`，相对仓库根目录；该行其他单元格一律不动。
- 单元格当前是 `—（待生成笔记）` 或指向 `./notes/` 下的笔记时，写入或更新为本次的笔记链接（同一行只保留最近一次阅读的笔记）；已经指向本笔记的行不重复写入。
- 单元格里若是其他内容（用户手写的批注、外部链接等），不覆盖，保持原样并在对话中说明。
- 匹配不到、命中多行或论文不在清单中时，保持 `README.md` 原样并在对话中说明，由用户决定是否收录。**但静态站点要求每个 `note.md` 都有对应行**（`site/build.py` 会扫描 `notes/` 并双向校验，缺行直接让构建失败）：所以这一步会阻塞发布，应把「是否收录、建议编号」作为明确问题交给用户，用户同意后按上一节的编号规则取号；**用户拒绝收录时照常交付笔记**，并在交付报告中说明站点构建会因缺行失败、等待用户决定——不要让缺行造成的构建失败混进交付，也不要静默加行。
- **第一机构与团队归属冲突时先问**：典型是学生实习论文——署名首位是学校、绝大多数作者与工作地点在公司（实际发生过：某文 ¹Northwestern、其余 8 位 ²Google Cloud AI Research，页注第一作者在 Google 实习；按「第一机构」规则放进「其他」后，用户直接指出「这个论文单位不是 google 吗」）。默认仍按第一机构，但在对话里说明这一冲突并询问是否按团队归属；**得到用户明确同意后**才按团队改写 `论文单位` 并挪到该团队所在分组（这是 `CLAUDE.md`「编号」节记录的「归并分组不改写该列」的唯一例外，必须有用户确认），同时同步笔记的「机构判断」段；不要自行按团队改分组，也不要把署名顺序从笔记里删掉。
- **核对论文条目的「论文单位」与原文首页的单位行是否一致**（含顺序）：例如原文写 `Zhipu AI & Tsinghua University`、清单只写 `Tsinghua University`，按「第一机构」口径就不一致；非论文条目按署名方核对，本项不适用。读完后在对话里报告并询问是否改；**本 skill 不自行改该列**——改列与分组调整都按 CLAUDE.md 的修改边界、由用户明确决定（实际发生过：GLM-5 的清单行写 Tsinghua，而论文首页把 Zhipu AI 列在首位）。
- **用户明确要求收录并分配编号时**（导读、博客、系统这类非论文条目常这样进清单），按上一节的规则取号：能归入既有同机构分组（含其子团队／子实验室）就追加到该组末尾；单位／署名方只有 1 个条目时不新建分组，追加到「### 其他」末尾；用户明确要求新建分组时按其确认的机构／署名方命名、插在「### 其他」之前，不重排既有分组。编号单元格写原文在线地址（无 PDF 可归档），论文单元格写标题并链到同一地址，单位按条目类型写第一机构／署名方原值（归并分组不改写该列；第一机构与团队归属冲突的例外见上条），笔记地址写本次笔记链接；不改表头、不动其他行。撤并、改名分组或搬迁既有行只在用户明确要求时执行。

## 交付前检查

检查笔记中的本地链接与图片是否存在、来源和版本是否一致、核心数值是否能回溯到原文，以及阅读范围说明是否符合实际；逐条打开核对自己写的 `§x.y`、`Figure n`、`Table n` 与公式编号是否指向正确内容，未编号的公式不编造编号。**凡声称「原文加粗/斜体/标星号的那几处」的归属句，回字体信息核一遍**（`page.get_text('dict')` 的 span `font`）；凡声称「最大/最小/唯一/首个」的极值句，回表格与正文核一遍。这两类断言是实战里暴露的检查点——**别把它读成「只有这两类会出错」**：同一次复核里还抓到页码范围写错、把否定断言绝对化、数值口径混淆三类，它们已分别并入上文对应条目。回写了 `README.md` 时，一并核对这一行：编号列的链接按条目类型可达（论文指向确实存在的 PDF，非论文条目指向可达的原文在线地址）、编号未与两侧最大值撞号、笔记链接可达。另核**公式格式**：正文段落、列表、表格中没有行内 `$…$`；公式块用 `math` 围栏（三反引号 + math；不是单行或列表内的 `$$`），每块后跟白话读法。**货币符号不要写裸 `$`**：站点 MathJax 把 `$…$` 当行内公式，同一段文字里出现两个 `$` 就会被排成公式（实测：`$4,432 与 $2,377` 被吃成数学；`$` 为奇数个时，最后一个留作字面量）；`doc_lint` 也会把围栏外未放进行内代码的 `$` 报为行内公式。写成行内代码（`$4,432`）或直接改写为「4,432 美元」——不要用 `\$` 转义，marked 会先把它还原成 `$` 再交给 MathJax。若 `**…**` 的加粗内侧边界紧贴标点或 `&nbsp;`（如 `**连续：**用户`），marked 会输出字面 `**`；把这些标点移到加粗外侧（`**连续**：用户`），括注则整对移出（`**局部性**（Locality）`）。`**加粗**中文` 本身没问题。渲染后确认没有字面 `**`；`doc_lint`/`github_render_check` 不抓这个，但 `check_render.mjs` 会以 `literalStars` 报出，实载页面时看该项。**每次增删表格行/单元格后重跑 `doc_lint`**：行尾多一个 `|` 会多出空列，`site/build.py` 不报错、只有 lint 会暴露（实际发生过复核记录行尾多一个 `|`）。改了公式或 Mermaid 后跑：
- `python3 -I <仓库根>/skills/summarize-paper-methods/scripts/doc_lint.py <note.md>`
- `python3 -I <仓库根>/skills/summarize-paper-methods/scripts/github_render_check.py <note.md>`

后者调用 GitHub Markdown API，要求源公式/图块数与 `<math-renderer>`/`highlight-source-mermaid` 数一致，且没有 `language-math`/`language-mermaid` 残留；它只验证公式/图块被识别，不验证 Mermaid 图语法，图要在站点/阅读页实际渲染检查。网络不可达时如实标注「未做」。

**HTML 渲染检查（Mermaid 必做）**：`build.py` 成功、`github_render_check` 通过都不代表页面能渲染——Mermaid 语法/兼容性错误会让阅读页整页显示「正文渲染失败」。构建后先启动本地预览（`python3 -m http.server 8000 --directory _site`），再用无头 Chromium 实际加载改动页：

```bash
CHROME=$(ls -d ~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome | sort -V | tail -1)
"$CHROME" --headless=new --no-sandbox --disable-gpu --virtual-time-budget=20000 \
  --dump-dom "http://127.0.0.1:8000/notes/<papers|blogs>/<slug>/" > /tmp/dom.html
! grep -q 'class="[^"]*render-error' /tmp/dom.html   # 无匹配才算通过
```

再核对 TOC 条目数非零（含表格的笔记再核对表格数）；**图数**用 `check_render.mjs` 核对（真实时间加载、等 `__renderDone`、调 `__ensureMermaid()` 后数 `.mermaid svg`）：`node <仓库根>/skills/summarize-paper-methods/scripts/check_render.mjs --page notes/blogs/<slug>/index.html`。`--dump-dom` 对图数不够（延迟加载下首图若在 2.5 屏以外，它数到的图是 0），但仍可查 `render-error`、TOC 与表格；**延迟加载时页面可能停在 `mermaid-pending` 占位、却同样没有 `render-error`**，所以图必须按 `check_render.mjs` 的结果判，不能只看 dump 里没有报错。发布后对线上 URL 用同样方式复查一次（部署完成前 `data-source-hash` 不会变）。**页面 Mermaid 较多时先单独跑**（不要与后台下载/其他渲染并行），并给命令本身留 ≥180 秒；预算从 20000 起，`--dump-dom` 不完整或超时再上调（如 60000）。实际发生过：一边后台下 8 MB PDF 一边检查 7 张图的汇总页，35 秒预算 + 外层 120 秒仍被打断；空闲时同一页面 2–3 秒完成。本机 Playwright 缓存里已有 Chromium，`npx` 装 mermaid-cli 会超时，不要因此跳过。

**Mermaid 是延迟加载的**：首图距视口超过 2.5 屏时，`window.__renderDone` 为真但图还没渲染（占位显示「图表加载中…」），所以上面必须用 `__ensureMermaid()` 或滚动到**首图**触发后再数图（观察器只盯第一张图）。另外 `--virtual-time-budget` 可能让 `Date.now()` 不前进（连续调用取同值），而 Mermaid 用它生成图表 id——同页多图可能拿到相同 id、第 2 张起渲染成空图；这是虚拟时钟的假象，正常浏览器下通常不会出现（Mermaid 逐张渲染，真实时间精度足够）（实测同一页用 CDP 真实时间复查时两图都正常）。多图异常时改用真实时间的 CDP（`--remote-debugging-port` + `Runtime.evaluate`）复查，不要据此改图或改标题。

笔记会自动进入静态笔记库：`python3 site/build.py --out _site` 扫描 `notes/papers/*/note.md` 与 `notes/blogs/*/note.md`；每个 note.md 必须有 README 行（构建会双向校验并检查图片/链接），所以生成笔记后仍要按上文回写 README（清单里还没有这一行时，先按上一节确认收录与编号）。本地链接一律用相对 note.md 的路径，不要写 `/...` 根绝对路径（构建会拒绝）；图片放在本篇 `assets/` 下，其余仓库文件链接会转到 GitHub。构建后用 `python3 -m http.server 8000 --directory _site` 预览；构建只写本地 `_site`，**要上线必须 commit/push**——Actions 在 `notes/**`、`docs/**`、`site/**`、`README.md` 或 workflow 变化时自动构建并部署。不生成单篇 PDF（PDF 只为汇总生成，流程见 summarize-paper-methods）。旧笔记里单行/缩进 `$$` 的批量改写需用户明确要求。缺失内容如实标注，不为填满章节而推测。

**用户要求上线时**：`git add <笔记目录> README.md` + `git commit` 后 `git push origin main`。本机未安装 `gh`（2026-11 实测），用未认证 API 查最近一次 run：`curl -s "https://api.github.com/repos/<owner>/<repo>/actions/runs?per_page=1"`，等 `head_sha` 匹配且 `conclusion` 为 `success` 再做线上复查。线上用 `check_render.mjs --url <线上 URL>`，并核对线上 `note.md` 的 md5 与本地一致、`data-source-hash` 与本地 `_site` 一致（部署完成前 hash 不会变，查太早会读到旧值）。

完成后在对话中给出核心结论，并说明影响理解的材料缺失或未验证事项。生成了文件时附笔记及实际归档的 PDF 路径（arXiv 论文不归档 PDF、只附 note.md 链接）；仅对话解答时直接交付解读，不输出未创建文件的链接。
