# 笔记复核

对已生成的笔记做一次与原文的对照复核，默认**动手修复**（用户明确只要报告时除外）。复核的基准是原文——不是记忆，也不是笔记自身。每条事实性陈述都要回到原文确认。

## 第一步：确定复核基准

**本机环境（2026-10/11 实测）**：poppler 系命令行工具（`pdftotext`/`pdfinfo`/`pdftoppm`）缺失；系统 `python3`（`/usr/bin/python3`）也缺 `pymupdf`/`PIL`/`numpy` 与 `pip`。已安装 Miniconda（`~/miniconda3`，base 环境），其中 `pymupdf`/`Pillow`/`numpy` 可用。**本机 `python3` 现已解析到 `~/miniconda3/bin/python3`（2026-11 复核，`python3 -I` 同样可用）；若某次环境解析到 `/usr/bin/python3`（缺 `pymupdf`），改用 `~/miniconda3/bin/python3 -I` 显式调用。** ghostscript（本机必须用它替代 poppler）：文本抽取 `pdftotext -layout` → `gs -q -dNOPAUSE -dBATCH -sDEVICE=txtwrite -dTextFormat=3 -sOutputFile=<out.txt> <in.pdf>`（输出会折行，检索前先把换行折叠为空格）；页数 `pdfinfo` → `gs -q -dNODISPLAY -dNOSAFER -c "(<pdf>) (r) file runpdfbegin pdfpagecount = quit"`（`file` 报的页数不可靠这一点不变）；渲染 `pdftoppm -r N -png` → `gs -q -dNOPAUSE -dBATCH -sDEVICE=png16m -r<N> -dFirstPage=<a> -dLastPage=<b> -sOutputFile=<prefix>-%03d.png <pdf>`。**pymupdf 专有操作**（字体判定 `page.get_text('dict')`、矢量路径 `get_drawings()`、图块 `get_image_info()`、局部裁剪 `page.get_pixmap(clip=…)`）与基于 `PIL`/`numpy` 的像素测量用 conda 解释器执行；换到未装这些包的机器时，按 gs 替代并把无法执行的核对标注「未做」，不得声称已核。

1. 定位笔记：给路径直接读；给标题或 arXiv 编号时在 `notes/*/*/` 下按目录名与笔记标题匹配；**给清单编号时先查 README 该行的「笔记地址」单元格**，单元格未回写或指向不存在的文件时，在 `notes/` 下按标题搜索再判断。只说「最近生成的笔记」时按修改时间定位（如 `ls -t notes/*/*/note.md`）。**候选不唯一或无法判断时直接询问用户。** 本 skill 所在目录为 `<仓库根>/skills/check-paper-note/`，默认以该仓库根目录定位 `notes/` 与 `papers/`，不依赖调用时的工作目录；经符号链接加载时先解析真实路径。对应笔记不存在时说明情况并询问用户——笔记生成是 read-paper-blog 的职责。
2. 读笔记头部「来源信息」：来源类型、版本（arXiv 要具体到 vN）、原文链接、本地归档路径、阅读日期、阅读范围声明——这些决定拿什么版本核对（字段缺项按「本项不适用」处理）。没有来源信息表时，用目录名与 README 对应行推断编号与版本；仍无法确定就先询问用户，版本一律以记录为准。
3. **重新获取原文**（核对基准一律来自本次重新获取的原文，而非记忆或上次阅读的印象）：
   - arXiv：取笔记记录的**那个版本**；PDF 必取，官方 HTML **若存在**也取（便于文本与公式交叉核验，老论文可能没有）。下载到临时文件（`curl -sL -o /tmp/x.pdf https://arxiv.org/pdf/<id>v<N>`）。**下载后必须校验**：用 `file` 确认确实是 PDF（页数以环境说明里的页数命令为准——本机用 gs；`file` 报的页数不可靠）且规模合理——`curl` 对不存在的版本会返回 exit 0 并静默写入 HTML 错误页；校验失败一律按「取不到原文」处理。多 MB 文件的下载可能超过单次命令超时：转后台下载或重试，以完整文件为准（页数命令可解析）；半截文件的 xref/trailer **可能**报错，也可能正常打开并报出正确页数（DeepSeek-V4 的 arXiv v1 半截文件报出 58 页）；不要依赖报错或页数判断完整性；**判断是否卡住看文件大小是否还在增长**（`ls -l` 隔几十秒看一次），停滞就换 `export.arxiv.org` 或重新建连，别对着半截文件下结论。**完整性判据**：下载字节数等于响应 `Content-Length`（若有；`curl -w '%{size_download}'`）、文件尾有 `%%EOF`、页数合理，且 sha256 与笔记记录（若有）一致。**HTTP 200 不等于下载完整**：`curl --max-time` 超时也可能打印 HTTP 200 与部分 `size_download`；退出码必须为 0（但 0 也不代表内容正确），且字节数与 `Content-Length`（若有）一致，再看 `%%EOF`/页数。**页数不能单独作为完整性判据**；以退出码 0 + 字节数对齐 `Content-Length`（若有）+ `%%EOF` 为准。实际发生过：4.7 MB 的 v1 用 120 s 超时下到 2,040,544 B，只看了 `-w` 的 HTTP 200，把半截文件当完整版。**下载中的副本不要读元数据**：后台下载时文件仍在增长，pymupdf 打开半截文件仍可能报出页数、却给出**完整文件里没有的** `creationDate`/`producer` 等字段（实际发生过：文件只下到 6.9 MB（总 8.1 MB）时打开，读到 `creationDate 2026-09-11`，完整文件没有该字段，笔记据此写错一条「原文张力」）。没有 sha 记录时不必强制第二次下载，只在怀疑副本不同或元数据异常时再下一份比对；HTTP `ETag` 不是文件 sha256，不要混用。arXiv abs 页提交记录里的 size 是提交的 **e-print 源码包**大小，与 arXiv 编译出的 PDF 未必是同一个文件（实际发生过：标 6,866 KB 而 PDF 实得 8,101,889 B），不能当完整性依据，也不要把差值写成「abs 页滞后」。**下载后与笔记记录的 sha256 比对（若笔记有记录）**；同一 vN 的 hash 不同时，先按「同版本被重新发布/重编译」处理：逐页比文本与图，记录旧/新副本，不默认新抓取就是笔记所用副本，也不把旧副本的缺陷当成当前原文的问题；若正文/数字有实质差异，按版本问题记录并请用户确认是否重读，不静默换基准。
   - 非 arXiv：优先读仓库 `papers/<编号>-<短标题>.pdf`；必要时按笔记中的链接重新获取。`provided.pdf` 只作参考，不同于原文。
   - 博客：按笔记记录的锚点重新取（源文件路径 + commit + sha256；页面无源码仓时用规范化正文哈希，见「博客笔记的差异」）；正文在源码仓库时走 GitHub API 取源 markdown，页面可能已更新——更新过的按「文章所述版本」核对。
   - 微信公众号：正文在 `#js_content`；锚点 = 规范化正文的字符数 + sha256（口径见「博客笔记的差异」），另记该 HTML 区块的 sha256。完整性用浏览器 `innerText` 做含空格的逐字符比对（标签剥离查不出段落与空格问题），见「博客笔记的差异」。
   - 仓库型系统（无论文）：基准是 repo 默认分支的 commit（来源信息里应记录）；按该 commit 取 README、构建配置与关键文件核对，代码行为断言回文件，不要求 PDF；README 的 star/许可/发布状态属材料自述，独立核验。
4. 同时准备两种材料：文本抽取用于检索（本机用 gs txtwrite / pymupdf；`pdftotext -layout` 不可用；注意文本会折行，搜长句前先把换行替换为空格），页面渲染用于定论（本机用 gs `png16m` / pymupdf `get_pixmap`；`pdftoppm -r 220 -png` 不可用；分辨率按需调高，配合读图工具查看）。公式、上下标、表格一律以渲染页为准，文本抽取只当索引；**grep 未命中不等于原文没有**——先排查折行、连字（如 `Tflops` 常被拆成 `T f lops`）、空格差异与自己检索串的用词，必要时看渲染页，再下结论。命令不可用时改用环境已有的等价能力（本机对应关系见本节开头的环境说明），不假定专用工具存在，也不默认安装依赖。
5. 原文取不到时：先试其他官方格式（abs 页、官方 HTML、镜像）；仍失败就只在可核验范围内核对（内部一致性、可复算的换算、公开可查的事实），交付时如实声明缺失范围。

## 逐条核对

每一项都要给出结论（符合 / 有问题 / 本笔记不适用），这是复核的完成判据。

**A. 元数据**：标题、作者、机构、日期、版本号与版本历史（撤回/新旧版差异）、链接可达性；阅读范围声明与实际核对范围是否相符。**作者项要核到人**：作者数、∗ 标注的贡献者类别（共同一作/核心贡献者）与通讯作者（†）按贡献/脚注判定——只写 `Core contributors` 时写「核心贡献者/Core contributors」，不要改写成共同一作；原文明确 `contributed equally` 时才写共同一作（实际发生过：mHC 的 ∗ 是 core contributors）；第一作者未必是通讯作者，p.1 的联系邮箱也不一定等于通讯作者列表（实际发生过：笔记把共同一作也列为通讯作者，而该文的通讯作者是另外三位）。**作者数要两处交叉**：PDF metadata 的 author 字段按分隔符切分可能含团队名或占位符，不等于人数；再数附录名单里的个人姓名（实际发生过：metadata 402 项含团队名 1 项、附录 A 为 401 人，arXiv 页写「400 other authors」）。若正文数字/机制与记录的版本对不上，先取相邻版本（vN±1）确认笔记实际基于哪一版，再决定改正文还是改版本声明；相邻版本不可得时（如已撤稿不再提供）用投稿历史与元数据做旁证，并声明该步未执行。**同一 vN 的两个副本**（官方 PDF 与仓库/项目页压缩版等）文本不一致时，先打印实际 diff 行再判断差异来源，不要为差异猜原因——实际发生过：唯一差异是 p.1 的 arXiv 版本水印，笔记却写成「作者/机构排版不同」。清单编号列链接的**上游归档 PDF** 也要核验：它可能是删改/学习版，与笔记所用版本不同——确认关系（常用手段：下载后与基准版做 **sha256 字节比对**，一致即「上游 = 基准版」，写进复核记录；不一致再按页数与多组关键句比对内容），必要时在笔记的来源信息中注明。**上游 PDF 与笔记基准版本不同时，即使关键数字相同也要写明版本关系**（实际发生过：README 00083 指向 v1，笔记基于 v2，Table 3/4/6 数字一致；初稿来源信息没写这层关系）。链接用 `curl` 等复核可达性；被网络策略完全拦截的域名如实标注「本机无法验证，链接字符串与原文一致」，不判为错误。阅读范围声明里列举的核对手段必须在笔记中有对应产出（例如声明了像素测量就要有图中读数）；声明里记了核对凭据（渲染 DPI、裁剪框坐标、定标锚点、检索词）的，按凭据复跑一步确认可复现。**凭据引用仓库外的中间文件时要能复现**：arXiv HTML 的图资产、SVG 等要带 URL 与获取方式（实际发生过：笔记只写了「在 1579×1075 的原始 PNG 上读数」却没记来源，独立审计无法复核，只能标「待确认」）。**公开版本现状是本项的必查内容**：按标题查 arXiv（`export.arxiv.org/api/query?search_query=ti:"<title>"` 或直接查同名条目），再看项目页/仓库是否标注新版本——**非 arXiv 来源的笔记同样要查**（有「疑似 arXiv 编号、未核验」记录的必须核）；网络不可达则保持「未核验」并如实声明。**「minor updates」不等于只改数字**：逐页 diff 要覆盖正文句子、归因、模板/符号修正与段落位置，不能只核表格数字（实际发生过：K2 v2 在 p5 增加 WRAP 归因、p27 修正工具调用模板、p14–p15 移动段落，而 Table 3/4/6 数字未变）。**版本重排要确认方向**：同一稿可能把章节上移/下移（DeepSeek-V4 的 FP4 QAT 从 arXiv v1 §5.2.1 上移到本地 §3.4）；写「压缩/上移」前用目标版 §x 的实际内容核对，别按页码猜；章节起始页后移不等于浮动体换页。若存在比基准更新的版本，下载比对关键数字与关键表述（**多组关键句检索**，不能只看标题/摘要），把差异写进报告。**正文数字被删改也算版本差异**：表格/图号相同不等于实验数字相同（实际发生过：arXiv v1 删掉 p17 的 140/53.4，主表与图号却完全一致）。这一步不能省：实际发生过基准版（项目页 36 页）其实已有 arXiv v1/v2，其中 **v2（43 页）是实质修订版，恰好改掉了笔记列出的 5 条「原文自身的表述张力」**——不查就会把作者已修正的表述长期当成现行问题。**仓库/项目页/README 自述的状态（发布渠道、许可、star 等）属「材料声称」，不是核验结果**，要独立核验并注明核验方式与日期。**条目占了编号时另核 README 那一行**：编号单元格的链接类型要与条目类型相符（论文指向本仓库或上游的 PDF；上游尚未归档的 arXiv 论文可暂指 arXiv 官方页；非论文条目指向原文在线地址）、链接可达、笔记链接可达、编号未与 `papers/` 文件名或上游归档撞号。**同时核对论文条目的「论文单位」列与原文首页的单位行是否一致**（含顺序；例如原文写 `Zhipu AI & Tsinghua University`、清单只写 `Tsinghua University`，按第一机构口径不一致；非论文条目按署名方核对，本项不适用）——**不一致只报告，不改列**：该列不在本 skill 的改动范围，是否改、以及分组是否同步，交由用户按 CLAUDE.md 的修改边界决定（实际发生过：GLM-5 的清单写 Tsinghua、论文首页把 Zhipu AI 列在首位，复核时提出、待用户确认）。

**B. 数字**：逐一回原文——内存、性能、规模、百分比、倍数。表格类数字（实验配置表、内存表）**必须在渲染页上核对**，文本抽取经常错位丢列。**跨列/跨行错配**也是常见错位：文本层按列输出或表格有 `-`/空单元格时，同一列里较靠后的数值容易被配到更早的行标签上（实际发生过：Table 9 的 66.9 属 MMLU-Redux，初稿配给 RULER@128k；回 400 dpi 渲染页才纠正）。**合并单元格的空白列不要按相邻列填充**：先看表头/表注，空白可能表示「0/不适用/未给」（实际发生过：mHC Table 5 的 `Leading Dense Layers` 在 3B（非 3B 1T）列留空，27B 也留空；只有 9B 与 3B 1T 为 1，不能按这两列回填；该表无表注，空白是 0 还是未给不能由表推断）。笔记若把原文表格重排、摘列或改列名，按**列语义映射**逐格核对，不能按位置对照（先建立映射再核对）；除渲染页逐格外，可再用文本层做一次「**按序子序列**」机器比对（笔记该行的每个数值须按原文列序出现在对应页文本里）作为补充——两种手段互补，不能只靠文本层。**反例/最优的基线列要按列名确认**：宽表同一行有多个模型列时，「低于某基线」必须指明是哪一列（实际发生过：Table 5 的 Commit 列 MLA 33.2 被当成 GDN-H 30.5，反例基线写错）。**原文表格自带的 Δ/百分比列也要复算**：与表内数字不一致时写成原文取整/口径，不要静默抄录（实际发生过：Table 2 总参数 1.04T/671B ≈ +55%、激活 (37−32.6)/37 ≈ −12%，原文写 +54%/−13%）。**表格分列「active experts」与「shared experts」时，是否相加是惯例推断**：原文没明说就标注推断（实际发生过：K2 的 8 个激活专家 + 1 共享 = 9 只是按 DeepSeek-V3 表格惯例，原文只写 8 和 1（中文「路由」是推断））。**原文只写 `Experts Active per Token` 时不要改写成 `routed`**；active/routed/shared 的术语按原文，推断要标注。**反例判定要按表注的 same-level 阈值**：表注说 gap ≤0.3 属同一水平时，0.1 的差距不能列为「更低」的反例；只有超出阈值的才写成反例（实际发生过：DeepSeek-V4 的 Table 1 里 Pro 87.5 vs V3.2 87.6 被列为反例，按 0.3 规则属同档）。**累积消融与分别禁用要分清**：表中按 `H_res` → `+H_pre` → `+H_post` 累积启用时，行间差值是按顺序加入时的增量贡献（不是各自独立消融）；写「X 占 81%」要标「按表值算术分解」（实际发生过：mHC Table 1）。**同一张表的两组指标可能各有自己的样本量**：DeepSeek-V4 的 Table 13 指令遵循 total 2,837、写作质量 total 2,198；引用「N 次」前先看该组自己的 Total，不要把一组基数套到另一组；若子类 `#` 相加与 Total 不一致，不要静默用子类相加替代 Total；先按 Total 行与正文/其他表交叉，无法判断时并列两值并注明表内不一致。**写「完整表」前先看笔记是否把原文表格里的参数/架构/元数据行并到了别的表**；否则改称「N 个 benchmark 行」并说明省略。**胜率表的「最高」要注明样本量门槛**：小样本子类（如 n=1、n=7）可能占最高，不能与「n≥100 的最高」混用（实际发生过：DeepSeek-V4 的 Table 12 全表最高 100.00%（n=1，仅 1 次比较），n≥100 的最高才是邮件书信 73.29%）。**micro-average 不一定等于各 domain 分数的平均**：论文写 micro 时，直接用 domain 分数平均会得到另一个数（实际发生过：K2 Tau2 的 70.6/56.5/65.8 简单平均 64.3，论文 66.1 是 micro；可用基线模型的 domain 均值同样低于其 micro 值交叉验证）。**由显存/总量反推参数只能声明「相容」**，不能唯一归因（实际发生过：6 TB 与 1.04T 相容，但 1T×6B 也约 6 TB）。**篇幅类数字**（「约 N 页」「pp.a–b」、附录跨度）同样要核：逐页检索标题定位起止页（实际发生过两处附录页数写错——约 5 页写成 15 页、约 10 页写成 14 页）。**注意末页续文**：下一节标题上方可能仍是上一节的内容（含表格/图），跨度要看到最后一页的实际内容——**标题上方确有上一节内容才把该页计入上一节，没有就仍按上一节最后一页截断**（实际发生过：§6 记到 p29，但 §6.3.5 末段续到 p30，§6 应记到 p30）。**论文自报的「平均提升约 N%」要问清基准集合与聚合方式**（哪些基准、哪一档设置、算术平均、几何平均还是中位数）——用两种自然口径复算并写清，复算不出唯一值就标「口径未给」，不要把某一种算法当成作者的（实际发生过：「约 20%」按四个均值口径算得 16.5%–26.8%，若把中位数也算入口径则扩到 15.1%–26.8%，原文未给平均方式）。声称的换算自己复算（例：卡数 × 每卡 TFlops ≈ 总 PFlops），推算要写出算式与实测偏差，不用「约 1% 以内」这类模糊措辞。**用已被四舍五入的中间值反推**（如由整数 Elo 反推胜率、由百分比反推计数）只能声明「在 0.01 量级内与表值一致」；表值若由精确计数算出，要写明「无法精确复现」，不要写「完全吻合」（实际发生过：反推的四家胜率代入后，与表值最多差 0.01）。**排版强调的归属也要核**：笔记写「加粗／斜体为原文所加」或复现了原文的强调范围时，用 `page.get_text('dict')` 的 span 字体列出粗体格逐一比对，不靠渲染页目测（实际发生过：笔记把 Table 4 的 Δ 列当成原文加粗——2 格误加——又漏了 Evolved 列 4 格，与原文共差 6 格；原文的粗体恰好只有 5 格、全在 Evolved 列）。**先确认表注规则本身成立**：表注说「两类各自最优」时逐行验证；发现例外先判断是漏标还是有意为之，无法解释时写成原文自身不一致（实际发生过：Table 2 的 Codeforces 开源最优 V3.2 2386、BrowseCompZh 闭源最优 GPT-5 63.0 未按类内最优加粗）。**同一数值可能有两种口径**：若某数字在原文出现两次而含义不同（如「省 25%」既可能是演化开销、也可能是部署后每任务成本），笔记引用时必须指明属哪一种——数值巧合相同不等于同一口径（实际发生过笔记把 §7.5 的每任务推理成本当成 §6.3 的演化开销）。**跨设置的聚合口径也要分开核**：「×」可能是几何平均、算术平均、项均值或维度均值的均值，不能把一个设置的口径套到另一个设置（实际发生过：EAT 的 MI350X 是算术平均、B200 是 geomean，独立审计统一说成算术平均）。**表内的 Average 行也未必是表内数字的平均**：它可能把某一列换成另一个指标再平均（实际发生过：Productivity 均值用 GDPVal 的平局调整胜率，而表里只显示 Elo，直接按表值平均对不上）；复算前先读表注与附录，确认每个基准进入均值的是哪一列。**机制描述里的频次与作用域**（per layer / per step / per rank / per micro-batch）也是数字口径：漏一个限定词会把开销写小近两个数量级（K3 的 93 层；实际发生过：QB 直方图是每层每 step 一次 all-reduce，笔记写成每 step 一次）。

**C. 公式**：变量、系数、上下标、单位逐项核对，看渲染页而非文本抽取；公式编号与正文引用对得上。**官方 HTML 的 `<math alttext="…">` 可交叉核公式**（LaTeXML 通常保留 TeX 源，最终仍以 PDF 渲染页为准；实际发生过：mHC 的 Eq 6–9/20 用 alttext 复核）。**目标函数里的 mask/条件项/正则项/stop-gradient 要逐项核**；不要只核主体（实际发生过：GRPO 式 (8) 的 `M_{i,t}` 初稿漏写）。**优化器的动量/状态递推行也不要省略**（实际发生过：Muon 的 `M_t = μM_{t-1}+G_t` 初稿漏写，读者无法实现）。**散文里的运算顺序也要按公式核**：先乘门控还是先加 bias、先归一化还是先投影（实际发生过：DeepSeek-V4 的 mHC `α·(X̂W)+S` 被写成 `α·(X̂W+S)`）。**论文先给通用公式、再给架构特例时，要标明适用对象**：不要把通用版的系数套到特例上（实际发生过：QK-Clip 的 `γ^α/γ^{1−α}` 是 MHA 写法，MLA 实际按 `q_C/k_C/q_R/k_R` 三分量缩放，初稿公式块没有区分）。**不等式的方向与严格性（`>` 与 `≥`）也要核**（实际发生过：α 的下界是严格大于 e^−5，笔记写成「不小于」）。**格式**：正文段落、列表、表格中不应出现行内 `$…$`（GitHub 对行内公式渲染不可靠）——公式应放在 `math` 代码围栏里（三反引号 + math，GitHub 原生支持，列表内也可用；新笔记不写 `$$…$$`，单行/列表内 `$$` 不可靠）并紧跟白话读法；发现行内公式按**格式问题**报告，若本次复核包含格式修复或该段正在修改，则改写为文字/行内代码/独立块并**保持符号与数值不变**；未要求格式修复时，不因格式原因整篇重写旧笔记。**货币符号**：裸 `$` 会被 `doc_lint.py` 当行内公式报错，站点 MathJax 也会把同一段文字里的两个 `$` 排成公式（实测 `$4,432 与 $2,377` 被吃成数学）；改为行内代码（`$4,432`）或「4,432 美元」，数值不变。不要用 `\$`——marked 会先还原成 `$` 再交给 MathJax，lint 也照样报（本轮实践最后统一改写成「美元」）。

**D. 引用定位**：每个 `§x.y`、`Figure n`、`Table n`、脚注 n 都打开原位置确认**内容与归属**。**笔记自身节号与论文节号重名时**，引用论文写「原文 §x.y」，避免与笔记的 §x.y 混淆（实际发生过：mHC 笔记的 §3.1 是 Kernel 融合，论文 §3.1 是 Numerical Instability）。不仅要问「该处有没有这个内容」，还要问「笔记说它出自这里，对不对」（摘要 / 引言 / 结论 / 图注的措辞常近似；实例：笔记把 §1 引言里的一整段逐域结果声明写成「摘要写」，而摘要全篇没有数字）。**同一节里 search/code/general 多段并列时，引用句的主语要核**（实际发生过：把 Search Agent 段的 “based on DeepSeek-V3.2” 写成 general 合成流水线的描述）；**一句话里并列两个产物/两个实验时，素材与数字要分别归属**（实际发生过：56 段素材属于 teaser 视频，笔记写成了架构讲解动画的素材）。注意原文自身可能有错标（例：附录表格图号与内容错位；正文称某组超参「reported in Table n」而该表并无这几行）——发现时把它标注为原文自身的问题（不是笔记的错误），并以「另注（复核时发现）」等形式写进笔记、在对话说明，方便下次复核查证。**多面板图是这类错标的高发区**：同一张图的各面板「图内标题」与「图注」可能指向不同的模型／条件（实际发生过：某图 9 个面板里有 3 个如此），核这种图要**逐面板成对读「图内标题 + 图注」**，不一致时按面板内容判谁对（内容与该论文正文一致的那个为准），并把三处一并列进笔记，别只改你恰好引到的那一个；**图注与正文对整张图的模型集合也可能不一致**（实际发生过：图注写 DeepSeek-V3.2、正文同段写 GLM-4.7，而图中只有前者）。HTML（LaTeXML）与 PDF 的参考文献编号可能不一致，引用编号以 PDF 渲染页为准。**小节标题与引用句可能不在同一页**：页码要定位到该句自己所在的页，不能按小节起始页推断（实际发生过：A.2 的标题与引用句都在 p.27，初稿按「A.2 从 p.26 开始」写成 p.26）。断言某说法在摘要/引言/结论**重复**、或说某处「未带限定词」时，把**每一处**（含 §6 开头与 §6.2 这类相邻位置）都打开核对完整句子与后半句限定——各处的措辞与限定并不相同（实际发生过：把 §6 开头段误写成「§6.2 结论重复」，而 §6.2 并无该句、§6 开头那句还自带 code/search 限定）。**「与本仓库其他条目的关系」一节里的指向也要核**：笔记若声称某篇就是仓库另一条目引的那篇、或据此关闭对方登记的字悬置，必须取**对方那篇**的原文核对（参考文献条目的作者串 + 标题 + arXiv 编号逐字比对），读了本方不足以宣称确认（实际发生过：笔记写「本次读原文确认」，而当时只读了本方；复核时另取对方论文，在其参考文献中找到 `T. Chen, … arXiv:2606.14249` 才真正坐实）。同节还要留意**同名不同文**：若怀疑与另一条目撞名，先按编号确认，别按名字对号。**被指向的笔记本身也要回查**：若对方仍写「本仓库未生成笔记 / 待生成」，在报告中列出，不自行改他篇（实际发生过：Kimi Linear 笔记生成后，K3 笔记仍写「本仓库未生成笔记」）。**同一数字同时出现在正文与图时，优先引正文页码**；若引图，阅读范围必须包含该图（实际发生过：K2 Figure 11 的胜率在 p29 正文也有，初稿引 Figure 11 但阅读范围写「未单独查看」）。**脚注/表注的符号范围也要核**：`*`、`†`、加粗、下划线究竟标了哪些单元格（实际发生过：BrowseComp 表注的 `*` 还标了 Gemini 60.2，笔记写成只标 V3.2 的 67.6）。

**E. 声称 vs 证据**：搜出所有「论文称 / 原文 / §x」样式的句子逐字对照；超出原文的概括要么改回原文说法，要么标注「解读/推断」。区分作者明说的局限与读者视角的判断——**「作者明确承认的局限」清单要逐条回原文找对应句**：读者自己检索不到的东西（如「不是盲评」「未做用户研究」——检索 `blind`/`user study` 零命中只说明作者没写，不等于作者承认）属于读者判断，不能写进作者承认（实际发生过）。**「只写在图注 / 附录 / 摘要」这类范围断言同样要全文检索**：先搜该事实的其他出现位置（含正文分析段），再下结论（实际发生过：笔记说「R1 从 base 重训只写在图注与附录」，而 §4.3.4 正文也写了）。**同一局限可能在两处措辞不同**：引用哪一处就标哪一处，不要合并（实际发生过：DeepSeek-V4 的 §4.2.3 `a comprehensive theoretical understanding of their underlying mechanisms` 与 §6 `underlying principles remain insufficiently understood`）。**没有方差/误差棒不等于单次报告**：若原文也没有说明重复次数，写「原文未说明是否多次运行取平均」；若原文说明了重复协议但没有方差，写「按 N 次…平均，未给方差/置信区间」；不要断言「都是单次报告」。原文自身前后有张力时（例：§1 的通信量声明与 §5.1 的机制描述不完全自洽），如实记录张力与两种读法，并标明这是原文自身的表述张力。对「论文未给出/未说明」类否定性断言，须用全文（HTML 与 PDF）多组关键词检索确认；**HTML 全文检索会命中页面模板**（如 `github` 出现在 Report GitHub Issue 模态框与 LaTeXML 页脚反馈链接；mHC 的 7 次命中均在模板，正文 `<article>` 无命中），否定性断言要限定为 PDF 正文/HTML 内容区并说明命中来源，报告中说明检索的用词；不能凭印象下结论。**情态词要核**：usually/often/can/may 是风险描述，不能写成实际发生（实际发生过：K2 原文「usually result in instability」被写成该次运行「随后出现 loss spike 甚至发散」）。**同一句并列两个 benchmark 时逐个找反例**，不要抓到一个就结束（实际发生过：p17 同句称 Tau2 与 ACEBench「outperforming all baselines」，只核了 ACEBench 的 GPT-4.1 80.1，漏了 Tau2 micro 上 Opus 67.6 > 66.1）。**数据消融的 token 预算/epoch 口径未说明时，不要断言等算力或不等算力**，写「原文未说明」。**「零/从未/全程」类断言要核图/表的覆盖范围**：图注可能省略开头/尾部（实际发生过：K2 Figure 3 图注说省略训练最开始一小段，「全程零尖峰」的完整证据不在图里）。把所有「全部/均/全面/无一例外」类全称断言单独列出、逐项回表格与正文找反例——实战中该类断言是审计与自查的主要漏网点。**「最大/最小/唯一/首个/从未」类极值断言同样单列**，逐条问「原文是否真的支持这个极值」：原文只给了某一次的具体数值，不代表它是极值（实际发生过：笔记写「最大单轮回退 −14.0%」，而同一图另有 −21 的落差、只是标注为跨两轮——「最大」二字无依据，须改为「原文点名的那次」并说明另一处口径）。对**材料自身**的否定性断言（笔记写「导读未引」「材料未注明」「§x 没有给代表工作」）同样要检索确认：搜材料的完整正文，并覆盖它的全部语言版本（双语站点常只更新一侧）；报告里写明检索用的词。笔记若对**代码仓库的实现形态**（桌面/CLI/框架/语言）下断言，回 `package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod` 等构建配置核对依赖与 scripts，不凭目录名判断。**只出现在表格、正文未讨论的指标属于表格读数，不能写进「作者明确承认的局限」**（实际发生过：BabyVision 被放进作者承认清单，正文并未讨论它）。**表题/图注的全称断言也要查**（实际发生过：Table 3/4 的 caption 都写 consistently；Table 3 的 EvalPlus、Table 4 的 LiveBench/MATH500/EvalPlus 就是反例）；检查不能停在摘要与正文。**厂商博客的「所有评测都是内部的」要逐项分类**：基准/评分器是否公开、运行配置是否公开、数据集是否私有；不要用一句「内部评测」抹平（实测 Harvey LAB 是公开基准、repo 为 MIT；作者没有说明的是自己的运行配置与所用任务子集，并购文档多为公开文件）。

**F. 读图**：图注里的每个数值、曲线关系、图例归属都要实测（目测只用于定位，不用于定论）。双轴图最容易把系列画错轴；把「图中读数」写成论文数字也是常见错误。**先读完整轴标题与图内脚注**：`progress toward` / `distance to` 方向相反，刻度是路线位置时不要按数值距离理解；`Log scale`、`Budget ... not measured spend`、`31 of the 57` 这类脚注常是读数口径。**高亮子集不等于全表**：图例把红线标为「需判断或算术」、橙线标为「跨多文档」时，正文的 87% vs 73% 只覆盖该子集，不能写成全题平均。**横轴定标**：用刻度标签中心/网格线，不要用绘图区宽度等分或最后一个刻度当右边界；曲线可能延伸到最后一个刻度之外（实际发生过：在本仓库 K2 笔记的 300 dpi 裁剪资产上，Figure 2 右图 50k 刻度实际 1287 px，初稿按 1317 px 定标，70k 从约 88 被读成约 40；曲线到约 237k，而最后刻度只到 200k）。至少取两个横轴刻度；若正文/表格给出某个点的值，用它在图上反查，否则用刻度间距与 PDF 矢量/刻度标签 bbox 自查。像素定标再用 PDF 矢量/刻度标签 bbox 交叉一次。**图内标签作用范围**：一个标注可能只覆盖相邻元素（实际发生过：Figure 4 的 4096 tokens 只标 full input，输出端未单独标）。**图例颜色/线型逐个对**，不要按记忆（实际发生过：某图的绿=SFT、灰=Exp 被对调）。**散点与拟合线分开**：同一图可能同时有数据点和拟合线，可能相差 0.3–0.7（实际发生过：Summary 散点 60.2 约在 364 步，拟合线末端约 60.9）。**折线图的数据点与图内文字标签要分开**：读数用 marker 的连通域质心或 PDF 矢量 marker 坐标，不要拿 `None`/`High`/`Max` 等文字标签的 bbox 当数据点位置；标签常偏在点的一侧（上/下/左/右），不要假设标签中心就是点（实际发生过：DeepSeek-V4 的 Figure 10 把 Pro None 的 x 从约 0.6k 读成约 6k（标签 bbox 中心约 8k）、V3.2 Think 的 y 从 25.1 读成 28）；刻度标签 bbox 只用于轴定标，不用于数据点定位。**趋势描述（linear/exponential）要按读数验算**：边际收益递减不能写线性增长（实际发生过：DeepSeek-V4 的 HLE 后段 +3 分花约 18k 1.6×）；引用时并列两者并标「图内读数」，不替原文改口径。**总览图还要与主表交叉核对**：多面板图可能混用设置（有/无上下文管理、不同 agent 框架、不同 split/月份/子集），逐面板拿 1–2 **G. 遗漏**：影响理解的实验条件与口径（硬件、并行布置、baseline 设置、比较口径、附录里的补充声明）、作者明说的局限、论证链上的关键中间结论。不求全求细，但影响解读的必须在。**逐实验记录（若适用）样本量、模式（thinking / non-thinking）、scaffold、user simulator 与评测环境**；不要把一个小样本诊断实验的 n 套到另一个下游基准消融上。**评测清单列出的基准不一定都有结果**（实际发生过：§4.1 列了 Aider-Polyglot，Table 2/3 没有它的数字）。**某个基准的硬件/设置不能外推到全套评测**（实际发生过：原文只说明 PostTrainBench 与 SWE-Marathon 用 H20，笔记写成「评测在 H20 上」）。**节选表的省略清单要逐项列全并给总行数/省略数**，不要用「等行」带过（实际发生过：Table 3 共 44 个数据行只摘 16 行，初稿用「等行」，复核时才补全 28 行）。**表注的粗体/下划线/SOTA 标记要读并解释**；节选表无法复现格式时注明（实际发生过：Table 3 图注粗体=全场 SOTA、粗体加下划线=开源最优，初稿只解释了 `*`）。**SWE 等需要多次尝试或存在缺测的评测要写清尝试次数与缺测原因**（实际发生过：SWE-bench Multilingual 只测 single-attempt，Opus 缺测因成本过高；笔记初稿只写了 SWE-bench Verified 的三种口径）。**scaling 曲线要写清每个点是否 compute-optimal**：数据量随参数同比例增长时，不能写成固定数据量下的纯模型规模扫描（原文称 proportional；Table 5 的 token/param 比并不严格恒定，不能反推严格常数；实际发生过：mHC 的 3B/9B/27B 三点）。**多面板图各面板的运行次数要分开记**（实测左图 16/3/3、右图 3/3/1），不要压成一个 `16/3/3/1` 序列；同一模型在不同面板的次数也可能不同。

## 读图的像素测量

关键图表读数（双轴、多系列、对数轴）用像素测量定论：

1. 高分辨率渲染页面（本机用 `gs -q -dNOPAUSE -dBATCH -sDEVICE=png16m -r<N> -sOutputFile=<prefix>-%03d.png <pdf>` 整页渲染，`pdftoppm` 不可用；按标记裁剪用 pymupdf 的 `page.get_pixmap(clip=Rect(…))`，已随 Miniconda 安装；像素测量读数建议 ≥300 dpi），先看图确认图例、轴与系列的大致归属。**同一批测量固定 DPI**：像素坐标只在同一渲染文件内有效，换 DPI 必须重新定标（实例：先在 220 dpi 图上套用 300 dpi 的坐标，白跑一轮）。
2. 用脚本按颜色提取数据点/柱/线（如 Python + PIL 读像素），按 x 位置求每列的 y 中心。注意：柱体填充色与网格线颜色可能不同，阈值要分别取、取准；两者区分不开时，柱顶改用**形状法**定位（自下而上的连续填充段），不用「最上方的命中像素」，否则网格线会被当成柱顶。图例（色块、样线）与**陡峭的线段**都会形成伪点——按数据点的预期 x 位置（类别中心）与形状筛选，先排除图例区，再定数据点。另两类同样常见的伪数据源：**坐标轴箭头/轴端装饰**常与数据曲线同色，会被掩码命中（实例：横轴箭头被当成数据点，把固定策略的曲线末端从 ≈998 代误读成 ≈1033 代）→ 测量前按面板/绘图区边界截断，或排除轴所在的行列；**与系列同色的文字标注**（轮次编号、数据标签、数值文字）也会进掩码（实例：红色曲线旁的轮次数字把某点读数拉高 ≈70 ms／1.3%）→ 定值用标记形状，并先排除文字所在的行。散点/圆点等标记用**连通域质心**定值，不要用最上/最下的边缘像素——标记半径会使读数系统性偏大或偏小（实例：平台值用边缘像素读出 78.8，质心为 78.4，后者与表格一致）。
3. 用刻度标签或网格线定标：找标签文字的 x/y 中心或网格线（行/列），建立「像素 ↔ 数值」映射，先确认轴是线性还是对数、左右轴是否不同量纲；刻度密集、文字行检测有噪声时，改用网格线（行/列）定标或放大目读刻度。定标前先放大**核对刻度标签文字本身**再建立映射——错认刻度（实例：把 7–14 的纵轴读成 3–15；把坐标轴下限当成曲线起点）会造成整体性偏差，是本类错误的头号来源。**至少取两个刻度**（或两条网格线）求出「像素/单位」并写进凭据；只认一个刻度时，错认的刻度没有第二个点来暴露（实际发生过：0.0 刻度记成 634 px、实为 677 px，该轮结论 0.96 恰好没变）。横轴同样至少两个刻度；不要用绘图区宽度等分或最后一个刻度当右边界，曲线可能延伸到刻度之外（实际发生过：K2 Figure 2 的 50k 刻度 1287 px 被当成 1317 px，70k 读数从约 88 偏成约 40）。
4. **交叉验证**：同一数据的不同呈现应互相吻合（例如总量曲线 ÷ 卡数 == 每卡柱；同一实验在另一张图里的点应一致）；不吻合就继续查，查清再下结论。
5. 写进笔记时标注「图中读数」并给不确定度（写明**取数口径**：质心/顶点/边缘），与论文数字区分。折线剧烈升降（V 形回落、陡升段）处取点，窗口内的像素簇会混入线画段——用标记形状定心（连通域质心），复核时先对齐口径再比数（实际发生过：V 底右侧一点因簇心含上行线画段被低估，改用标记质心后修正——该轮复核记录为 H4「约 41」→「约 43」）。

## 独立复核

默认执行：另派一个子 agent 做独立审计（它没有你的上下文包袱，容易发现你忽略的问题；历史上它抓到过自查漏掉的问题）。只有复核范围很小（只查单点疑问、不查全篇）时才跳过。给它的材料：原文获取方式（具体命令）、笔记路径、上面的核对清单、以及「只报告、不改文件」的要求，让它按位置给出「笔记原文 / 原文依据 / 判定」清单。**对它报告的问题逐条自己验证**（尤其数字和图），确认后再改——子 agent 也会读错图、算错数；尤其混淆矩阵/分类图的列序读反是高发误报，回高倍渲染页确认后再改；它引用的**聚合口径**（算术/几何平均、单次 vs 均值）与参照系（best-of-k、总预算）也要回原文核（实际发生过：子 agent 把 B200 的 geomean 说成算术平均，据此提出的修正不成立）。**还要检查它比较的对象对不对**：子 agent 可能拿错参照系（实际发生过：用 best-of-4 的 77.0 去否定原文「k=2 已超过所有 **k=5** 基线」那句，而 k=5 的对照是 74.9），采纳前先确认它引用的数字与原文那句话的主语/预算一致。与子 agent 的读数出现小数级差异时，自己复测定夺，并说明保留哪个值及依据。派发前**固化笔记快照**（记录 md5 或 mtime 并写进提示）。**审计期间自己不要在同一个文件上落笔**——把自查发现的修改先记成待改清单，等审计报告回来一次性改；否则行号与磁盘状态错位，审计报告里的每条都要额外标注版本（实际发生过：审计期间笔记被改两次，报告需逐条标「已修正／仍存在」）。确需中途修改时，在报告中按新快照对齐行号，避免行号漂移。要求它在报告末尾给出**覆盖度小结**（A–H 哪些项逐项查过、哪些未查），便于判断盲区。子 agent 可能分批送达并**自我修正**（实际发生过先报「全部图为示意图」、补充时才更正为「其中 2 张含定量元素」，也有审计期间它自己的下载还在跑的情况）——以它最后一份报告为准，把两版差异并入你的复验，并在最终报告里说明取了哪一版。**提示里把「渠道核验项」（项目页/GitHub/star/许可等要联网的）明确划出来，要求它标注「未复核」**——这些本就不该占它的核对时间，你另行复跑；不划出来它会去访问，既慢又可能与你的核验时点不一致。同理，要求它**自报方法**（它若用了另一套读数口径，正好当作交叉验证——实际发生过：独立审计用矢量路径提取、自查用像素连通域，两法读数差 ≤0.07pp，多方法互证比单一方法可信）。

## 修复规则

- 先改「确凿错误」，再处理「易误读」的表述；不确定的宁可不改，或在笔记中标注不确定性。
- **同一篇笔记被反复要求复核时，轮次可换取证重点**（第一轮数字/机制/图表；第二轮措辞与口径；第三轮跨工件一致性），但**报告仍要逐项声明 A–H 本轮是重查还是沿用上轮结论，并对上轮结论做抽查**——「换重点」不等于不用声明覆盖度。后几轮的典型产出是**口径精化**：修正与原文不符的表述（把推断写成原文、把两个消融混称、把推导的成本式写成原文给的），它属于修复；**纯润色仍不属于复核范围**。口径精化要写进复核记录；若同一错误也出现在引用该笔记的汇总里，在报告中注明并交由 summarize-paper-methods 同步（本 skill 不直接改 `docs/`；实际发生过：某文 Figure 7 左的 "Direct Editing w/o Execution" 被笔记简写成「不进库」，与 Table 3 的 "w/o library" 混为一谈）。
- 修完必须回原文验证新文字本身，避免补丁引入新错误。**补丁自己会出错，也要按原样回查**（实际发生过：为修正作者分工标注而重写的那句，把 Core Contributors 写成 5 人、实为 6 人——回原文逐字数一遍才发现，交付前已改正）。**修补时不得扩大限定词**：把「某两个基准用 H20」写成「评测都在 H20」也是新错误（实际发生过），改完按原句的主语/范围再读一遍。
- 自己的推断被证伪时直接删改；修复的是事实，加限定词不算修复。
- 以最小改动修复，保留笔记中的人工内容、批注与待办；无法区分归属时追加带日期的补充。
- 格式修复（把行内公式改为独立块/文字，或把单行/缩进 `$$` 改为 `math` 围栏）只在用户要求或该段本就要改时做；批量改写旧笔记的公式格式属于用户明确要求的事项，不默认执行。改写后保持符号与数值不变，并跑渲染检查。
- 改动限定在该笔记目录内（`note.md` 与 `assets/`）。`papers/`、其他笔记、README 默认不动；仅当发现清单里该论文的笔记链接失效，或单元格仍未回写（`—（待生成笔记）`）而笔记已存在时，按 read-paper-blog 的「回写根 README」规则修正那一格——匹配不到、命中多行或单元格是手写内容则只报告。
- 修复后重跑笔记的结构自检：本地链接与图片存在、表格列数一致、代码块与公式块闭合；改过 `assets/` 时重新与原文比对（像素差≈0）。**表格行尾不要多出 `|`**——会多出一个空列，`site/build.py` 不报错而 `doc_lint.py` 能抓（实际发生过「复核记录」行尾多一个 `|`，构建通过、lint 才暴露）；每次增删表格文字后重跑 lint。
- 临时文件（下载的 PDF/HTML、渲染图、脚本输出）用后清理；arXiv 论文只记官方链接，不归档 PDF。
- 若发现阅读范围声明与实际不符（如声称读了全文但内容只覆盖摘要；声称某些表格/公式「已渲染页逐格核对」而实际只读过 HTML 版），**先补做缺失的核对**——把声明里列到、实际没在渲染页看过的表格、公式、图逐项补验；确认结论无误后再把声明改到实际做过的范围，而不是一删了事。反向不一致（声明**少列**了正文实际引用过的材料）同样要修：把引用到的部分补进声明，避免「引用了却没写进声明范围」（实际发生过：声明只列某附录的前 3 步与另两步，而正文引用了该附录的 06/07 步与另一附录的第 03 步）。
- 发现比基准更新的公开版本时：① 默认**不改笔记基准**（换基准＝重读，属 read-paper-blog 的职责，需用户明确要求）；② 在笔记中新增/更新「版本关系」小节（各版页数与日期、关键数字是否一致、表述与图/表编号差异、新版有哪些内容未覆盖）；③ 给「原文自身的表述张力」逐条标注适用版本与是否已在更新版修正；④ 在对话报告中说明新版有哪些内容未覆盖、哪些张力已失效。若该论文同时是**仓库归档版**，一并核对清单那一行的编号单元格指向是否需要按用户要求调整（只报告，不自行改）。
- 复核完成后在笔记的「来源信息」中追加或更新一条「复核记录」（首轮写在来源信息表里；日期、基准版本、核对方式、修正摘要；修正摘要里一并写**未修项与理由**，如「原文未给口径、无法复算」），便于追溯与下次复核；记录里带上本次用到的**可复现凭据**（渲染 DPI、裁剪框坐标、定标锚点、否定性断言的检索词），下次复核可直接复用。**多轮复核时记录会迅速变长**：超过两轮就在来源信息表之后的正文里单列「复核记录」小节（若笔记有「阅读范围与核对凭据」段则紧随其后；没有就放在来源信息之后、正文第一章之前；单轮记录也可以直接用独立小节）、按轮分条（日期 + 基准 sha + 改了什么 + 未修项），表格里只留一句「见下」——单格塞进上千字会让来源信息表被一条巨长的记录压住、很难读（实际发生过：三轮记录挤在一个单元格里，占掉整屏）。**处置过程中值得进 skill 的观察也一并记进来**——读数被哪类伪数据源拉偏、配图裁剪漏掉了哪类元素、检索词怎么选才命中、工具与环境上的坑：skill 的素材就是这些记录，只写「改了什么」不写「怎么发现的」，下次要往 skill 里补实例时就得回头重做一遍取证（实际发生过：skill 里引用的实例在对应笔记的复核记录里查不到，只能重新下载原文测量核对）。

## 交付

对话中报告：

1. 核对范围与方式（原文版本、用过的核对手段、全查还是抽查；若改了公式/Mermaid，写明 `doc_lint.py`/`github_render_check.py` 的结果）；
2. 确认无误的部分，写明对应「逐条核对」A–H 中的哪些项；
3. 问题清单：位置（行号 + 原文片段）、原文依据（页码/节/图表号）、判定（事实错误 / 未标注推断 / 遗漏 / 易误读）、修法；
4. 已修复内容（只报告未修改时写明）；仍未核实或无法核实的事项。

报告只声明实际核对过的范围。生成的文件有变化时附路径；仅对话解答时不输出文件链接。一次复核多篇时，逐篇独立执行本流程、各自使用独立的临时文件，逐篇给出上述四项报告。

## 博客笔记的差异

博客没有版本号，版本锚点是笔记记录的**源文件路径、commit 与 sha256**：重取后先比对这些锚点——一致即基准未变，可放心引用行号与原文片段；不一致再查明改动，按「文章所述版本」核对。笔记没记锚点时，退而比对笔记里的原文引用。

**页面是服务端渲染、没有源码仓时**（`…/article.md`、`/raw` 等直链 404）：版本锚点 = **规范化正文的字符数 + sha256**。规范化口径必须与笔记一致（本仓库实际用过：取 `<article>` 区块、标签替换为空格、解 HTML 实体、连续空白折叠为单空格）；按同一口径重算，一致即页面未变。不一致时先比对笔记引用的原句定位改动，报告「页面已更新」，不要直接拿新版页面改写旧结论。同时注意导语（standfirst / meta description）与正文是两套措辞，引用正文；厂商文章可能转引自家另一篇，**措辞强度可能被下调或上调**（实际发生过 "consistently has outperformed" 被后一篇写成 "frequently outperformed"），核 D 项时把两篇都取回比对。**整页 HTML 哈希不是版本锚点**：SSR 框架常把构建 ID/内联数据写进 HTML，重抓后哈希可能变（实测规范化 `<article>` 文本 24,423 字符与 sha256 完全一致，整页 HTML 从 242,373 B 变为 242,416 B）；只比 `<article>` 规范化哈希，整页哈希只作当次快照。**`alt` 是独立文本层**：图内数值可能在 `alt` 里有文本版，而正文/图注没有。措辞可能与图注/正文冲突（实测图注/正文 24 questions、`alt` 24 criteria）。引用时标明来源，冲突并列。

**微信公众号（`mp.weixin.qq.com`）**：锚点用 `#js_content` 的规范化文本 + 字符数 + sha256，另记该 HTML 区块的 sha256；口径须与笔记一致（本仓库实际用过：**块级元素记一个空格、行内元素不记空格**、解实体、连续空白折叠——与「标签一律替换为空格」的结果不同，按错口径会得出不同字符数）。**完整性用浏览器 `innerText` 与笔记/转载页做含空格的逐字符比对**：这篇的正文段落被写成 `<h1>/<h2>`（靠 15px 字号区分），按标签转会把 22 个段落当成标题（`h1/h2` 共 45 个，其中真实标题 23 个），另有 2 个真实标题写成加粗 `<p>`（§5、§7.2）——按字号与字重判定（正文 15px、二级标题 16px、一级标题 18px 且加粗）即可避开；另有 9 个 `<em>`（8 条图注 + 1 条表注）被内层 `font-style: normal` 抵消，按标签一律转斜体时确实做错过、后续修正。标签剥离能证明文本没丢，但证明不了段落结构、空格与强调的视觉样式。转载页的图片应与图床原图逐字节相同（`sha256` 比对）；文末的二维码/招聘海报若用户要求不收录，核对时按「已声明排除」处理，不判为缺失。

站点是 JS 单页应用时**不能只抓 HTML 壳**（那只是一个 `#root` 空容器，核不到任何正文）：到源码仓库取源 markdown（如 `site/src/data/blog/*.md`）再核；双语站点两个语言版本都取回，数字与机制以两版一致为准。`raw.githubusercontent.com` 不可达时用 GitHub API 的 blob 接口（`/repos/<owner>/<repo>/git/blobs/<sha>` 返回 base64）。

用户需要当前行为时查官方文档并标注来源。代码示例连同依赖与上下文一起核对。

## 转引型材料的核对

笔记的「原文」若本身是转引（导读、综述、awesome list），要核两层：**①笔记 ↔ 这份材料**（转写是否忠实）与 **②材料 ↔ 被引论文**（转引是否忠实）。第二层的核对目标只是「转引是否忠实」，不是「结论是否成立」——报告里要写清这一区分。

1. 被引论文的元信息（编号、标题、第一作者、日期）批量核：arXiv 一次可查多篇（`export.arxiv.org/api/query?id_list=a,b,c`），与材料的参考列表逐条比对；材料标的日期常是 v1 提交日期，核数字时以各自最新版为准并注明。
2. 数字逐条回摘要；只有承载结论的数字才取全文或复算表格（表格仍在渲染页核对）。**范围型数字**（如「提高 3.7–6.2 个百分点」）先判它是不是原文原话——全书检索该范围的两端；不是原话时按材料的表格复算，并在笔记里注明这是复算值及其基线选择。
3. 材料转引时的取舍也要记录：省略了哪些更强的结果、哪些限定词（子集口径、backbone、评测预算）被丢掉、哪条数字其实来自论文而非材料。
4. 笔记要标明每条数字的核对层级（元信息／摘要／全文／复算／未核），未取到全文的如实保留「未核」。

## 边界

- 复核只做静态核对（阅读、取原文、渲染、比对）；运行文章代码、训练模型、复现实验超出范围（用户明确要求时另说）。
- 离线时只做可离线核验的部分，并声明这一点。
- 复核只解决两类问题：「与原文不符」与「影响理解的遗漏」；润色、扩写、换结构不属于复核范围。
- 若笔记缺 README 行导致 `site/build.py` 构建失败：这是预期现象——按 read-paper-blog 的「回写根 README」规则**只报告、不自行加行**；在交付报告中说明需要用户决定是否收录。
