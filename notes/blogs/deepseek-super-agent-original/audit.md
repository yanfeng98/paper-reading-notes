## 初步实验（原第 7 节）

### 7.1 消融：双层架构 vs 单 Session + Subagent

- **负载**：用群聊和 GitHub CI 消息流同时驱动；单次实验约 **300 条消息**，其中约 **20 条**是工作请求，其余是闲聊、跟进、叫停和 CI 消息。编码工作用一个**只消耗时间的工具**代替，因此实验衡量的是系统的调度与协作能力，而不是单个任务的执行能力。每种方案重复运行 **5 次**；消息间隔与工作时长按 1/4 缩放，模型调用耗时为真实值。
- **四种方案**：① Super-agent；② 去掉直通的 Super-agent；③ 单 Session + Subagent 工具，中性提示；④ 单 Session + Subagent 工具，提示优先委派。
- **两段提示词原文**：
  - 中性提示：`Use a subagent for a piece of work when appropriate...`
  - 提示优先委派：`Every message of the chat reaches you, so work you run yourself keeps stopping for new messages. Prefer handing each piece of work to a subagent of its own, and do only small things yourself...`
- **结果（正文明确写出的部分）**：
  - Super-agent 的任务完成时间 p50 为 **12.4 分钟**、p95 为 **15.7 分钟**，显著优于带 Subagent 工具的单 Session。
  - 中性提示下，模型在 5 次运行中**一次都没有调用 Subagent**，所有工作都在主 Session 中进行并不断被新消息打断，p95 达到 **29.5 分钟**。
  - 改为提示优先委派后，5 次中有 **4 次**进行了委派，完成时间有所缩短但整体仍慢于 Super-agent；剩下 1 次模型判断工作「很小」而选择自己执行，形成图中的紫色长尾。
  - 作者归因：带 Subagent 的单 Session 在实验场景下受提示词影响较大，主 Session 常常决定自己直接执行任务，导致总完成时间长、性能不稳定；双层架构让 Router 不直接执行具体工作、Worker 仅接收所订阅 Thread 的消息，在系统层面缓解了这个问题。
- **系统开销**：由于维护了多个独立会话，Super-agent 单次实验的读缓存 token 高于单 Session。去掉直通机制后，任务完成时间与完整版基本一致，但单次实验中 Router 需要做出的决定增加了约 **30%**，总读缓存 token 从 **2323 万**增加到 **3177 万**，增幅约 **37%**。作者结论：直通在实验负载下不提高任务完成质量与速度，但为 Router Session 节省了可观的 token 与推理开销。
- **未转录**：完整四方案表（`fig-13`）中的其余 p50 / p95 与 token 数值未在正文逐项写出，本档案不据图补录。

### 7.2 Router 层的批处理

- **设置**：让 Router 调用真实模型、Worker 使用 Mock 模型；将需要决定的 Trigger 到达速率从每分钟约 **1 条**逐步提升至约 **40 条**，观察平均 batch 大小、单次请求耗时与单个决定分摊的推理时间。
- **结果**：到达速率从约 1 条/分钟升至约 40 条/分钟时，平均 batch 大小从 **1.0** 升至 **2.8**，单次请求耗时仅从 **2.5 秒**增至 **3.9 秒**，增长慢于 batch 大小，从而使单个决定分摊的推理时间从 **6.4 秒**降至 **1.6 秒**。
- **作者结论**：外部事件突发拥堵时，Router 层能通过自动合并积压事件提高有效吞吐。这解释了为什么 §7.1 中即使去掉直通使 Router 峰值负载增加，仍未触及单 Router 的吞吐瓶颈；因此在其团队规模下无需过早对 Router 层做水平切分而牺牲全局上下文的连续性。
- **口径提醒**：见上「复核记录」最后一条；分摊时间与「单次请求耗时 ÷ batch」不完全对应，原文未说明分母口径。

## 开放问题（原第 8 节）

作者先交代前提：这套系统能以较低复杂度运作，很大程度是因为当前阶段做了一系列工程和场景简化；超出这些简化后，以下四类问题仍待解决。

### 8.1 如何扩展双层架构

- 当前组合是「单常驻 Router Session + 订阅直通 + Worker 间不直接通信」，以较小工程代价覆盖了大多数日常任务。
- 任务规模扩大、耦合度提高后，层内结构没有定论：Router 层何时需要水平切分、粒度如何划分；同层 Worker 之间何时需要引入直接通信、采用何种协作拓扑。
- 系统与模型的协同设计（Co-design）值得探索：针对 Router 层的事件判别、批量分派与上下文召回做专项训练，可能提升吞吐与决策性能。
- 长程记忆是更大的瓶颈：常驻 Router + 基于引用图的链式召回主要解决近期任务与会话历史的按需检索；运行周期拉长到跨月甚至更长时，长程记忆成为制约可扩展性的主要瓶颈。

### 8.2 脱离 Session 之后如何与 Agent 协作

- 双层架构把底层多会话管理隐藏后，Session 不再是产品设计的首要问题；但执行会话不再直接对应用户界面上的会话后，如何呈现任务、提供自然的交互与项目管理形式，成为新问题。
- 作者认为以聊天窗口为中心的交互在一定程度上是路径依赖的结果；交互可以更多发生在领域特化的界面里（例如让 Super-agent 直接在 GitHub 的 Issue 和 PR 中工作）。Session 可以因使用习惯在界面上保留，但用户看到的一个会话在底层未必只对应一个 Session。
- 文章主要讨论任务发起与结果验收阶段的交互；模型能力演进的过渡期内，许多任务仍需要人中途参与，如何兼顾逐步干预与后台自主推进（随时介入、接管、实时协同）仍待探索。
- 总的判断：用户所需的项目管理与交互形式与工作领域、个人风格密切相关，最终形态可能高度定制化；DeepSeek Harness 的开放架构更容易支持这种定制。

### 8.3 如何划分上下文边界并进行 A2A 协作

- 前文默认单个 Super-agent 实例服务范围内的信息都汇总在同一个全局上下文中。
- 使用范围从个人/小团队扩展到更大组织时，配备 Super-agent 实际上是在划分上下文共享与隔离的边界：需要共享的范围共用一个实例，需要隔离的范围各自独立配备。
- 一旦组织内或组织间存在多个彼此隔离的实例（例如每个成员的个人助手与团队共用的 Super-agent），跨边界协同就是 Agent 间通信（A2A，不特指某个协议）；在互不共享底层上下文、各自代表不同权限边界的前提下，如何实现安全、可靠的 A2A 通信与协作仍需探索。

### 8.4 如何保障安全与隐私

- 事件驱动让 Agent 能被更广泛的环境驱动，也增加了接触不可信输入的风险；安全与隐私不解决，Super-agent 只能在很小且可信的范围内工作。
- §5 的云端 Loop + 端侧 daemon 默认云端与端侧彼此受信任；但云端持续接入外部事件、端侧又有私有代码、敏感数据与本地凭据时，跨设备连接引入显著隐患。一旦云端 Agent Loop 遭遇服务端入侵或提示词注入而被攻破，其连接的全部端侧设备都面临被控制的潜在风险。
- 即使云端未被攻破，只要端侧环境中的凭据能进入模型上下文，正常执行过程中同样存在凭据泄露风险；需要设计机制让 Agent 在完全不接触凭据本身的情况下使用凭据。
- 作者结论：架构要走向更广泛应用，必须在能从多样环境召回上下文的同时解决上述安全与隐私问题。

## 结语（原第 9 节）

- 文章自评没有提出全新理论，而是把计算机系统中经典的工程思想应用到 Agent 系统构建上；具体实现会随技术发展演进，但背后的系统设计思路有更长期的参考价值。
- 目前基于这套思路和 DeepSeek Harness 构建的内部 Super-agent 实例已在持续运行，日常参与问题复现与修复、代码审查响应，以及 DeepSeek Harness 自身的迭代。
- 文章回到开篇判断：随着大模型执行单个任务越来越少需要人工干预，限制生产力进一步提升的瓶颈正在转向人的注意力。双层架构、事件驱动、异步多信道交互、存算分离与外部 Watchdog 在底层接管了繁琐的会话管理与上下文同步，使人类得以从执行细节上移到更高层的决策与验收。
- 在这种形态下，Agent 不再只是被动等待指令的对话窗口，而是数字环境中持续在线的自主协作者：面向个人是跨设备处理日常事务的个人助手，面向团队则融入研发工作流、承接并推进具体任务。
- **文末声明**：部分设计已在 `dsh-superagent-prototype` 中实现；该插件只是为了验证技术路线而提供的原型，并非 DeepSeek 的正式产品。

## 机制细节完整版

### 四个基础特征

- **连续**：用户可以直接在 IM 聊天、GitHub 评论等熟悉的工作界面与它交互，感觉始终只存在一个 Agent，不需要去想「Session X 的上下文中是否有 Y 信息」。例如先在 IM 上提出采用方案 A、随后在 GitHub PR 评论里改为方案 B，它能理解并调整执行方向。
- **高效**：交互响应迅速，同时能并行、高质量地完成多个复杂任务；无需等上一个命令或任务完成，就能接受下一条指令。
- **主动**：无需等待用户逐条下达指令，能持续观察环境事件并主动推进值得处理的事项，不需要介入时保持安静。
- **持久**：始终在线、直接接入用户真实的工作环境，并在长期运行中遇到异常时自动恢复。

文章的总述：通过双层架构兼顾连续交互与高效并发，通过事件驱动实现主动响应，通过面向人的交互在交互过程中同时做到连续与高效，并通过计算/状态/环境的分离及 Watchdog 实现跨设备的持久在线与异常自愈。原文配图 `fig-03` 的标号 [2]–[6] 对应第 2–6 节。

### 双层架构（§2）

- **权衡**：每条事件交给同一个 Session，上下文最连续，但受单个 ReAct Loop 串行速度上限约束，任务完成耗时长、吞吐低，多任务中间细节混杂也影响完成效果；每条事件都新开独立 Session，并发吞吐最高，但任务不独立时缺少全局上下文会让结果割裂，多个 Session 各自向用户响应也会造成交互混乱。
- **Router 层**：常驻的全局路由层，承接所有入口的人类交互；所有跨任务的信息与决策在此汇总，充当全局的序点（Sequence Point）、协调点和记忆。为避免成为性能瓶颈，不直接执行具体任务，只负责人类交互与任务分派，甚至可以不配备 Bash 工具。
- **Router 与 Agent Team 的区别**：常见 Agent Team 用于单个复杂任务内部的步骤拆解与角色协作，子步骤耦合紧，Team Lead 往往要深入理解任务细节、规划子任务并高频协调，推理负载重；Super-agent 的 Router 只处理任务之间的高层关联与分派，不介入单任务内部拆解。反过来说，如果用提示词约束一个 Agent Team 的主会话不亲自执行、只对外交互并分派任务，它也可以视为这种双层架构。
- **Router 的实现自由度**：不必局限于单个 Session，部分逻辑甚至未必需要调用 LLM。文章选择最直接的单个常驻 LLM Session 作为核心实现。
- **批处理**：上一轮推理期间到达的 Trigger 会积压，在下一轮一并处理。事件流平稳时 Trigger 逐条进入，单次响应延迟低；事件密集、出现排队拥堵时，积压的多条 Trigger 自动合并进下一次 LLM 调用。Router 每步通常是长输入、短输出，多条 Trigger 合并后在 Prefill 阶段并行计算，单次请求耗时的增长远慢于批处理大小；因此在一定范围内，积压越多，单个决定分摊的推理时间越低。上限取决于上下文长度，以及模型一轮能准确处理多少条 Trigger。
- **扩展**：规模进一步扩大、单个会话不足以承载时，Router 层内部可设计为多层过滤结构，或水平切分（Sharding）为多个会话；切分粒度越细吞吐越高，但分片之间的记忆与上下文连续性越低。「在全局记忆问题被解决之前，这一权衡始终存在。」
- **Worker 层**：负责具体执行的会话，彼此上下文隔离，挂载完整执行工具，在独立上下文中专注完成单一任务；直接决定任务结果与代码质量，通常配置能力最强的模型。Worker 不直接与人类交互，推理过程和工具调用不输出到外部信道，而是向 Router 汇报状态、由 Router 统一回复。
- **Worker 内部可嵌套**：执行复杂单任务时可以再创建 Subagent，也可以本身就是一个 Agent Team，这些对 Router 保持透明。
- **Worker 间协作**：同层 Worker 通常不需要直接通信；冲突多出现在同一个 PR 等共享工作环境，只要都订阅了对应 Thread，就会收到相同事件通知，有机会自行发现和解决冲突，少数跨任务协同由 Router 中转。
- **适用场景**：代码协作（同时推进多个独立的问题复现、PR 评审与特性开发而互不阻塞）；个人助手（前端单一聊天页维持交互连续性，底层为每个话题分派 Worker 并行推进、起草回复）。

### 事件驱动（§3）

- **Trigger**：群聊消息、邮件与日程提醒、代码审查评论、CI 运行结果等半结构化环境事件。驱动 Agent 的主要输入不再是人类逐条键入的提示词。
- **两级过滤（§3.1）**：借鉴 Fast Path / Slow Path。程序层策略作为 Fast Path，针对事件来源、群组范围、用户或机器人白名单等确定性条件做快速准入，例如对不同来源分别设置「仅响应明确请求」「作为候选事件」「直接忽略」，在调用模型前滤除大部分无关消息；语义层策略作为 Slow Path，把通过准入的候选事件交给 LLM，按提示词编写的策略与上下文判断是否需要行动。语义层同时是面向人类的自然语言扩展点，可随时通过提示词开关或新增策略。
- **Thread 与订阅（§3.2）**：同一个 GitHub PR、同一个 IM 话题或同一封往来邮件串下的连续事件构成一条 Thread。Router 根据 Thread 的初始事件创建 Worker 后，Worker 直接订阅该 Thread，路由分为两条路径：
  - **已订阅（Fast Path）**：同一 Thread 下的后续事件由程序直通已订阅的 Worker，无需 Router 再次调用工具转发；若新事件超出当前任务范围，Worker 可取消订阅或交回 Router 重新分派。
  - **未订阅（Slow Path）**：Router 仍可观测所有事件以掌握全局状态，但仅负责判断和分派尚未被订阅的新事件。
  - **多对多**：一个 Worker 可同时订阅多个相关 Thread，一个 Thread 也可被多个 Worker 订阅；多个 Worker 在同一工作环境或讨论中发生交集时，新事件会同时直通给所有订阅者，使它们无需点对点通信也有机会获知彼此操作并自行解决冲突。输出侧，Worker 仍将关键结论汇报给 Router，由 Router 统一回复并同步全局记忆。
- **上下文组织（§3.3）**：把有限的上下文窗口当作 Cache 管理。**Inline** 将近期很可能用到的信息直接内联进当前窗口，省去额外工具调用往返；**Spill** 将超出窗口预算或低频使用的完整信息留在窗口外，仅在窗口内保留引用或摘要。结合局部性（Locality）的优化步骤：
  1. 从最少信息开始：最初只提供当前对象的 ID 和内容摘要。
  2. 利用局部性逐步 Inline 关联信息：先附紧密关联对象的 ID，再附时空相邻的内容，例如内容前 50 字、IM 消息的前后相邻消息与所回复的消息，或代码评论所在评审讨论中的相邻评论。
  3. 超出上限则 Spill：对无法全部 Inline 的长内容设定较小的长度上限，截断超出部分并保留续读入口，模型需要完整内容时再调用工具读取。
- **链式召回（Chain of Recall）**：系统为 Trigger、Thread 和 Worker Session 等对象赋予唯一 ID，注入时内联紧密关联对象的 ID，使这些对象在底层构成一张引用图。每次调用工具召回的对象同样遵循 Inline & Spill，返回结果中又会内联下一跳关联对象的摘要与 ID，模型便可以从当前事件出发，沿引用关系逐跳按需召回上下文。例子：从一条当前消息读取所在 Thread，再从 Thread 内联的 ID 追踪到相关 Worker Session，进而找到该 Worker 关联的另一个代码评审 Thread。它缓解的是 Router 在长程运行中丢失先前信息的问题。
- **投机执行（§3.4）**：借鉴 Speculative Execution，在还不确定结果是否会被采用时，根据环境信号在后台提前尝试，用额外后台算力减少人类的等待与介入成本；结果有价值就交付，没有价值就丢弃。个人助手例子：收到会议邀约邮件或待办消息时，先核对日程冲突、搜集背景资料、备好回复草稿，待用户过目后确认发出。研发例子：在内部 Harness 用户群配置「静默复现并修复」策略，有人反馈问题或讨论改动方案时，Agent 先在后台尝试复现并寻找修复方案，只有确认问题并找到简单修复方案后才交付，否则全程保持安静。

### 面向人的交互（§4）

- **异步 ReAct Loop（§4.1）**：经典 ReAct Loop 中，模型发起一次同步的 `run()` 工具调用后循环阻塞，直到工具执行完毕并返回结果，期间会话无法响应新输入。改为异步的 `start()` 和 `stop()`：模型调用 `start()` 后立即收到「已启动（Started）」返回，循环不再等待；后台工具执行完成后，系统将最终结果作为一条新事件消息投递进会话；模型也可以根据上下文调用 `stop()` 主动终止执行时间过长的后台命令。由此前台对话响应与后台任务执行解耦，新输入在当前推理步结束后即被处理，不必等待后台工具完成。
- **产品状态**：这套异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。
- **多信道（§4.2）**：不同工作信道信息密度与交互习惯不同。双层架构已把冗长的推理过程与密集的工具调用隔离在 Worker 内，不直接输出到外部信道；在此基础上接入用户日常使用的各类工作环境，并通过提示词针对不同信道定制交互规范：
  - **IM 等即时通讯信道**：低打扰的轻量沟通，像人类同事一样只在需要决策或验收时发送通知，只问直接问题、给简短结论；验证过的一条硬性规定是单次回复不超过 100 词。
  - **GitHub、邮件与文档等异步信道**：结构化、高信息密度的异步交付，例如创建或更新 PR 时按项目规范撰写完整的问题背景、改动说明与验证结果，或个人助手场景下直接起草结构化的邮件与文档摘要。

### 计算、状态与环境的分离（§5）

- **问题**：现有本地 Agent 默认把推进 Agent Loop 的计算、需要持久保存的会话状态、代码仓库与本地工具链等执行环境绑定在同一台设备上；设备休眠或离线，Agent 停止运行，且无法访问其他设备上的环境。
- **第一步，计算与状态分离（§5.1）**：推进 Agent Loop 的计算做成无状态，放入云端无状态弹性计算容器；Session 等持久化状态存入数据库。容器可水平扩展、重启或替换，会话与任务连续性由持久化存储保障，使 Agent 摆脱单台本地设备的生命周期限制。
- **第二步，计算与执行环境分离（§5.2）**：模型工作所需上下文很大一部分要通过工具调用从代码仓库、本地文件、依赖服务等执行环境获取，广义上下文也包含执行环境本身。两种常见思路都不可行：在云端启动沙箱、拉取代码并重建同步环境，成本高且容易遗漏（真实环境有未提交的本地修改、私有凭据、内网服务依赖、特定硬件或工具链）；要求用户放弃本地环境迁往云端，迁移成本过高。
- **做法**：Agent Loop 在云端，重状态的执行环境留在原地；端侧只部署一个不保存会话状态的轻量 daemon，只负责执行命令与返回结果，相当于把执行环境留在云端之外，由 Agent 按需读取其中的上下文。
- **与 Anthropic「脑手分离」的关系**：一致之处是让 harness 保持无状态、把会话日志存放在 harness 之外、通过统一接口按需接入执行环境。区别在场景：那篇文章描述托管服务，主要讨论按需创建的沙箱和客户 VPC 内的资源；这里首先要接入用户日常使用、可能间歇在线的个人机器，上面有未提交的修改和本地凭据。因此设计既支持 **BYOM（Bring Your Own Machine）**，也支持接入云端托管机器或按需创建的计算环境。
- **效果**：一个 Agent 不再受限于单台机器，可以在不同执行设备之间切换，按任务需要选择环境执行命令并获取上下文；甚至支持间歇在线的设备——某台个人设备重新上线后，由云端 Agent 自动触发并完成需要在该设备上执行的任务。

### Watchdog（§6）

- **动机**：持久在线的分布式系统很难仅靠主系统内部逻辑保证长期可靠，需要在主系统之外引入独立的外部控制回路（Control Loop）。Agent 系统还多一层：许多异常不是进程崩溃，而是模型在执行中陷入无效循环或偏离目标；只靠传统进程存活探测或监控脚本不够，还要监控任务本身的进展。
- **实现**：在主系统外部配置一个独立的 **Watchdog Session**，用定时消息驱动，构成外部 Control Loop。它处理接口报错、状态恢复失败等基础设施故障，也由模型判断各个 Worker 是否有实质进展、方向是否偏离整体目标；发现异常及时介入修复，遇到外部偶发故障则持续复查直至恢复正常。
- **可运维性**：Watchdog 本身也是具备完整工具能力的 Agent Session，维护者可以用自然语言向它询问故障原因，也可以让它在线修正主系统行为，例如增删提示词、调整触发规则。
