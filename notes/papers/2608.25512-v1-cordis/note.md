## 核心结论

一句话：**这篇把「运行时动态组合」拆成时间与空间两个可组合性维度，用「可逆效应」（每个上下文变换都由运行时持有一个逆）与「响应式余效应」（把每次上下文变化对照组件声明的依赖集分类成激活/去激活/中性）分别建立单组件的局部保证，再把两者塞进同一个上下文类型，给出一个组件演算，并用五组定理把保证提升到任意交错的多组件系统。**

它的贡献层次要分清：

- **理论**（§3–§4，p9–57）：主要工作量在这里。核心构造是「上下文 = 状态 × 逆累加器」的效应上下文 `∂Γ`、把逆改为在应用点返回的 `𝔈*Γ`、把一次加载重化成迭代器 `ℑΓ`，以及把余效应上下文 `Σ` 并进自相似的 `Γ∞`；演算是九个规则 + 两个关系（编排 `⇒` 与生命周期 `⟶`），元理论给的是保持性、恢复精确性（含 terminal recovery）、依赖排序与 resolution coherence、进展、合流。
- **实现**（§5，p57–70）：Cordis 三层（核心库 / 组件加载器 / 应用框架），核心库只有一条原语 `ctx.effect`，其余（`ctx.set`、`ctx.use`、HMR）都归约到它。给出十个算法，但**没有任何性能数字**。
- **证据**（§5.3，p69–70）：Koishi 的 4000+ 社区插件是**观测性**案例，作者自己把它定性为 "existence-and-adoption result rather than a quantitative one"，并明说开销与开发效率的度量是 future work。所以这篇的说服力来自证明，不来自测量。

适合谁读：做插件系统、IDE 扩展宿主、agent harness（尤其是「运行时自我改写」这一类）的工程师，以及关心 effect/coeffect 如何从静态类型系统落到运行时的 PL 读者。只想看工程结论的话，读 §1.2、§4.2.2、§5.1.3、§5.2、§6.1、§6.5 六处即可，其余是证明。

## 问题与动机

### 两个维度

作者把「动态组合」的要求拆成两个正交维度（§1.1，p4）：

- **时间可组合性**（temporal composability）：组件被移除时，它对共享环境做过的修改必须被完整、安全地撤销。静态情形下这退化为词法作用域（RAII、bracket）；动态情形下要处理**生命周期不受词法边界约束的长时效应**。
- **空间可组合性**（spatial composability）：组件必须能声明、发现、解析彼此之间的依赖，并在依赖变化时协调生命周期。静态情形下这退化为模块导入解析；动态情形下依赖会在执行中**出现、消失、换身份**。

这个拆法的好处是它把「动态组合」这个模糊诉求变成了两个可分别形式化的东西：时间维度对应 effect（计算如何改环境），空间维度对应 coeffect（计算如何依赖环境）。论文的全部形式化就是围绕这一句展开的。

### 两个动机案例

**VSCode 插件系统**（§1.2.1，p4–5）。作者给了两个具体限制，并配了两个可核的数字（脚注 1：数据取自 2026-06-09 的 VS Code Marketplace）：

- 时间侧：所有扩展跑在共享的 extension host 里，**没有卸载单个扩展代码的机制**；`activate` 执行过之后，禁用/卸载要重启整个 host。按安装量前 100 的扩展里 **87 个含可执行代码**，因此移除时都需要重启。`deactivate` 钩子只是 host 进程终止时的优雅关闭回调，不构成热移除；而且它把效应释放（`deactivate`）与效应创建（`activate`）分到两个函数里，破坏「关注点局部性」，完整清理难以验证。
- 空间侧：`extensionDependencies` 存在但几乎没人用——前 100 里**只有 7 个**对非内置扩展声明了它。原因是 API 形状：扩展是通过 commands/views/language features 这些固定的宿主扩展点贡献能力，而不是彼此依赖；跨扩展交互走 `vscode.extensions.getExtension(...).exports`，返回值默认 `any`，**没有受检接口**。

**自演化 agent harness**（§1.2.2，p5）。作者把 harness 的职责列了一串（工具套件、执行环境、权限与沙箱、会话状态、上下文管理与记忆、子 agent 编排、对外接口），然后指出：未来的 harness 可能会在自己持续服务请求的同时生成并部署对自身组件的修改（原文用 `may`，是可能性而非断言），每一次修改都是一次动态组合。没有时间可组合性，每次自我修改都要重启并丢掉进程内累积状态；没有空间可组合性，每个模块只能自己检测并适配依赖的出现/消失/换身份，而朴素的代码替换可能静默打断依赖者或引入只在 reload 时才暴露的循环依赖。

这一段是动机，不是证据——论文没有做任何 harness 实验（§8 把它列为未来方向）。

### 粗粒度替代为什么不够

操作系统在**进程**粒度给时间可组合性，容器编排在**服务**粒度给空间可组合性（§1.2.3，p5–6）。作者认为这带来两类成本：时间上每次重启丢掉进程内状态（缓存、连接、部分计算），重建要秒到分钟，期间维持可用性得靠冗余副本；空间上容器级编排无法表达**同一地址空间内**组件之间的依赖，且把本可以是本地函数调用的交互变成网络调用。结论是「粒度错配」：现代系统在比进程/容器更细的层次上组合，需要一个和组件同粒度的抽象。

## 背景：effect 与 coeffect（压缩版）

§2（p7–8）是给 PL 读者的铺垫，这里只留理解后文必需的部分。

- **effect 系统**把类型判断精化成 `Γ ⊢ t : T | effect`，effect 是「这次计算可能产生哪些副作用」的代数元素。三条主线：Moggi 的 monad（`T(A)`、`η`、`μ`）、Plotkin & Power 的代数效应（签名 `Σ` 声明操作，程序自由调用而不绑定解释）、Plotkin & Pretnar 的 handler（`handle e with { op(v, κ) ↦ … }`，`κ` 是被界定的续延）。
- **coeffect 系统**反过来注解**上下文**：`Γ | coeffect ⊢ t : T`，描述「这次计算要求环境提供什么」——要访问的资源、要持有的权限、要依赖的服务。两条主线：Uustalu & Vene 的 comonad（`ε` 取出当前值、`δ` 复制上下文）、Petricek 等人的 coeffect，以及用预序半环 `S` 做刻度的 graded 版本（0 未用、1 线性、n 有界、∞ 无限制）。
- **关键差异**（§2.3，p8）：经典 effect/coeffect 系统是**静态工具**——effect 在词法固定的作用域里追踪、由编译期 handler 消解；coeffect 注解在**执行前**确定的上下文上校验。而动态组合要求这些保证对**运行时到达和离开**的组件成立、对着**持续演化**的上下文成立：部署后加载的插件没有词法作用域可界定，运行时配置产生的依赖没有编译期上下文可预期。

作者的转向因此不是「给静态类型系统加更多注解」，而是**把 effect 与 coeffect 的概念结构具体化（reify）成运行时可直接操作的对象**，让运行时动态地建立这些系统在静态世界里提供的保证。这句话是整篇的方法论纲领。

## 机制一：可逆效应（§3.1）

### 从「变换」到「带账本的变换」

起点很朴素：任取一个不纯函数 `f : X ⇝ Y`，把它改写成纯形式 `f : Γ × X → Γ × Y`，其中 `Γ` 是上下文类型。固定输入 `x`，映射 `γ ↦ pr₁(f(γ, x))` 就是这次调用的副作用，与返回值无关。于是**所有副作用都是 `Γ → Γ` 上的变换**，而 `Γ → Γ` 在复合 `∘` 下是幺半群：闭包（两个效应顺序复合还是效应）、结合律（复合与括号无关）、单位元（`id_Γ`）。

要能撤销，就给每个变换配一个逆。作者在这里做了一个明确的取舍：**只要单侧逆**。`g` 是 `f` 的左逆，运行时只保证 `g ∘ f`，从不要求 `f ∘ g`。为什么单侧够用，是 §3.1.2 才展开的（逆在应用点返回、见证只要求 `g(δ) = γ`）：运行时把逆拿到「该效应刚产生的那个状态」上跑，`f ∘ g` 这个方向不会被用到——这一句是本笔记对后续论证的概括，不是 §3.1.1 的原话。

成对的变换自带一个乘法（Definition 1，式 4）：

```math
(f_1, g_1) \circ (f_2, g_2) := (f_1 \circ f_2,\ g_2 \circ g_1)
```

读法：左操作数在右操作数之后作用，逆则按相反顺序累积。这让 `(Γ→Γ) × (Γ→Γ)` 成为幺半群——变换幺半群与其反范畴的积，作者叫它**扭转复合幺半群** `𝔗_Γ`。

把这个「逆的累积」放进上下文本身，就得到效应上下文（Definition 2，式 5）：

```math
\partial\Gamma := \Gamma \times (\Gamma \to \Gamma)
```

一个元素是 `(γ, φ)`：`γ` 是当前状态，`φ` 是**累加器**——到目前为止所有效应的逆的复合，也是把上下文恢复到初始状态的函数。初始效应上下文是 `(γ₀, id_Γ)`。迭代 `∂` 得到塔 `Γ, ∂Γ, ∂²Γ, …`。

两个具体构造（Definition 3、6）：

```math
\begin{aligned}
\mathrm{track}_\Gamma(f,g) &= (\gamma,\varphi) \mapsto (f(\gamma),\ \varphi \circ g)\\
\mathrm{recover}_\Gamma(\gamma,\varphi) &= (\varphi(\gamma),\ \mathrm{id}_\Gamma)
\end{aligned}
```

读法：`track` 改状态的同时把逆压到账本上（注意是 `φ ∘ g`，新逆在里层，所以 `recover` 时按 LIFO 顺序执行）；`recover` 把账本作用到当前状态并把账本清零。

四条性质撑起「局部时间可组合性」：

- **Theorem 4**（p10）：`pr₁ ∘ track_Γ(f,g) = f ∘ pr₁`——追踪不改变前向行为，账本带什么逆都不影响状态怎么变。
- **Theorem 5**（p10）：`track_Γ` 是 `𝔗_Γ → (∂Γ → ∂Γ)` 的幺半群同态——逐个追踪与一次性追踪扭转复合的结果一致，所以一串效应可以当作单个效应来推理。
- **Theorem 7**（p11）：若 `g(f(γ)) = γ`，则 `recover(track(f,g)(γ,φ)) = recover(γ,φ)`。也就是说**恢复的目标不因中间插入一个可逆步骤而移动**。作者把 `φ(γ) = γ₀` 叫作状态的**可靠性不变式**（soundness invariant）：从 `(γ₀, id_Γ)` 出发，凡逆真的能撤销的追踪步骤，都保持这个不变式，`recover` 把每个这样的状态带回 `(γ₀, id_Γ)`。
- **Theorem 16**（p15）：一串 `𝔈*` 按序应用、按**逆序**撤销时，每一步逆都拿到它自己那次应用产生的状态，中间状态全部满足不变式。

### 单侧逆与逐状态逆

`track/recover` 有两个明显不足（§3.1.2，p12）：

1. `track(f,g)` 在**看到状态之前**就固定了 `g`，所以同一个 `g` 必须在效应可能遇到的**每一个**状态上都满足 `g(f(γ)) = γ`。实际需要的少得多：只需要在**它被应用的那一个状态**上能撤销，而那个逆可以逐状态不同——它没法在参数位置给定，只能在应用点返回。
2. `recover` 是**全有或全无**的：不能选择性地撤一个效应而保留其它。

于是两头各改一次，改完形状对称：输入侧与输出侧都是「从上下文到一个变换后的上下文**加上一个逆**」的映射。Definition 8（式 12）先给类型 `𝔈_Γ := Γ → Γ × (Γ → Γ)`，再用一个见证把它精化成 `𝔈*_Γ`：

```math
\mathfrak{E}^{*}_\Gamma := (e : \Gamma \to \Gamma \times (\Gamma \to \Gamma)) \times \big((\gamma:\Gamma) \to (\delta:\Gamma) \to (g:\Gamma\to\Gamma) \to ((\delta, g) = e(\gamma) \to g(\delta) = \gamma)\big)
```

读法：`𝔈_Γ` 是「给一个状态，返回新状态和这次效应的逆」；`𝔈*_Γ` 再附一个**见证**（witness）——对任意状态 `γ`，若 `e(γ) = (δ, g)`，则 `g(δ) = γ`。注意这个方程只在**应用点**成立，所以每个状态可以选不同的逆；而一个满足 `g ∘ f = id_Γ` 的均匀逆自然满足它（Theorem 11，p13：`𝔈*_Γ` 是 `𝔈_Γ` 的子幺半群，且这个嵌入把每个 `g∘f = id_Γ` 的对送进 `𝔈*_Γ`）。

由于 `𝔈_Γ` 不再是上下文上的自同态，不能直接复合，于是定义新的**效应复合**（Definition 9，式 13）：

```math
f \diamond g = \gamma \mapsto \mathbf{let}\ (\delta, s) = g(\gamma)\ \mathbf{in}\ \mathbf{let}\ (\varepsilon, t) = f(\delta)\ \mathbf{in}\ (\varepsilon,\ s \circ t)
```

读法：先跑 `g` 再跑 `f`，两个逆按相反顺序拼成一个。Theorem 10 说 `(𝔈_Γ, ⋄)` 是幺半群且扭转复合到它是同态；Theorem 13 说 `effect_Γ` 保持 `⋄`。

接下来是把 `𝔈_Γ` 提升到 `𝔈_{∂Γ}`（Definition 12，式 14）：`effect_Γ(e)` 在 `(γ, φ)` 上先跑 `e` 得到 `(δ, g)`，把 `g` 压进账本，**再为「撤销这个效应」本身返回一个逆**——那个逆就是 `track_Γ(g, pr₁ ∘ e)`，即「用 `g` 改状态，而撤销它的办法是再执行一次 `e`」。这一步是整节最漂亮的地方：**撤销本身也是一个效应，于是它自己也需要被追踪**，`∂` 塔因此是自相似的。

但 Theorem 15（p14–15）给出了一个必须诚实对待的结论：`effect_Γ` **不**把 `𝔈*_Γ` 送进 `𝔈*_{∂Γ}`。提升后的逆 `g′(Δ) = (γ, φ ∘ g ∘ f)` 状态恢复精确，但累加器只在 `g ∘ f = id_Γ` 时才恢复（注意这仍是**单侧**条件，不是 `f ∘ g = id_Γ`）；一般情况下 `(φ ∘ g ∘ f)(γ) = φ(γ)`，即**只保住可靠性不变式**。用一句话说：撤到「恢复目标」为止是稳的；要让账本也一字不差，需要这个逆在该效应上**处处**可撤销（`g ∘ f = id_Γ`），而不只是在应用点那一个状态。

### 迭代器：一次加载是多步

组件加载的不是一个效应而是一串，卸载要撤的是整串。作者把它具体化成**效应迭代器**（Definition 17，式 17）：

```math
\mathfrak{I}_\Gamma := \mu \mathfrak{I}.\ \Gamma \to \Gamma \times (\Gamma \to \Gamma) \times \mathsf{Maybe}(\mathfrak{I})
```

每次迭代返回 `(δ, g, o)`：新状态、这一步的逆、以及续延（`Nothing` 终止、`Just(i)` 继续）。见证与 `𝔈*` 同形。`effectiter_Γ`（Definition 18，式 18）把 `effect_Γ` 沿续延递归展开，每步把逆压进账本，于是 `φ ∘ g₁ ∘ ⋯ ∘ g_k` 按 LIFO 撤销。

这里有一个值得工程读者注意的观察：作者明确指出 `Maybe(ℑ)` 的续延**在任意两次相邻迭代之间提供了一个边界**，边界处的上下文就是「到目前为止的迭代造成的状态」、账本只恢复这些而不多恢复。作者把它称为「具体化的有界续延（reified delimited continuation）」，也就是主流语言用 `yield` 暴露的结构——所以这个模型能直接落到生成器上。§5 的 `execute`（Algorithm 1）正是这么实现的。

普通效应函数是退化情形：第一次迭代就返回 `Nothing` 的迭代器（式 19），嵌入保持见证。

### 局部保证到此为止

作者把「局部时间可组合性」明确表述成一条**判据**：对一个组件施加的每个效应函数序列，累加器把它带回起始上下文（Theorem 7）；按逆序撤销时每个逆拿到它自己那次应用跑过的状态（Theorem 16）。然后主动点出这条判据**漏掉的两件事**，都要等多组件才出现：按累加器强加的顺序之外的方式撤销；以及一个序列**交错**了别的组件的效应。这两件事由 §3.4 的独立性补上——而独立性是**对效应的条件**，不是构造本身的属性。这句限定很重要，后面 §4.3.2 的全部工作就是在验证这个条件。

## 机制二：响应式余效应（§3.2）

### 余效应上下文 Σ 与 get/set

传统 IoC 容器把依赖建模成简单的键值映射。论文把它形式化成依赖偏函数（Definition 19，式 20）：

```math
\Sigma := (k : K) \rightharpoonup \mathcal{V}_k
```

用**类型族** `𝒱 : K → Type` 而不是统一的 `V`，是为了让每个键自带值类型、给依赖访问静态类型安全。四个操作记号：`σ(k)` 应用、`σ[k ↦ v]` 绑定、`σ ∖ k` 限制、`k ∈ dom(σ)` 成员。扩展与限制带前提：**不能重复提供**（扩展要求 `k ∉ dom(σ)`）、**不能撤销不存在的**（限制要求 `k ∈ dom(σ)`）；违反前提被报成错误且**不产生迁移**，所以描述「确实发生的迁移」的效应代数原样适用。作者还给了一个可选的读法：把每个 `Σ ⇀ Σ` 读成 `Σ → Maybe(Σ)` 在 Maybe monad 里复合。

两个核心操作（Definition 20，式 21）：`get(k)` 要求 `k ∈ dom(σ)`，返回 `σ(k)`；`set(k, v)` 要求 `k ∉ dom(σ)`，返回 `(σ[k↦v], λσ′. σ′∖k)`。

关键的一句：**`set(k,v)` 的类型是 `𝔈*_Σ`**，即它是余效应上下文上的效应函数。于是 §3.1 的全部机器直接可用——`effect_Σ` 自动给出依赖注册的追踪与恢复。作者把这叫「响应式余效应与可逆效应的协同」：**余效应操作是效应，而效应是可逆的**。

### 满足谓词与三分类

只登记和访问还不够：访问一个缺席的依赖是运行时失败，所以组件应该**在所有声明的依赖都就位之后才激活**，而不是乐观访问再失败。为此定义满足谓词（式 22）：

`σ ⊧ d ≔ ∀k ∈ d. k ∈ dom(σ)`（对余效应规格 `d ⊆ K`），因 `dom(σ)` 有限所以**可判定**。

因为所有对 `σ` 的修改都经过效应函数（而它们的逆恢复前一个域），**满足性的变化在每个效应边界上都是可检测的**——这是响应性的代数基础。

于是余效应规格就是键集（Definition 21：`𝔇_Σ := Set(K)`），而「响应式」体现在它如何**分类状态迁移**（Definition 22，式 24）：`notify_d(σ, σ′)` 在 `σ ⊭ d ∧ σ′ ⊧ d` 时给 `activating`，在 `σ ⊧ d ∧ σ′ ⊭ d` 时给 `deactivating`，否则 `neutral`。

激活迁移触发组件的效应执行（按 §3.1 追踪），去激活迁移触发恢复（应用累加器）。这两个动作的**操作语义**在 §4 给出——§3 只到分类为止。

同样，作者在这里也给了「局部空间可组合性」的判据：组件只在满足其规格的状态上激活（所以永远不会读到缺席的绑定），每次上下文变化都被对照规格分类（所以满足性的丧失在发生处被检测并驱动去激活）。然后同样点出漏掉的两件事：**只在引起的去激活都完成之后才撤下绑定**，以及**在激活运行期间保持它读到的绑定不动**。这两条是「对其他组件的条件」，属于全局形式，§4.3.3 建立。

### isolation 与 interception

平铺的 `Σ` 不够用：同一逻辑依赖在不同组件下可能要绑不同值。§3.2.3（p19–21）加两个机制，并且先做了一个区分——**denotation vs realization**（Definition 23）：

- **原地实现**（in-place）：修改上下文并返回非平凡逆；后继别名输入，恢复靠跑逆。
- **派生实现**（derived）：不动输入，返回一个从它派生的新上下文，逆是恒等；恢复靠丢弃派生上下文。

纯函数式设定下两者重合，命令式宿主可以逐操作选择（§5.1.2 两种都实现了）。**isolation 与 interception 直接给定为派生实现**：它们不写共享表，只调整「键在这个上下文下如何解析」，所以没有效应可追踪、也没有东西给 `effect_Γ` 提升，恢复就是丢弃派生上下文。

**余效应隔离**（Definition 24–25，式 25–26）：`Σ_iso := (K ⇀ R) × ((r : R) ⇀ 𝒱_r)`，一对 `(ρ, σ)`——`ρ` 是隔离域表（把键映射到域标识，域外的键解析到自身，`R ⊇ K`），`σ` 是依赖表（域 → 值）。访问 `k` 先 `ρ(k)` 再 `σ(ρ(k))`。`isolate(k, r)` 派生一个把 `k` 指派到域 `r` 的上下文，依赖表原样继承；**已隔离的键是重新指派而不是拒绝**。作者把它称作「运行时的 ad-hoc 多态系统」：同一个键可以在不同上下文下解析到完全不同的值，而且可以在运行时调整。`set` 仍是 `𝔈*_{Σ_iso}`（因此继承可逆性），`isolate` 不需要——它派生而不写共享表。

**余效应拦截**（Definition 26–27，式 27–28）：`Σ_inter := ((k : K) → ℳ_k) × ((k : K) ⇀ (ℳ_k → 𝒱_k))`，规格也扩成 `𝔇_inter := (k : K) ⇀ ℳ_k`。上下文带 `(ι, σ)`：`ι` 是装在上下文上的元数据（默认空 `ε_k`），`σ` 把每个键映射到「元数据 → 值」的提供函数。每个键的元数据自带幺半群 `(ℳ_k, ⊕_k, ε_k)`。访问时算 `σ(k)(d(k) ⊕_k ι(k))`：组件声明的元数据与上下文携带的元数据合并，再喂给提供函数。

这里有一个方向性细节：合并是**右偏的**，`ι(k)` 优先，可以覆盖组件的声明——「让外层上下文约束一个组件如何使用某个余效应，而不修改这个组件」（§6.3 用到）。另外 `intercept` 也要求元数据幺半群，且合并语义按键自定（标量覆盖、集合取并）。

## 统一：上下文范式与观察等价（§3.3）

### Γ∞

把效应上下文 `∂Γ` 的递归结构与余效应上下文 `Σ` 合起来（Definition 28，式 29）：

```math
\Gamma_\infty := \mu \Gamma.\ \Gamma \times (\Gamma \to \Gamma) \times \Sigma
```

三个投影：当前上下文状态（递归）、本层的逆累加器、携带依赖信息的余效应上下文。于是 `𝔈_{Γ∞}` 映射回自身，`∂` 塔塌缩成一个自相似类型。

两个后果值得单独说：

1. **`Σ` 吞掉了所有共享可变状态**，不只是「组件间依赖」：`𝒱` 无约束，系统需要共享的任何状态都可以编码成某个键上的依赖。这让「每一次组件与环境的交互都经过同一个实体」成为可能。
2. **光有「唯一实体」还不够**，所以 Definition 29 给每个键配的不只是值类型，还有一组**余效应操作** `𝒜_k`：`a : X_a → 𝒱_k ⇀ 𝒱_k × (𝒱_k ⇀ 𝒱_k) × B_a`（前两段构成 `𝒱_k` 上的效应函数，第三段是**结果**）。操作通过 lift（式 31）作用到 `Σ` 上，读写的只有 `k` 的绑定——「给 `k` 的操作定型在 `𝒱_k` 上，这就是把它限制在 `k` 的绑定上」：不需要额外侧条件。

Definition 30（式 32）再定义**上下文中介的迭代器** `ℑ^𝒜_Σ(S, P)`：最少包含单位元，并在续延都合法时包含两类阶段——`k ∈ S` 上的一个操作阶段（`a_Σ(x)`，按**结果**选续延，所以后面的参数可以依赖前面拿到的结果），以及 `k ∈ P` 上的一个**提供阶段**（`set(k, v)`，装在操作无法创建的键上）。成员的阶段包括它自己的和续延能到达的每个迭代器的。

「成员资格」就是「每个交互都经过上下文」的形式内容。落在类外的是读别的东西的映射——读一个它不执行阶段的键，或读没有键绑定的位置。作者举的例子很具体：一个从**上下文不携带的计数器**取句柄的分配器属于第二种，一旦把计数器绑到自己的键上，它就成了上下文中介的。

### 观察等价：为什么「完整恢复」不等于「一字不差」

§3.1 的恢复保证断言的是**状态相等**，作者立刻说这是理想化，因为物理状态不可能原样恢复（§3.3.2，p23）：

- `free` 把块还给分配器，但**不恢复** `malloc` 之前的堆布局；
- 生成名（generative name）不会被「丢弃它」的逆恢复，因为下一次创建会取一个新名。

所以 §3 的等式都要**模一个等价 `≃`** 来读，而 `≃` 取**观察等价**：没有观察者能区分的两个状态就相关。观察者拿到什么，关系就是什么——对值，观察者是它的键的操作集（Definition 29）；对上下文，关系由各键的关系组装。

形式化（Definition 31–33）：

- **测试**（test）是有限字，字母是各操作 `a(x)` 的**前向映射**与**产出的逆**，每个字母作用在前面的字母留下的值上；它的**结果**是其中前向映射沿途给出的那些；前提失败处未定义。两值**不可区分**（`v ≈_𝒜 v′`）当且仅当每个测试在两边都定义或都不定义、且结果相同。键上的等价就是它自己操作下的不可区分：`≃_k := ≈_{𝒜_k}`。
- **Lemma 32**（p23）：每个 `≃_k` 是等价关系，每个操作都**尊重**它，且它是**最粗**的这种关系。第 (2) 款同时是证明原则：要证两值相关，只需给出一个被所有操作尊重、且包含该对的等价关系。
- 上下文层面（Definition 33，式 34）：`σ ≃_S σ′` 当且仅当它们在 `S` 内的键上域相同、且逐键值相关；状态层面比较余效应投影。`S = K` 时下标省略。
- **Definition 34**（式 35）把 `≃_S` 沿类型构造子扩展：函数是「相关输入给相关输出」、积逐分量、`Maybe` 分情况、递归类型**余归纳**读（取满足展开的最大关系）。函数与迭代器上的 `≃_S` 只是**偏等价**（Lemma 35：对称、传递，但不必然自反）——自反性要求映射在每一对相关输入上都给相关输出，这正是「尊重」这个条件而非免费获得的东西。作者点得很准：**尊重在 `≃` 与 `≃_S` 上是两个互不蕴含的条件**，因为 `≃ ⊆ ≃_S` 同时弱化了假设和结论；一个在 `S` 外的键上分支的映射就是分离两者的例子。
- **Lemma 38**（p25）：把 `=` 换成 `≃` 之后，§3.1 的每个状态等式仍成立，且从 `(γ₀, id_Γ)` 可达的每个状态的累加器都尊重 `≃`。证明只用传递性与尊重，所以对任何等价都成立。

这一段的意义不只是技术性的：**`≃` 的粒度是一个设计变量**。`≃_k` 是「键的操作生成的测试下的不可区分」，所以**接口发布的结果越少、关系越粗**；把一个调用者不需要的结果收回，就能把某个键从「不交换」挪到「交换」那一侧（§3.4.2 用 POSIX 的 `open` 与 `mmap` 举例，并援引 scalable commutativity rule）。这条对工程读者是可直接用的：**恢复语义的强度，由你暴露的接口决定**。

### 层次化组合

`Γ∞` 的递归结构给出层次控制（§3.3.1 末，p22–23）：父上下文聚合多个子层的效应，形成树形控制结构。作者把「plug-in」的字面意思兑现了：加载组件 = 执行它的效应（插上），卸载 = 撤销它的效应（拔下，不影响其它运行中的组件）；不同层次的组件可独立装卸，父上下文聚合管理所有子组件的效应，支持任意嵌套。

## 独立性：把局部保证推到多组件（§3.4）

### 𝔐(i) 与两条要求

在单个组件内，Theorem 16 只覆盖「在它自己那次应用产生的状态上撤销」。有两种情形需要更强的东西（§3.4.1，p26）：**一个逆可能在后续效应仍在的情况下被运行**（这就是从一个运行中的系统里移除一个组件）；以及**一个序列可能交错多个组件的效应**，每个组件持有自己的逆，于是一方的逆被另一方的应用隔开。两种情形下逆都会遇到被外来效应移动过的状态，「它是否仍能撤销它本该撤销的东西」就变成**交换性**问题。

迭代器会产生多个映射：它可达的每次迭代的前向映射，以及它在每个上下文状态上产出的逆。所以交换性要谈的是两个**集合**（Definition 40，式 38）：`reach(i)` 是最少包含 `i`、对续延封闭的迭代器集；`𝔐(i)` 是 `reach(i)` 里每个迭代器的前向映射与产出逆**生成的子幺半群**；`len(i)` 是续延序下链长的上确界。

**Lemma 41**（p27）把检查降到生成元上：生成元两两交换则两个幺半群逐元素交换；且 `⋄` 不放大变换幺半群（`𝔐(e₁ ⋄ e₂) ⊆ ⟨𝔐(e₁) ∪ 𝔐(e₂)⟩`）。

**Definition 42**（式 39–40）给出独立性，两条缺一不可：

```math
\begin{aligned}
&\forall f \in \mathfrak{M}(i),\ g \in \mathfrak{M}(j).\ f \circ g = g \circ f\\
&\forall i' \in \mathrm{reach}(i),\ g \in \mathfrak{M}(j),\ \gamma \in \Gamma.\ \mathrm{pr}_{2,3}(i'(g(\gamma))) = \mathrm{pr}_{2,3}(i'(\gamma))
\end{aligned}
```

读法：第一条是所有前向映射与所有逆（含外来逆）两两交换；第二条是**一方的变换不改变另一方「产出什么逆、接下来走哪一支」**，并且原文要求**对调 `i` 与 `j` 后同样成立**（独立性是对称的，两条各自都要双向）。第二条不是多余的：交换映射本身并不保证迭代器在被移动过的状态上产出同一个逆和同一个续延。作者还特意区分了「`⋄` 下交换」与「独立」：`e₁ ⋄ e₂ = e₂ ⋄ e₁` 只把两个顺序的复合前向/复合逆互相比，而每个逆进入复合时都是在**它自己那次应用产生的状态**上；独立性则把一方每个变换与另一方每个变换配对，包括「前向映射配外来逆」。

**Theorem 43**（p28）：若 `e₁, …, e_n ∈ 𝔈*_Γ` 两两独立、按序从 `γ₀` 应用，每个 `g_i` 是 `e_i` 在应用处产出的逆，则在序列到达的状态上**按 `{1,…,n}` 的任意排列**应用这 n 个逆，都能回到 `γ₀`。证明是对排列首元素做下降归纳，用两条：`g_j` 能穿过它之后的所有前向映射（第一条），以及后续效应在「省略 `e_j` 的状态」上产出同一个逆（第二条）。

这条定理就是「热拔一个组件」的理论依据——**不必按 LIFO 撤**，只要两两独立。

### 单键交换性成为组件的义务

`≃` 是模等价读的（Lemma 38），这既让交换性可达（两个操作留下 `≃_k` 视为相同的值仍算交换），也多要一样东西：操作还产出**结果**（Definition 44，式 41）：两个操作独立，当且仅当它们的 lift 在每对参数上作为效应函数独立（Definition 42），**并且**一方的变换不扰动另一方产出的结果。

**Theorem 45**（p29）：**不同键上的操作天然独立**。因为每个生成元都是「只读写一个键」的映射，两个不同的键互不干扰。所以条件只在**同一个键内部**的键对上才紧。

于是作者把这个条件做成**余效应自身的第三个组成部分**（Definition 46）：一个键上的余效应 = `(𝒱_k, 𝒜_k, 证明该键交换)`。这与效应函数的见证是平行的——「每个见证证明的是消费者本来只能假设的条件；返回的逆在那里撤销，操作在这里交换；两者都在**写定义的地方**提供，而不是在**使用的地方**检查」。又因为 Theorem 45，这个义务只落在**提供该键的组件**上，不落在消费者上。

三个例子把「交换性」变成可判定的设计问题（p29）：

- **表类值**（路由表、事件监听器）：每次注册取一个自己的标识符、逆删掉那一条，则两次注册命名两条条目，**任意顺序都留下对每个测试回答相同的表**，且任一注册可在另一条还在时撤下。CRDT 正是为此给每次添加附唯一 tag；而「只命名裸元素的集合」没有这个性质。
- **有序链**（middleware 链）：**不交换**——插在另一个前面的 middleware 看到的是不同的请求，两个顺序也无法在不扰动对方的情况下撤下任一个。
- **分配器**：按接口发布什么来分。若句柄不被任何操作比较，则没有测试观察它们，`≃_k` 把两个堆按句柄重命名视为相同，分配就**交换**（这正是 CompCert 关联程序与翻译后程序内存状态的办法）；若地址是**按相等比较的结果**，则进一步分配的结果能区分两个顺序，键就**不交换**。POSIX 自己画了同一条线：`mmap` 可返回任意未用地址、`creat` 可指派任意未用 inode，而 `open` 被要求返回**最低可用描述符**——仅这一条要求就让两次描述符分配不交换。

**Theorem 47**（p30）：若 `i₁ ∈ ℑ^𝒜_Σ(S₁, P₁)`、`i₂ ∈ ℑ^𝒜_Σ(S₂, P₂)` 且 `P₁ ∩ S₂ = P₂ ∩ S₁ = ⌀`，并且两者都有操作出现的每个键都交换，则 `i₁` 与 `i₂` **独立**。

这是全篇的枢纽：**独立性（时间侧的条件）被归约到单键交换性（空间侧的性质）**。有了每个余效应都带见证（Definition 46），Theorem 47 的交换性假设在每个键上都由组件自己提供，只剩 `P₁ ∩ S₂ = P₂ ∩ S₁ = ⌀` 这个**不相交性**要逐对检查——而 §4 把它从两个组件的声明里读出来。

作者最后把这种分解讲成一句话：**交换的部分由效应承担，顺序敏感的部分由余效应承担**。前者一个组件按任务需要的顺序执行、系统按方便的顺序撤销，两个组件互不约束；后者由「不交换的键」承担，顺序只能从效应外面强加，而强加的地方有两个——组件内部由累加器按 LIFO（Theorem 16），跨组件由声明的余效应（提供先于满足）。可组合性因此在**组件的粒度**而不是单个效应的粒度上获得。

## 演算：组件、纤维与九条规则（§4）

### 组件与纤维

**组件**（Definition 48，式 42）是一个三元组：

```math
\mathfrak{C}_\Gamma := (d : \mathfrak{D}_\Gamma) \times (p : \mathfrak{P}_\Gamma) \times \mathfrak{I}^{\,d \cup p}_\Gamma
```

读法：`d` 是**余效应规格**（要向环境要哪些键），`p` 是**余效应提供**（可能提供哪些键；`p` 之外的键它的效应函数不装绑定），`e` 是**在 `d ∪ p` 这些键上被见证的效应迭代器**——注意见证的键集就是「这个组件自己的接口」，这是后面「每个组件的保证在它自己声明的键上读」的来源。

**纤维**（fiber，Definition 49）是组件的一次实例化，记作 `⟨d, p, e, π, σ, τ, θ⟩`：`π` 是父（`root` 或另一条纤维）、`σ` 是它自己的余效应表（激活前为空，激活中由它的效应写）、`τ` 是退休标志、`θ` 是生命周期状态：

`Θ_Γ := Inactive | Reloading(i, g, ω) | Active(g, ω) | Unloading(g, ω)`

其中 `i` 是**剩余的效应迭代器**、`g` 是**已建立的累加器**、`ω` 是**已提交的视图**（committed view）：把声明的每个键送到「transition 提交时提供它的那条纤维的名字」。两个稳定态是 `Inactive` 与 `Active`，两个过渡态是 `Reloading`（激活中）与 `Unloading`（去激活中）。这个「过渡态」的设计是全文工程味最重的一处：真实运行时的 transition 是**跨一个区间**的，不是一步完成的。

**registry**（Definition 50）是 `F_γ : 𝔑 ⇀ 𝔉_Γ`，父指针构成以 `root` 为根的树。名字是**原子**：没有规则计算它、检查它的结构、或用相等之外的关系比较两个名字，引入纤维只是取一个未用的名字。作者明确说这是「动态创建的局部名字」的纪律，在这里用于纤维身份。

一个关键设计：**每个纤维拥有自己的表，所以余效应上下文是派生而非存储的**（式 46）：

`σ_γ := ⋃ { σ_m | m ∈ dom(F_γ), θ_m = Active(−, −) }`

只并**Active** 纤维的表，带来三个后果：

1. 不相交性让这个并是函数（每个键恰好在一个 Active 纤维的表里），于是每个键有**唯一可能的提供者** `provider_k(γ)`，由提供集固定而不由状态固定。
2. **一个纤维可以在撤下任何东西之前先停止提供**——这正是 §4.2.2 的排序纪律的来源。
3. 过渡中的纤维（`Reloading`/`Unloading`）通过它持有的 `ω` 读余效应、**不提供自己的任何键**，所以「它已经写进去的键」还不算「依赖者可以据此激活的键」。

### 九条规则与图 1

§4.2（p34）给九条规则、两个关系：**编排规则** `γ ⇒ δ`（编排者可做的动作，前提说明何时合法、不说明何时发生）与**生命周期规则** `γ ⟶ δ`（系统在前提成立时无提示地走一步）。八条落在 Figure 1 的边上，第九条 `O-Retire` 只写退休标志、在四个状态上都适用，所以是四个自环，图里省略。

![Figure 1：组件生命周期。最左侧空节点表示纤维不在 registry 中；八条边对应八条规则，`O-Retire` 是省略的四个自环。来源：原文 p34，300 dpi 渲染页裁剪](assets/figure1-lifecycle.png)

**编排**（§4.2.1，p34–35）：

- `O-Insert`：取一个未用的名字，父在 registry 或 root，组件合法，且**它的提供集与现有每条纤维的提供集都不相交**（`∀m. p ∩ p_m = ⌀`），装入一个 `Inactive`、`σ = ⌀`、`τ = ⊥` 的条目。最后这条前提就是**单源纪律**：一个键只有一个可能的提供者，因为编排者不能放进第二个声明它的组件。
- `O-Retire`：`n ∈ dom(F_γ)` 即可，把 `τ_n` 置 `⊤`。**无条件**，因为退休是请求，执行由生命周期规则完成。
- `O-Remove`：要求 `τ_n = ⊤`、`θ_n = Inactive`、`σ_n = ⌀`、且没有 `m` 的父是 `n`。前两条保证它已经去激活过（否则会丢掉累加器、泄漏），第四条保证树良形（子先于父移除），第三条保证移除不丢弃任何绑定（去激活后表已空，Corollary 69）。

**实例化**（Definition 52，p35）：一次迭代可以实例化一个组件，做法是**取该组件的 `O-Insert`（父为 `n`）代替状态映射**，产出的逆是**被实例化纤维的 `O-Retire`**。逆选 `O-Retire` 而不是 `O-Remove` 的理由很干脆：**逆必须在它被到达的任何状态上都能执行**，而 `O-Remove` 带前提（子纤维还 Active 时父的累加器就跑不动，且没有规则会移动子纤维，因为 `target_n` 不读纤维树）；`O-Retire` 只有 `n ∈ dom(F_γ)` 一个前提。它留下的条目是「退休、Inactive、空表」的**残留条目**（vestigial entry，Lemma 62）：与「纤维不存在」只在控制字段上不同，而没有规则能区分两者。

**生命周期**（§4.2.2，p35–37）。六个规则按方向分：激活把纤维带向它还没有的目标视图，去激活把它带离一个不再是目标的已提交视图。

激活：`L-Begin` 进 `Reloading(e_n, id_Γ, ω)`；`L-Iter` 取一次迭代，前提 `target_n(γ) = ω`，把新逆按 `g ∘ h` 压进累加器（与 Definition 18 一致，于是 LIFO）；`L-Finish` 落在 `Active(g ∘ h, ω)`。

去激活**不能一步做完**，理由很具体（p36）：一个因为提供者要走而被拆掉的组件，正在跑自己的 teardown，而 teardown **可能需要正在被撤走的那个余效应**——关连接池通常意味着把连接交还给提供它们的东西。所以消费者必须在整个去激活期间仍能读到那个键，而提供者的撤下必须在那之后才生效。于是规则把**决定**与**动作**分开：

- `L-Divert`（从 `Reloading`）：目标变了，把纤维路由进 `Unloading(g ∘ h, ω)`，其中两个分支是「中止当前迭代（`(δ,h) = (γ, id_Γ)`）」或「让这次迭代落地」。**中止只在迭代边界可能**，所以 divert 的粒度就是迭代器的粒度。
- `L-Leave`（从 `Active`）：只记录决定，把纤维标成 `Unloading`，**停止提供**（表离开 `σ_γ`），但保留自己的 `ω` 与别人的 `ω`。
- `L-Unload`（从 `Unloading`）：前提 `¬ relied_n(γ)`，应用累加器 `g(γ) = δ`，丢弃 `ω`，回到 `Inactive`。它是**全演算里唯一应用累加器的规则**（Table 1 确认）。

**guard**：`relied_n(γ)` 表示「有另一条已安装纤维把某个声明键解析到 `n`」（Definition 54，式 50）。它按**绑定**而非按纤维施加：声明了 `n` 的键以外的键的纤维不算障碍，在另一个域里解析同一键的也不算（§3.2.3）。在单源纪律下，这个逐绑定读法与更粗的「有纤维声明了 `p_n` 里的键」重合。

**为什么这个 guard 不死锁**（p37）：一旦 `L-Leave` 或 `L-Divert` 标了 `n`，它的表就离开 `σ_γ`，于是**没有目标视图还能指向 `n`**，每个曾提交到 `n` 的消费者自己也已经在离开的路上。Theorem 73 把这条变成「guard 总会释放」。

### 表 1：规则即写操作

Table 1（p40）把九条规则读成「对纤维 `n` 的写」，五列是规则、`θ^n_t`、`θ^n_{t+1}`、`Ψ_t`、被编辑的控制字段。这张表是后面所有 case analysis 的查表依据，也是工程实现与形式模型之间的对账表。几个查表结论（Lemma 59，p40–41）：

1. **表只在一个 `Ψ_t` 里动**：`σ^m_{t+1} ≠ σ^m_t` 只在该步作用于 `m`、或作用于 `n ≠ m` 且 `dom(σ^m) ∩ d_n ≠ ⌀` 时发生，后者只改 `d_n` 那些键上的**值**、不改域。
2. `ω_n` 只在 `L-Begin(n)` 出现、只在 `L-Unload(n)` 消失，所以**在一个 episode 内恒定**。
3. `Ψ_t = g^n_t` 只在 `L-Unload(n)`——没有别的规则把累加器应用到状态上。
4. `¬installed^n_t ∧ installed^n_{t+1} ⇒ step_t = L-Begin(n)`，反之 `⇒ L-Unload(n)`。
5. `π_n, d_n, p_n, e_n` 随条目进入就存在、**再不写**；`τ_n` 单调，只被 `O-Retire` 写 `⊤`。

第 5 条是后面几个定理的地基：组件的接口（声明、提供、效应函数）在一次存在期内**不可变**，变的只有生命周期与表。

### target view、quiet 与 confinement

**目标视图**（Definition 53，式 48）：

```math
\mathrm{target}_n(\gamma) := \begin{cases} \bot & \text{if } \tau_n \lor \lnot(\gamma \models d_n)\\ (k \in d_n) \mapsto \mathrm{provider}_k(\gamma) & \text{otherwise}\end{cases}
```

读法：目标**不是布尔**，而是「每个声明键当前由哪条纤维提供」这张总表；退休或依赖不满足时为 `⊥`。`quiet(γ)`（式 49）要求每条纤维都停在它的目标视图上：`Inactive` 的目标是 `⊥`、`Active(−, ω)` 的目标是 `ω`、其余状态直接不 quiet。

**记录提供者而不是值**是这里的关键取舍（p36）：否则「另一条纤维提供了相等的值」会被比较成相等。实现里 `fiber.committed` 存这张表、`fiber.target` 存它的哈希（§5.1.3）。由此得到一个对使用者有直接影响的行为：**提供者原地覆写自己的绑定不会被观察到**——想让替换传播，必须撤回绑定再重新装（§5.1.3，p63）。

**confinement**（Definition 55，p38）规定一个效应函数能碰什么。对每个 `n ∈ dom(F_γ)` 的状态，写 `δ = f(γ)`：

1. **写**：`dom(F_δ) = dom(F_γ)`；对每个 `m ≠ n`，`δ(m)` 与 `γ(m)` 只在 `σ_m|_{d_n}` 上可不同；`δ(n)` 与 `γ(n)` 只在 `σ` 上不同。
2. **读**：在两个状态上 `σ_n` 与各 `σ_m|_{d_n}` 相同的两个状态，被 `f` 送到同样这两处相同的状态。

读法：写侧允许**唯一一种**越出自己表的写——声明键的值住在提供者的表里，所以对声明余效应做操作就是移动 `σ_m|_{d_n}`；读侧则是「组件能读它声明的值」，否则它没法用自己的余效应。它**不能**读写的：两个声明之外的任何表、任何控制字段、任何没有表持有的东西。这正是「组件不能根据它没声明的纤维的生命周期状态分支」的形式化，也是 §4.3 能把 Table 1 当作写操作完整清单的原因。

**Definition 56** 再定义「对 `n` 的上下文中介迭代器」`ℑ^𝒜_Γ(n)`：单位元，加上三种迭代形式——`d_n ∪ p_n` 里的操作阶段、`p_n` 里的提供阶段、以及实例化。每个纤维的效应函数都必须属于它。**Lemma 57**：`ℑ^𝒜_Γ(n)` 的成员对 `n` 是 confined 的，且落在 `ℑ^{d_n ∪ p_n}_Γ` 里（即满足 Definition 48 要的见证）。

几点需要展开：

**恢复精确性**（Thm 68）的形式陈述是

```math
g^u_n(\gamma^u) \simeq_K (\Psi^{t_l} \circ \cdots \circ \Psi^{t_1})(\gamma^b)
```

其中 `t₁ < ⋯ < t_l` 是 `[b, u)` 里**作用于 `n` 以外**纤维的那些步。原文 (55) 里 `γ` 与 `Ψ` 的指标写成**上标**（`γ^u`、`γ^b`、`Ψ^{t_i}`）；同一段的证明里又写成下标（`h(Ψ_u(γ_u))`），这是原文自身的记法不统一，语义相同。

读法：在第 `u` 步跑 `n` 的累加器，得到的是「那些外来步照做一遍、但 `n` 从未开始」的表的等价状态——控制字段不在比较范围内。**这个读法有前提**（原文紧接公式后说明）：`[b, u)` 内没有 `n` 实例化的纤维走步；否则右侧不是「`n` 从未开始」的状态，因为那样一条纤维本来不会存在、也就不会走那一步。证明是对 `u` 归纳，每步用两种事实之一：若该步作用于 `n`，用 `𝔈*` 的见证（`h(Ψ_u(γ_u)) ≃_{d_n∪p_n} γ_u`，再由 Lemma 57 升到 `≃_K`）；若作用于 `m ≠ n`，用独立性（Lemma 66）或纠缠情形（Lemma 67）把 `g^n_u` 与 `Ψ_u` 交换。

**纠缠（entangled）**是独立性覆盖不到的那类键对：`p_m ∩ (d_n ∪ p_n) ≠ ⌀` 或对称。作者说得很坦白：消费者的操作作用在提供者的扩展所装的那个值上，所以在绑定缺席的每个状态上两个顺序都不同——无论按哪个等价读都不同。Definition 65 对这一类仍要求**共享键上的操作交换**（第二分支），而 Lemma 67 补的是交换性也救不了的方向，且分两种情形：(1) 当 `p_m ∩ (d_n ∪ p_n) ≠ ⌀`（一方提供、另一方声明）时 `Ψ_t = id_Γ`——guard 挡住提供者的 `L-Unload`，它在消费者装好期间到不了 `Inactive`，只剩 `L-Leave`/`O-Retire` 这类 `Ψ = id` 的步，是**规则**在替代独立性；(2) 另一方向 `p_n ∩ d_m ≠ ⌀` 时两者在 `γ_t` 上交换——靠的是该键的交换性。这是「定理依赖演算而非仅依赖代数」的地方，也是这套框架不能随便换一个运行时还成立的原因。

**排序（Thm 70）**的第二款——提供者的 episode 严格**包含**消费者的 episode——是「依赖者的去激活先完成、提供者才撤」的形式版本；第三款——键的值只在声明它的纤维的操作下移动——是「transition 不跨两份 resolution」的另一半。实现里对应三行（§5.1.3，p63）：`reload` 在第 14 行提交视图、`unload` 在跑完所有逆之后才丢弃它；`refresh` 在第 10 行先把纤维标成 `UNLOADING`（即 `L-Leave`）再创建 transition 任务；`unload` 在第 25 行等所有被通知的依赖者到 `INACTIVE`（即 guard）。

**进展（Thm 73）**的三个前提要看清：`≺` 无环、`len(e_n) ≤ K`、名字集有限。`≺` 是「`n` 可能提供 `m` 声明的键」（`p_n ∩ d_m ≠ ⌀`），**无环是假设而不是定义给的**——`n ≺ n` 对一个声明自己提供的键的组件成立。作者明确说 `≺` 排的是**激活**而不是生命期：`n ≺ m` 说 `n` 必须先 `Active` 才能让 `m` 激活；而「提供者活得比消费者久」是 Thm 70(2)，是带 guard 的演算的定理。终止性证明给的上界 `S(n) ≤ (K+3)(V(n)+1)` 里，`V(n)` 是目标视图翻转次数；`V(n) ≤ 1 + Σ_{m≺n} S(m)` 靠无环性做良基递归。名字集有限也是**假设**：宿主持有的组件是运行前给定的有限程序，只要没有组件能（间接地）实例化「自己这个组件的纤维」，实例化就构成有界深度的树，`len(e_n) ≤ K` 再界住分支。

**合流（Thm 80）**的直觉最值得工程读者记住：**动态历史不留痕**。编排者加一个组件、移除它、替换一个提供者、再撤销替换，最终一定到「一开始就把最终组合写下来」的那个状态；组件作者推理「哪些余效应在作用域内」时只需推理静息态。规范形式的存在性靠三步：闭合的 episode 先按 `⊲`-极大消去（Lemma 79）、编排步前移（Lemma 78(2)）、episode 排序并连成块（对 `|A|` 归纳）。前提是 **total on provision**（Definition 76：完成的激活装上了 `p` 的每个键，于是 `Active` 纤维的 `dom(σ_n) = p_n`）——没有它，support set 只是 `Active` 集合的**过近似**（Lemma 77 才能把两者等同）。作者也点明合流说的是**状态**，不是系统沿途产生的 emission（§6.1 的 acquisition/emission 之分）。

### ctx.effect：唯一的变更原语

**所有上下文变更都走 `ctx.effect`**——余效应提供、组件实例化、以及任何其它改上下文的操作都归约到它，所以任何经上下文做的操作都自动被追踪、在组件卸载时被撤销。它是 `effectiter_Γ` 的实现：接收 `ℑ_Γ` 的回调，提升成 `ℑ_{∂Γ}`，返回一个 `dispose` 闭包。`𝔈_Γ` 与 `ℑ_Γ` 通过同一个操作接受（ad-hoc 多态），因为普通效应函数是「只产出一个逆」的退化迭代器。

Algorithm 1（p59）的核心是一个 `execute(callback, guard)` 循环：每步 `await iter.next()`，若拿到值就把逆**前插**到累加器（`inverse ← value ∘ inverse`，于是 LIFO），每步之前查 `guard()`；guard 一旦跳闸就停止迭代、只保留已累积的逆。`ctx.effect` 是它的薄包装，加两件事：

1. **自撤销**：guard 读 `armed` 标志，返回的 `dispose` 把它翻成 `false`，同时**中止在飞的迭代**并让恢复**至多发生一次**。作者给了理由：跑两次会把逆应用到一个「没有任何应用产生过」的状态上，那里没有任何东西保证它能撤销什么。
2. **父级复合**：`dispose` 被前插到外层上下文的 `ctx.dispose` 上，于是子效应的逆本身是父上下文上的一个效应——这正是 `∂²Γ` 的递归结构。

组件层复用同一个 `execute`，只把 guard 换成「`fiber.target` 是否稳定」。

**这里必须记下作者自己声明的实现缺口**（§5.1.1，p59）：`ctx.effect` **不检查 `𝔈*_Γ` 的见证**。回调提供逆，而「这个逆确实撤销了这个效应」是**组件作者的义务**，不是运行时验证的性质；Theorem 68 用到它的地方正是这里，§6.1 划定这个义务的边界。余效应的见证（交换性）**同样不检查**。也就是说：**元理论依赖的两类见证，在实现里是两个未强制执行的责任**；除此之外，§4.3.4–§4.3.5 的 `≺` 无环、名字集有限、`len(e_n) ≤ K` 与 total on provision 也同样不由运行时检查。这些合起来决定了「结构保证」这句话能读多重——它不是疏漏，而是论文明确的设计选择。

### 余效应操作与响应式通知

三个符号键槽：`@@store`（`σ`：域符号 → 值）、`@@isolate`（`ρ`：键 → 域符号）、`@@intercept`（`ι`）。`ctx.get(key)` 先读 `ρ(k)` 再读 `σ(ρ(k))`（Algorithm 2）。

`ctx.set(key, value)` 是 `set(k, v)` 的实现：回调把值绑进 `σ` 的 `ρ(k)` 下，返回的 dispose 删掉它；**装与删都调用 `notify`**（Algorithm 3）。`notify` 遍历 `all_fibers`，对每个声明了变化键、且该键解析到同一域符号的纤维调 `refresh`，并返回被重估的纤维供调用者等待。这就是 Definition 22 的三分类落地：翻转满足性的变化激活或去激活，`refresh` 的幂等性让中性变化无害。

两个实现细节值得注意：

- **可用性按「提供者 Active」判**，而不是只看 store：`refresh` 把每个声明键解析到**活跃**提供者。于是「提供者已进入 `UNLOADING` 就停止提供」让依赖者在撤下**前一步**就看到，从而在它的绑定都还在时开始自己的 teardown。
- `notify` 是**对全部纤维的线性扫描**（Algorithm 3 第 3 行 `for fiber in all_fibers`），没有索引。论文没有给复杂度或实测——这在有数千纤维的宿主里是个真实的成本问题，属于「作者未测量」的范围。

### proxy 访问与 capability

`ctx[key]` 用 TypeScript 的 `Proxy` 的 `get` trap 中介（Algorithm 6，p64）：从访问方上下文沿纤维链**向上**走——第一个 `committed` 视图里绑定了该键的纤维授权并返回该绑定；若走到一个**声明了**该键但还没提交的纤维，说明它没加载，访问失败（`INACTIVE_ACCESS`）；若走到 root 都没声明，按未声明拒绝（`UNDECLARED_ACCESS`）。

这与裸 `ctx.get` 的区别正是**访问控制**：`ctx.get` 是对 store 的查表，返回值或空、从不失败；proxy 则对着访问方自己的视图解析，并在**使用点**强制 `d`。读视图而不是读 store 也是 Thm 70 依赖的东西——它让「因依赖消失而被触发 teardown 的组件」在整个 teardown 期间仍能读到那个依赖。作者还指出：因为 `d` 是静态声明的，这个违规**原则上可以在编译期**对每个 `ctx[key]` 检查（§6.4 讨论宿主语言怎么承载）。

### 加载器：声明式配置与协调

加载器把「编排者想装什么」变成一份**持久记录**（Definition 81 的 entry：`id`、`url`、`isolate`、`intercept`、`config`、`disabled`），再把记录的变化翻译成纤维操作。entry 能当规格用，是因为**支持集读的正是 entry 记的东西**：`disabled` 给 `τ`、树里的父给 `π`、`url` 选组件从而给 `d` 与 `p`。

协调按字段分派（§5.2.1，p66）：`id`/`url` 变化 → 重建条目；`isolate` → 重指派域（Algorithm 7）；`intercept` → **原地更新**（元数据在读取时被查，不需要重载）；`config` → 交给组件自己决定（典型是按差异比较、只在实质变化时重载）；`disabled` → 置位时卸载、清除时重载。

四条「为什么增量协调是可靠的」直接对应四条定理：Thm 80 说静息态只由最终配置决定（所以中途怎么做都行）；Thm 73 说系统确实会静息（所以发出装卸就算完成）；Cor 69 说离开的纤维贡献为零（所以重建一个条目只撤它自己装的东西）；Thm 70 说条目可以**一起**实例化、编排者不必安排加载顺序（依赖不满足的纤维在 `L-Begin` 处等，提供者离开时消费者先被去激活）。最后一条有个具体的工程收益：依赖约束的是**纤维何时激活**而不是**模块何时被抓取与求值**，所以加载器可以**并发**取模块——作者说「bring up a large configuration spends its time」正是在这里。

**受管域**（managed realms）是 `isolate` 的加载器版本：`true` 选条目私有、以 `id` 标记、随条目移动的局部域；字符串选全局共享域。重指派域的难点是「一个域符号可能被多条纤维共享，其中只有一条是提供者」，加载器用**定界符**（delimiter）解决：每个键一个符号 `δ_k`，每个上下文在它下面存一个自己的 tag，tag 写在条目上下文上并被后代继承，所以「条目的 tag 与提供者的 tag 相同」恰好等价于「两者在同一个 isolate 作用域内派生」，也就等价于「`k` 的绑定是条目自己的、要跟着它走」（式 64）。Algorithm 7 据此把绑定从 `s₁` 搬到 `s₂`，并用 `affected` 精确挑出受影响的依赖者。

### HMR：三阶段

§5.2.2（p67–69）把「可逆效应模式」用在模块级：文件变了，就地替换受影响的模块而不重启进程。因为纤维已经界定了组件的全部效应与余效应，**模块只要本身是一个组件，就能纯靠纤维操作替换**——丢掉旧纤维恢复它装的一切，从重载模块实例化新纤维重装。因此它**不需要** Webpack/Vite HMR 那种开发者标注的 acceptance 边界。

三个阶段：**模块分类**（Algorithm 8：以变化文件为种子，从 import 关系求不动点——一个模块只要有一个 import 被接受就被接受，全部 import 被拒就被拒，剩下的（落在 import 环里的）默认拒绝）；**陈旧条目检测**（Algorithm 9：沿每个条目的依赖树走，把 `declined` 当边界，树与 `accepted` 相交则条目陈旧）；**事务式重载**（Algorithm 10：先失效缓存并备份，再对每个陈旧条目 `dispose` 旧纤维、`ctx.use` 新模块；任一 import 失败就恢复缓存、从备份重建所有陈旧条目再抛错）。

事务性是这里唯一有「全或全无」语义的地方，也是整个 §5 里最接近工程实践的一处。

## 案例：Koishi（§5.3）

Koishi 是建在 Cordis 上的开源聊天机器人应用框架：四年开发、**4000+ 社区贡献插件**（IM 适配器、数据库驱动、管理台、最终用户功能——原文 `end-user features`）。作者用它支持两个论点：

- **表达力**：Koishi 的每个功能都是 §5.1 原语之上的插件，Koishi 自己只贡献聊天机器人领域的词汇。而且同一个模型在**完全不同的运行时**里复现——Koishi 的 Web 控制台是第二个独立的 Cordis 应用，它的插件组合的是浏览器与 UI 的原语。所以这套原语足以承载一个完整生产系统，且不预设领域或运行时。
- **时间可组合性无认知负担**：§1.2.1 里那些插件系统不能在不重启宿主的情况下卸载单个扩展；Koishi 经常做这件事——编排者在控制台禁用一个插件，它的效应就地撤销；开发时 HMR 在保存时重新应用被改的插件，同时保留别处的缓存状态与活连接。因为经上下文的效应被自动追踪、逆被自动复合，**即使经验不足的作者也能得到有序清理，而不用写卸载路径**。这正是 §1.2.1 指出缺失的关注点局部性：本来依赖每个作者勤勉的正确性，由抽象一次性承担。
- **空间可组合性跨开放生态**：与 §1.2.1 那些几乎没有插件间依赖的系统相反，Koishi 的生态有真实的依赖拓扑——IM 适配器提供平台访问、数据库驱动提供持久存储、功能插件把这些声明成余效应再访问。运行时重配一个提供者（换存储后端、重连适配器）只重新激活**解析到的依赖变了**的那些依赖者；依赖不可用的插件保持 inactive 直到它出现，不报错。作者强调的是：这种组合**跨独立编写的代码**成立——插件与它的依赖通常由不同作者写、除了连接它们的余效应之外不协调任何东西。

**证据边界**（作者自述，p70）：单一生态、单一宿主语言，所以**无法**把范式的功劳与 TypeScript 实现或 Koishi 特定领域的功劳分开；且是观测性的，不是与替代架构的受控比较。结论是「存在性与采用度」而不是定量的。此外 p69 脚注 4 说明：**Koishi 当前用的是 Cordis v3，本文呈现的是 v4**（核心组合模型两版共享，v4 精化了 effect/coeffect 语义并重设计了加载器）。所以这 4000+ 插件的采用事实，严格说是 **v3 生态**的事实。

## 讨论：值得工程读者读的部分（§6）

### 系统边界：acquisition 与 emission

§6.1（p70–71）是全文对「完整恢复」最重要的限定。边界把环境分成两半：一个位置在**界内**，当系统能独占修改它、并能恢复修改前的状态——那么它上面的操作被追踪进 `Γ`、可撤销；在**界外**，当两个能力有一个不成立——那么操作就是 `id_Γ`，既不追踪也不撤销。

**余效应移动边界**：它把一个外部位置具体化，把对该位置的每次访问限制在它提供的一组操作里、每个操作都能给逆，于是原本 `id_Γ` 的操作变成被追踪、可撤销的。所以边界是**按位置**画的，不是按介质：一块内存区域在界内当且仅当只有系统写它；一个文件在界内当且仅当只有系统能到达它（私有路径下的临时文件）。

一个操作越界时通常分两段：**acquisition**（取得访问权、在界内装一条记录——`open` 装描述符、`malloc` 预留块、`fork` 起子进程）与 **emission**（把数据推过这条通道——`write` 把字节交给文件、`send` 把数据报放到线上）。前者留在界内，后者跨到界外。所以「已发送的消息不会回来」**不是实现缺陷，而是边界定义的一部分**。

必须从 emission 恢复的系统只有两条路：**withhold**（把 emission 压到产生它的状态确定持久之后，即 rollback-recovery 的 output commit 问题）与 **compensation**（用应用提供的、比 `≃` 更粗的等价来恢复——删掉刚建的文件、退款）。补偿按同样的 LIFO 复合，所以 §3.1 的复合可迁移；但**元理论不迁移**：Definition 65 的交换性是对 `≃` 证的，得对更粗的等价重新建立。这一段是全文最诚实的地方，也是任何想把「完整恢复」写进产品文档的人必须读的一段。

### 服务多路复用：broker 而不是多提供者

单源纪律下「一个键一个提供者」，所以「一个服务多个实现」要靠两种形式（§6.2，p71–72）：**独占绑定**（多个实现共享一个接口但至多一个绑定，切换要卸一个装一个，**瞬时扰动每个消费者**）与**服务代理**（一个中心服务作为接口入口，被后端提供者与消费者同时注入，由它分发；更新后端时代理不动，消费者看不到依赖变化、不触发重载）。代理支撑三件事：负载均衡（轮询/最少负载/延迟加权，提供者是普通组件，注册是可逆效应，卸载自动掉出路由集）、滚动更新（新提供者作为额外纤维加载并注册，`ACTIVE` 后逐步转移流量，旧的不再承载在飞请求后卸载——把基础设施级的蓝绿部署变成应用级组合模式）、跨进程调用（每个进程有自己的 Cordis 上下文，协调组件把远程提供者当本地提供者，RPC 保持接口；但跨进程调用有延迟且可能中途失败，所以暴露的接口必须按异步契约设计）。

### 访问控制与沙箱

依赖访问机制本身已是一种访问控制：组件只能访问它声明的依赖，未声明即报错——这与 capability-based security 结构相同（`inject` 是能力请求、context proxy 是能力中介），且因为请求是静态声明的，**组件所需的全部 proxy 中介能力在运行前就已知**（原文限定为 `proxy-mediated capabilities`；直接 import 或全局对象不在其中），编排者可以在加载时审查批准，而不是运行时才发现访问。

细粒度策略走 interception（§3.2.3）：访问控制元数据由上下文携带或组件声明，提供者在被调用时查它决定是否允许（例：文件系统依赖携带「哪些路径可读写」的元数据）。因为拦截活在上下文而不是任一方代码里，编排者能约束任何组件对某依赖的访问而不改提供者（社区组件给只读数据库权限、核心组件保留全权）；又因为拦截只影响**如何调用**、不影响**是否满足**，它可以运行时装卸而不触发重载、不扰动依赖图。

沙箱是另一回事：不可信代码需要超出语言级手段的执行边界（SFI、独立运行时、沙箱进程、虚拟化容器），因为能访问宿主运行时的恶意组件可以直接摸到底层对象。这时不可信组件跑在自己的沙箱上下文里，经桥接访问宿主依赖——这泛化了 §6.2 的跨进程调用，同样的透明性论证让桥接访问与本地注入不可区分；宿主侧的桥接是普通纤维，其能力可被上面的访问控制削减。

### 语言与 OS 协同

§6.4（p73–74）给出「一个语言至少要提供什么」：时间侧要**闭包**（逆必须作为值被捕获，连同它恢复的状态）以及**运行时可引入/可撤回**的代码（托管运行时用可编程模块注册表，Node.js 有；原生代码用 `dlopen`/`dlclose`、`LoadLibrary`/`FreeLibrary`；Wasm 取决于嵌入者）。空间侧要**依赖声明与注入**（DI 问题），分两层：类型层（Haskell typeclass、Rust trait、TypeScript module augmentation 都能让提供者从自己的模块扩展上下文类型）与运行时层（需要透明中介访问——JS 的 `Proxy`、Python 的 `__get__` 描述符；没有的话用运行时反射，代价是类型安全与开发体验）。两者合起来靠元编程：注解/装饰器 + 编译期宏（Rust proc macro、Scala macro、Zig comptime）为每个依赖生成带类型的声明与访问器。

§6.7（p76–77）反过来问「与范式共同设计的语言/OS 能多给什么」：语言可以让上下文重新变成**隐式**的（同时消掉「把上下文当普通参数传」带来的两个风险——组件可能经闭包或全局变量摸到别人的上下文，从而让效应泄漏出自己的生命周期、让余效应逃出自己的声明），也可以让 effect/coeffect **对编译器可见**（为整个迭代生成单个状态机、把逆存在帧里；把余效应规格纳入类型系统，从而编译期报循环依赖、并按结构而非键名比较依赖，如 row types）。OS 侧可以让「组件声明的余效应就是它能到达的全部」，把资源作为余效应提供（记录只保留一份、且天然归属于请求它的组件），并把 §6.1 只能 withhold/compensate 的操作变成可回滚的（事务式持久写、copy-on-write/不可变存储靠移指针回退）。

### 循环依赖与粒度

§6.5（p74）给了一个很干净的结论：**依赖环只是让相关组件永久 inactive**——`A` 要 `B` 提供的键、`B` 要 `A` 提供的键，两者的满足谓词都不可能变真。与并发死锁不同，这个条件**只从声明就能预测**，所以运行时可以在加载时报出来。

实践上大多数「看起来互相依赖」可以拆成更细的组件消环：server 与 access controller 双向交互，拆成 server-core、access-control-core、request-mediation（依赖两个 core，把访问控制施加到入站请求）、policy-management（依赖两个 core，经 server 暴露策略修改）。两个 core 互不依赖，只有集成组件依赖两者。作者说这种分解**原则上总是可能**（任何双向交互都能分解成独立单向绑定），代价是组件数：一般情形下 n 个互相作用的组件，集成组件数可能**随 n 二次增长**。这不影响正确性与运行时性能（组件很轻），甚至有益（用户只装自己需要的集成绑定）；但影响开发体验（更多配置、命名与认知负担）。缓解手段是工程性的：包捆绑、按命名/类型约定自动接线、从声明式规格生成样板集成组件。

### 版本与接口漂移

§6.6（p75）指出形式模型的一个真实缺口：依赖链接**只靠键身份**，`𝒱_k` 的类型一致性只在单个编译单元内成立。独立开发的组件生态里这导致两个问题：**接口漂移**（提供者改了 `k` 的接口，消费者还声明同一个 `k`，余效应层面满足但运行时不匹配——类型错误、方法不存在、或静默的行为分歧）与**键冲突**（两个独立开发的提供者用同一个键名表示完全无关的接口，消费者会接受另一个的值而没有任何兼容检查）。

三条路，从最耦合到最语言无关：**键命名空间**（键空间从 `K` 扩到 `K × P`，`P` 标识定义接口的包，构造上消除冲突，但把包命名空间嵌进形式模型、依赖外部包注册表）；**peer dependencies**（用宿主包管理器声明版本约束——**Cordis 目前采用这条**；限制是依赖提供者遵守 semver（不可强制）以及包管理器通常把依赖解析到单一版本、无法在一个应用里装同包的多版本）；**结构兼容**（把成员检查 `k ∈ dom(σ)` 换成兼容谓词，验证提供的接口结构上包含消费者期望——类似结构子类型；但语言无关地定义这个谓词很难：记录类型（宽度子类型）容易，行为契约（前后条件、效应规格）复杂，一旦引入有界量化就不可判定）。作者把「统一这三条并保持动态组合保证」列为开放问题。

## 相关工作：与本方法的差别（§7）

| 线 | 代表 | 与本文的关键差别 |
| --- | --- | --- |
| monadic effect 系统 | ZIO（`ZIO[R,E,A]`）、Effect-TS（`Effect<A,E,R>`）、fp-ts | 追踪要付 monadic 嵌入的代价（程序必须写在 effect 类型里）；requirement 由解释器满足，服务被撤走时**它做过的事仍留在原地**；Cordis 是叠加在普通宿主代码上的追踪，且每个效应配一个逆、提供者来去时重新解析需求 |
| 代数效应即能力 | Effekt（Brachthäuser 等） | 目的不同：代数效应让 effect 可见是为了**多重解释**，Cordis 是为了**追踪与撤销**；设定不同：Effekt 在类型层静态约束、能力是二等的、被限制在词法作用域（靠 boxing 恢复一等使用），Cordis 在运行时约束、目标是组件移除时的完整资源回收 |
| 可逆效应语义 | Heunen 等（dagger arrows / inverse arrows） | 最接近的形式工作，但可逆性是**全局**性质（每个计算都可逆、逆是双侧的、由范畴结构导出）；Cordis 在运行时追踪逆，只要求**每个原子效应**有单侧逆、由调用者在应用点提供，复合的逆由复合导出 |
| graded 类型统一 effect/coeffect | Orchard 等（Granule） | 都在**类型层**、编译期、词法固定作用域上做；本文把同样的两个概念提升到运行时机制，让时间撤回与空间依赖随已加载组件集合演化而**重新解析** |
| 面向上下文编程（COP） | ContextL（[95]） | 「context」指环境情形（位置、用户、模式），激活改变方法分派、layer 既不追踪也不撤销它引出的副作用、激活不由依赖满足驱动；Cordis 的 context 是中介 effect/coeffect 的 `Γ∞`，激活跑可逆效应、由响应式余效应驱动、去激活完整撤销。作者自评：Cordis 只能把 COP 的**全局、值驱动**那一小片表达成余效应 |
| 面向切面编程（AOP） | AspectJ | 声明 vs 无意识：pointcut 是 oblivious 且量化的，Cordis 把横切限制在每个组件**声明**的余效应上（范围恰好是声明面，因而确定、可追溯，编排者不必读源码）；生命周期集成：Cordis 的横切由组件效应承载、卸载时撤销、响应式传播给依赖者，动态 AOP 也能运行时织入/拆出但那是独立操作 |
| 状态前向迁移（DSU / HMR） | Hicks 等、Kitsune、Erlang/OTP、webpack/Vite | 它们把状态**前向迁移**（手写迁移函数、在安全点切换）；Cordis 撤销旧组件的追踪效应、从干净状态重装新组件，所以组件自己的内存状态**不跨重载存活**（除非放进更长命的依赖）——作者明说把 DSU 式前向迁移叠在可逆效应之上是 future work，但 Cordis 更一般的地方是不需要手写迁移、且支持彻底卸载并回收资源 |
| 开发者自写恢复 | OSGi、Eclipse extension points、Command 模式、saga、代数效应 handler 的 finalizer、event sourcing、React `useEffect` | 逆是**未强制的手写义务**、与操作解耦，忘一个就静默泄漏；`useEffect` 最接近（返回 cleanup、运行时在下次执行前与 unmount 时调用），但**可组合性**不足：hook 只能在组件或另一个 hook 顶层调用，不能在条件、循环、嵌套函数里，effect body 也不接受 async 函数或迭代器——于是效应无法由别的效应组装、无法与控制流交错，也就没有可导出复合逆的东西 |
| 静态作用域的反转 | STM、可逆计算（Janus）、可逆进程演算（RCCS、Phillips & Ulidowski）、线性类型/RAII/Rust ownership | 都由**构造**保证、但作用域**预先固定**；RCCS 的因果一致性是 Cordis 恢复顺序的并发对应物（累加器按 LIFO 应用自己的逆 + guard 推迟提供者撤出），但它的可达范围由语义固定（每个动作永远可撤），而 Cordis 组件为每个原子效应提供逆、累加器把上下文带回组合开始处 |
| 接口介入式回收 | Nooks、shadow drivers、Akeso | 最接近的系统级先例（运行时维护记录而不是靠开发者记得写清理），但**平台决定能记录什么**（每类内核对象的 release 代码、每类驱动一个 shadow、每个被插桩分配器一个逆），组件只能持有平台已知如何释放的资源；Cordis 组件引入自己的效应、为每个原子效应提供逆，且恢复范围是组件整个生命周期、并把移除传播给依赖者 |
| 初始化期依赖装配 | Spring、Guice、Angular、Inversify、Vue `provide/inject`、React Context | 初始化时注入，**不响应式重解析**：提供者被替换或移除时，已有依赖者既不去激活也不重新初始化，也没有本文这种生命周期状态机 |
| 可用性响应式组件模型 | OSGi Declarative Services、iPOJO（Gravity）、R-OSGi | 最接近的先例：声明 provided/required，运行时按服务出现/消失自动激活/去激活；但恢复靠**手写的去激活回调**（资源安全依赖开发者勤勉），且回调是**同步**的——teardown 需要与正在离开的依赖做异步交换时没有协议可等，只能对一个可能已过期的引用做阻塞等待。Cordis 的两点补足：去激活撤销依赖者累积的效应；惯性 `Unloading` 状态把异步 teardown 跑完再响应后续变化 |
| 值级响应式 | FRP、signals（SolidJS、Vue reactivity、Angular Signals） | 它们在**值级**传播、同步或在调度器下重算；Cordis 在**组件级**、加异步生命周期语义。一致性方向相反：FRP 靠「一个 turn 内按依赖图定序传播」实现 glitch freedom，Cordis 没有 turn（编排动作一次一个到达），只保证**没有单次 transition 跨两份 resolution**（Thm 71）。两者互补：Cordis 的余效应本身可以携带响应式值 |

## 工程视角：落地路径、成本与失败模式

**落地路径**（如果要在一个现有系统里复制这套东西）：

1. 先立**唯一变更原语**。所有副作用必须能写成「回调 + 逆」的形式，并由一个 `effect(callback)` 包装前插到父级累加器。这是最不可绕过的一步：只要还有绕过它的写入，`Theorem 68` 的前提就不成立。
2. 把一次加载写成**迭代器**（生成器/异步生成器），而不是一个函数。这样每一步之间才有边界，才能在边界上查目标是否变了（§4.2.2 的 `L-Divert` 粒度就是迭代器粒度）。
3. 用**键 + 声明**替换显式的服务引用。消费者声明键集 `d`，提供者声明可提供的键集 `p`；「满足」是「每个声明的键都有 Active 提供者」。
4. 把「目标」存成**提供者身份表**而不是值。否则等值替换不可见；反过来，如果确实想让等值替换传播，就撤回再装（§5.1.3 明说）。
5. 把去激活拆成「停止提供」与「应用逆」两步，并在两者之间等依赖者卸载。这一步主要由 `Theorem 70(2)`（提供者的 episode 严格包含消费者的 episode）与 `L-Unload` 的 guard 承担（Theorem 70 还有第 (1)、(3) 款），也是最容易实现错的地方：一步做完会让 teardown 读不到正在被撤的依赖。
6. 异步宿主只能取 `L-Divert` 的**落地**分支（inertia），不能中止在飞的迭代。论文的进展定理不依赖中止分支，所以仍然会静息。

**成本与代价**（论文没有量化，这里只列结构性的）：

- 每次变更多一个闭包 + 一个逆闭包；每条纤维一条累加器链；`notify` 是全体纤维的线性扫描（Algorithm 3），没有索引。
- `target` 每次余效应变化都要重算（`refresh`），按 Algorithm 5 的 `resolve(inject)` 推算，代价是「声明键数 × 查表」；实现用哈希比较避免逐字段比。
- 每个组件作者要承担两项**不被检查**的义务：逆真的撤销（`𝔈*` 见证）、同键操作真的交换（Def 46 见证）。这两项错，定理不适用而运行时不会报错——这是采用这套东西时最大的隐性成本。
- 循环依赖要靠人拆；拆完组件数可能二次增长（§6.5）。

**失败模式**（从形式模型直接读出来的）：

- **逆不完整** → 泄漏，且只在卸载路径上暴露；`O-Remove` 的 `σ_n = ⌀` 前提会兜住「表没清空」这一类，但兜不住边界外的 emission。
- **同键操作不交换** → 两个组件交错时结果依赖调度；`Theorem 43` 的任意顺序撤销不再成立。典型反例：有序 middleware 链、按「最低可用」分配的描述符。
- **在声明外的键上分支** → confinement 被破坏，`≃_{d_n∪p_n}` 上的见证失效；实现里 proxy 会拦未声明的访问，但 `ctx.get` 不会。
- **一步式去激活** → teardown 读到已被撤走的依赖；表现为「关连接池时拿不到连接」这类问题。
- **异步宿主上做「中止」语义** → 与 inertia 冲突；论文明确说这种宿主不提供 abort 分支。
- **失败不重试** → `FAILED` 纤维在环境不变时不会被 `L-Begin` 重新拉起（§4.4），需要一次 revision（重插入）才会清掉错误结果。

## 局限与待确认

**作者明确讨论的**：

- 无定量评估：开销与开发效率的度量是 future work（§5.3，p70）；全文没有**本文自己测得**的延迟、吞吐、内存或开发者效率数字（我用 `benchmark`/`latency`/`throughput`/`overhead` 全文检索确认过，命中处均为定性；§1.2.3 的「秒到分钟」是引用 [15] 的既有观察，不是本文测量）。
- 案例是单一生态、单一宿主语言、观测性而非受控比较；且跑在 **Cordis v3** 上，本文形式化的是 **v4**（p69 脚注 4）。
- 「完整恢复」是在 `≃` 与系统边界之内完整：物理状态不可原样恢复（堆布局、生成名），边界外的 emission 只能 withhold 或 compensate，且补偿的等价更粗、需要重新证明交换性（§3.3.2、§4.3.2、§6.1）。
- 进展依赖 `≺` 无环、`len(e_n) ≤ K`、名字集有限三个假设（§4.3.4，p49–50）；合流依赖 total on provision（§4.3.5，p52–54）。
- 单源纪律把「一个组件多次实例化」限制在**不提供键**的组件上（§4.1，p33）；需要同键多实现时走 realm（§3.2.3/§4.4）或 broker（§6.2）。
- 失败扩展**必须**把失败纤维排除在合流之外（§4.4，p56），因为一次迭代是否抛错取决于它遇到的状态，不同调度可能一个失败一个成功。
- 依赖链接只有键身份，接口漂移与键冲突没有解决（§6.6）；统一三条路是开放问题。

**读者根据证据提出的判断**（不是作者结论）：

- **最大的理论与实现落差是「见证不被检查」**。元理论的两类见证（逆真的撤销、同键操作真的交换）在实现里明确不被验证（§5.1.1）；此外 `≺` 无环、名字集有限、`len(e_n) ≤ K`、total on provision 这些假设同样不由运行时检查。所以「结构保证」实际是「结构 + 作者义务 + 未检查的全局假设」；作者在 §6.1 划了义务边界，但没有给出任何静态检查或运行时断言的方案。
- **`notify` 的全量扫描是可扩展性隐患**。数千纤维的宿主里每次绑定变化都扫全体，论文既没给索引方案也没给实测；这一条我只能从 Algorithm 3 的伪代码读出，属于实现细节而非形式模型。
- **合流定理对「配置相关安装」的组件不适用**。§5.2.1 承认：一个声明了键、只在某些配置下才装它的组件，loader 仍能协调，但「加载了哪些组件」这时也取决于配置。这与 Definition 76 的要求是同一件事的两面。
- **`isolate` 在运行时重指派被视为接口变更**（§4.4 的 Configuration 段），因此要走「退休—去激活—移除—重插入」的复合，而不是改一个字段。这对实现者是个不直观的约束。
- **本文对 agent harness 是动机而非证据**。§1.2.2 的论证（自演化 harness 需要这两个维度）有说服力，但 §8 把在自演化 harness 里验证列为未来方向，全文没有任何 harness 实验。

## 原文自身的表述张力

- **「carries … to a whole system」的条件性在摘要层面读不出来。** 摘要与 §1.3 贡献 4 都说元理论把时空可组合性「从单个组件带到整个交错组件的系统」，这在小节层面是真的，但两条全局结果各带实质前提：进展要 `≺` 无环（§4.3.4 明说这是假设而非定义给的），合流要每个组件 total on provision（Def 76）。同时 §4.1 的单源纪律又把「一个组件多次实例化」限制在提供集为空的组件上。这些都是正文写清的限定，但只在摘要读会得到过强的印象。
- **「完整恢复」与 `≃`、与边界的关系需要三处合读。** §3.1 的等式是状态相等，§3.3.2 立刻说这是理想化、要模 `≃` 读（堆布局、生成名），§4.3.2 又把结论限定在「表、且在每个键的 `≃_k` 之内」，§6.1 再把边界外的 emission 排除。单独引用任何一处都会把「完整」读得过强；作者没有在摘要里做这个限定。
- **§4.4 开头「每个扩展都让 §4.3 的结果保持不变」的覆盖范围过宽。** 原话是四个扩展「each leaving the results of Section 4.3 intact」，但 Failure 段随后说 "Confluence excludes failed fibers, and has to"。作者紧接着用 `and has to` 收窄了，并不是没意识到，所以这不是矛盾而是**开头的概括比实际结论宽**：对 Failure 应读作「其余结果不变、合流需排除失败纤维」。
- **案例的版本口径。** §5.3 用 Koishi 的 4000+ 插件支撑「范式在生产系统里成立」，而 p69 脚注 4 说明 Koishi 用的是 v3、本文是 v4。作者在脚注里交代了（「核心组合模型两版共享」），但正文的论证强度是按「本文这套语义已被 4000+ 插件验证」在读的，实际是 v3 生态的采用事实。
- **「无开发者标注的 acceptance 边界」是比较性断言。** §5.2.2 说 HMR「不需要 Webpack 或 Vite 那种开发者标注的 acceptance 边界」，这个对比成立的前提是「模块本身是组件」；对不是组件的模块（纯数据模块、副作用在模块顶层执行的模块），论文没有说会怎样，只把 `externals`（不能热替换、触发整重启的模块）作为输入交给分类算法。
